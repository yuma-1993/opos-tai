# Tema 5.2 · Bloque 3 — Arquitectura JEE

> [!abstract] De qué va este tema
> JEE (hoy **Jakarta EE**) es un conjunto de APIs que se ejecuta sobre un **App Server**: unas definen los **componentes** que programa el desarrollador (capa de presentación en el Web Container, capa de negocio con EJB y Web Services) y otras los **servicios** que obliga a ofrecer el servidor (JTA, JNDI, JPA, JDBC, JMS, CDI...). El tema detalla el Servlet como Front Controller, el flujo y la estructura de empaquetado de una aplicación (`.ear`, `.war`, `.jar`) y la persistencia de alto nivel con JPA. Es el añadido empresarial sobre Java SE ([[B3 - T5.1 JAVA]]).

### 1. Evolución del nombre

`J2EE` de **Sun Microsystems** → `JEE` de **Oracle** → **Jakarta EE** de **The Eclipse Foundation**.

> [!important]
> Pasar de J2EE a JEE (Jakarta) obliga a **tocar fuentes**: antes los paquetes eran `javax.*`, ahora son `jakarta.*`.

El proceso de especificación se llama **JESP** (Jakarta EE Specification Process).

## Parte II — JEE como conjunto de APIs

JEE es un conjunto de APIs. Hay dos grandes grupos:

| Grupo | Qué define | Quién lo programa |
|---|---|---|
| **Componentes** de tu aplicación | Capa de presentación y capa de negocio | El desarrollador |
| **Servicios** que ofrece el App Server | Transacciones, nombres, persistencia, mensajería... | **Obligan al proveedor** (el App Server debe ofrecerlos) |

Arquitectura Java EE (diagrama del PDF): el **Browser** (Http/Http-SSL, WebSocket) y el **Java Client** acceden al **Web Container** (Java ServerFaces, WebServices, Tag Libs, WebSockets, JSPs, Servlets), que a su vez usa el **EJB Container** (EJBs) y la **Database**. Por debajo, los servicios del servidor: Security, Dependency Injection, Transactions, JMS, Persistence, JavaMail, Connector, JDBC.

### 5. Componentes

#### Capa de presentación

Muy cerca del cliente. Están en el **Web Container**.

| Componente | Descripción |
|---|---|
| **JSP** | HTML + `<% código java %>` + objetos predefinidos |
| **JSTL** | HTML + *taglib*/etiqueta personalizada. Sacas Java de la página. Ej: `<report>` |
| **JSF** | Tags de UI predefinidos. Ej: `<datatable>` |
| **Servlets / Filter** | Reciben las peticiones HTTP y canalizan el flujo del programa a otras capas, llamando a mi código. **Capa de control** |

#### Capa de negocio

| Componente | Descripción |
|---|---|
| **EJB Session** | *Enterprise Java Beans*. Implementan la **lógica de negocio**. Sin estado (clases sin atributos) y con estado (guardan información). Son componentes **transaccionales**: el *commit* y el *rollback* están garantizados, ya están implementados. **EJB de tipo Singleton (monoinstancia)** (*Actualización 20/05/2026*) |
| **EJB MDB** | *Message Driven Bean*. **Lógica de negocio asíncrona**. Gestor de colas: está escuchando de una cola. Los gestores de colas sirven para implementar procesos asíncronos. Todos los App Servers Jakarta EE tienen un servidor de colas. **JMS** manda el mensaje a la cola, el **EJB MDB** recibe el mensaje y llama al proceso que esté configurado para ejecutar nuestro código |
| **Web Services** | **SOAP y REST**. Online. Están en el motor de Web Services |

> [!tip]
> EJB Session = lógica de negocio **síncrona** (con/sin estado, transaccional). EJB MDB = lógica de negocio **asíncrona** (escucha una cola, recibe el mensaje que manda JMS).

### 6. Servicios que ofrece el App Server

| Servicio | Descripción |
|---|---|
| **JTA** | Servicio de **transacciones distribuidas**. Monitor transaccional para gestionar transacciones en BD distribuidas. Protocolo **two-phase commit**. Todos los App Server JEE tienen un motor transaccional. Ej: CICS y Tuxedo (ver [[Transacciones distribuidas (Two-Phase Commit, Monitor Transaccional)]]) |
| **JNDI** | Servicio de **nombres**, árbol de objetos. ≈ LDAP compatible. Todos los objetos están creados en el árbol: el servidor hace el `new` de los objetos y los registra en el árbol. **Yo no hago el `new`** |
| **JPA** | Servicio de persistencia de **alto nivel**. ORM |
| **JDBC** | Servicio de persistencia de **bajo nivel**. Viene de J2SE |
| **JMS** | Servicio de colas de mensajes. Cliente. Manda mensajes a la cola |
| **JSON-P** | Servicio para documentos JSON |
| **JAX-WS** | Web Services **SOAP** |
| **JAX-RS** | Web Services **REST** |
| **Jakarta MVC** | (ver [[MVC (Model-View-Controller)]]) |
| **Jakarta NoSQL** | (ver [[B2 - T5 NOSQL Y BIG DATA]]) |
| **CDI** | Servicio de **inyección de dependencias** |

### 7. Web Container, Servlet y Filter

**Web Container**: contenedor que tiene la lógica para entender el mundo HTTP y llamar a mi código Java. Aquí viven los componentes de la capa de presentación.

**Servlet** canaliza funcionalidades de aplicación y los **Filter** se ponen delante de los Servlets para cosas muy horizontales.

**Cadena de responsabilidades (*Chain of Responsibility*)**: cada filtro hace solo una cosa, una responsabilidad. Los filtros pueden **cortar o cambiar el flujo de ejecución**, por ejemplo si no pasa ciertas validaciones. Ej: comprimir, codificar, validar, etc. Es el patrón [[Chain of Responsibility (patrón GoF)]]; el *Intercepting Filter* está en [[Patrones J2EE (DAO, Intercepting Filter, Composite View)]]. Esquema del PDF: Filter → Filter → Filter → (Servlet / Servlet / Servlet) → ServletContext.

### 8. Relación de servicios con sus objetos principales

Los objetos que ya vienen implementados los **crea el app server**, no los creo yo.

| Servicio | Objetos / anotaciones principales |
|---|---|
| **JTA** | `UserTransaction`: métodos `commit()`, `rollback()` |
| **JNDI** | `InitialContext`: método `lookup(String)` → buscar objetos en el árbol. Objetos que contiene JNDI: objetos para mails, colas de mensajes, JTA, Data Sources, EJBs de las aplicaciones, etc. |
| **JDBC** | `Driver` / `DataSource`; `Connection`; `Statement` / `PreparedStatement` (SQL precompilado: **elimina el posible SQL Injection**) / `CallableStatement` (para llamar a procedimientos almacenados, ver [[Procedimiento almacenado (Stored Procedure)]]); `ResultSet` → cursor (ver [[Cursor (SQL)]]) |
| **JMS** | `MessageListener`: `onMessage(Message)`. `Queue` / `Topic` |
| **JPA** | `EntityManager`: métodos `persist()`, `find()`, `delete()`. `@Entity` / `@Table` / `@Id` / `@Column` / `@OneToMany` |
| **JAX-WS** | `@WebService` / `@WebMethod` / `@WebParam` |
| **JAX-RS** | `@Path` / `@GET` / `@POST` |
| **CDI** | `@Inject` / `@RequestScoped` / `@Named` |

#### JMS: Queue vs Topic

| | Queue | Topic |
|---|---|---|
| Relación | **1:1** | **1:N** |
| Consumidores | Muchos pueden publicar, pero **solo uno consume**. Con una cola no puedes hacer multidifusión | Puedo tener **varios consumidores**. El mensaje se difunde a todos los receptores teniendo una única cola |

> [!important]
> Queue = punto a punto (1:1, un solo consumidor). Topic = publicación/difusión (1:N, multidifusión).

#### EJB MDB: código

```java
@MessageDriven(activationConfig = {
    @ActivationConfigProperty(propertyName = "destination",
        propertyValue = "tutorialQueue"),
    @ActivationConfigProperty(propertyName = "destinationType",
        propertyValue = "javax.jms.Queue")
})
public class ReadMessageMDB implements MessageListener {
    public void onMessage(Message message) {
        TextMessage textMessage = (TextMessage) message;
        try {
            System.out.println("Message received: " + textMessage.getText());
        } catch (JMSException e) {
            System.out.println("Error trying to consume messages: " + e.getMessage());
        }
    }
}
```

### 9. Inyección de dependencias (CDI)

| Diseño **sin** inyección de dependencias | Diseño **con** inyección de dependencias |
|---|---|
| `Clase Vista1 – new → Clase LogicaV1 – new → Clase BBDD1` | `Clase Vista1 – "referencia" → Clase LogicaV2 – "referencia" → Clase BBDD1` |
| `Clase Vista1 { LogicaV1 logica; }` | `Clase Vista1 { @Inject Logica logica; }` — el runtime EE será el encargado de colocar en ese atributo un objeto de `LogicaVxx` |
| **Argumento**: para actualizar a LogicaV2 tendremos que **modificar el código** | En un fichero de configuración definimos la versión de Logica a instanciar. Consigues **abstraerte de las versiones** |

- "Inyección de Dependencias" en JEE con **CDI** y en **Spring desde siempre**.
- Partimos de la aplicación multicapa o MVC (Presentación – Lógica – Datos).
- Relacionado con **Polimorfismo** (ver [[Polimorfismo (POO)]]).

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Esta idea de depender de una abstracción (`Logica`) y no de una implementación concreta (`LogicaV1`) es la aplicación práctica del principio D de SOLID: ver [[Dependency Inversion Principle (DIP)]] y [[SOLID (principios)]]. `@Autowired` es el equivalente en Spring, tratado en [[B3 - T4.1 PATRONES DE DISENO Y SOLID]].

### 10. Proxy inverso delante de varios servidores

Ejemplo del PDF con **Apache / Nginx (proxy inverso)** delante de dos Apps JEE y un servidor IIS + ASP.NET (ver [[B3 - T5.3 .NET]]):

| Petición del cliente | Resultado |
|---|---|

## Parte III — El Servlet

### 11. Definición

**Servlet**: es el **interface más importante**. Es el componente que canaliza una URL de petición/negocio al resto de capas de la aplicación. También llamado patrón **Front Controller**. Pasarela que comunica el mundo HTTP con la lógica de negocio. Es un **Controlador** (ver [[MVC (Model-View-Controller)]]). Es un componente invocado por el app server: código Java codificado por nosotros que va a gestionar el Web Container.

URL de ejemplo: `http://localhost:8080/<app>/calculadora?param1=10&param2=5` → `<app>` = nombre del fichero `.war` (configuración de JBoss); `calculadora` = mapeo del servlet; `param1=10&param2=5` = parámetros.

### 12. Ciclo de vida

El **Web Container** hace el `new` del servlet y llama **una única vez** al método `init()`. Cuando se apaga el app server se llama al `destroy()`. Por cada petición al servlet se llama a `service()` y éste llama a `doGet()`, `doPost()`, etc. en función del verbo.

| Método | Cuándo se llama |
|---|---|
| `init(config)` | Una única vez, tras el `new` |
| `service(req, res)` | Por cada petición; delega en `doGet()`, `doPost()`... según el verbo HTTP |
| `destroy()` | Al apagar el app server |

Son los únicos métodos que "ve" el Web Container (los que definen el ciclo de vida del Servlet).

### 13. Interfaces y clases (diagrama de clases del PDF)

Inicialmente se pensó que la Request y la Response podrían ir por otro protocolo que no fuese HTTP, por eso está separado en **2 interfaces cada una**.

| Tipo | Elementos |
|---|---|
| `«interface» ServletRequest` | `getParameter(String)`, `getParameterValues(String)`, `getAttribute(String)`, `setAttribute(String, Object)`, `removeAttribute(String)`, `getInputStream()` |
| `«interface» HttpServletRequest` | `authenticate(HttpServletResponse)`, `getCookies()`, `getDateHeader(String)`, `getHeader(String)`, `getIntHeader(String)`, `getHeaderNames()`, `getMethod()`, `getPart(String)`, `getParts()`, `getQueryString()`, `getRequestURI()`, `getRequestURL()`, `getSession()`, `getUserPrincipal()`, `isUserInRole(String)`, `login(String username, String password)`, `logout()` |
| `«interface» ServletConfig`, `«interface» Servlet` | Interfaces base |
| `GenericServlet` | `service(ServletRequest, ServletResponse)` |
| `HttpServlet` | `service(HttpServletRequest, HttpServletResponse)`, `doGet`, `doPost`, `doDelete`, `doHead`, `doOptions`, `doPut`, `doTrace`, `getLastModified(HttpServletRequest)` |
| `«interface» ServletResponse` | `getWriter()` (PrintWriter), `getOutputStream()`, `setContentType(String)`, `setContentLength(int)`, `setCharacterEncoding(String)` |
| `«interface» HttpServletResponse` | `addCookie(Cookie)`, `addDateHeader`, `addHeader`, `addIntHeader`, `containsHeader`, `encodeRedirectURL`, `encodeURL`, `getHeader`, `getHeaderNames`, `getHeaders`, `getStatus`, `sendError(int)`, `sendError(int, String)`, `sendRedirect`, `setDateHeader`, `setHeader`, `setIntHeader`, `setStatus` |
| Otros | `Cookie`, `HttpServletRequestWrapper`, `HttpServletResponseWrapper`, `«interface» Part`, `«interface» HttpSession` |

Jerarquía: `GenericServlet` implementa `ServletConfig` y `Servlet`; `HttpServlet` extiende `GenericServlet`; `HttpServletRequest` extiende `ServletRequest`; `HttpServletResponse` extiende `ServletResponse`.

### 14. Métodos clave

| Método | Función |
|---|---|
| `getParameter()` | Coge cosas de la URL |
| `getHeader()` | Coge la cabecera, por ejemplo la cabecera de autenticación |
| `addCookie()` | Crea cabeceras HTTP como `Set-Cookie` |
| `sendError()` | Manda errores **400 y 500** |
| `sendRedirect()` | Manda la nueva URL y el código **300** |

### 15. Configuración: `web.xml` y `@WebServlet`

`src/main/webapp/WEB-INF/web.xml` es donde se **mapea el nombre de la clase con el servicio de la URL**.

```xml
<servlet-mapping>
    <servlet-name>ServletCalculadora</servlet-name>
    <url-pattern>/calculadora</url-pattern>
</servlet-mapping>
```

Para evitar el fichero de configuración podemos usar anotaciones: **`@WebServlet("url")`** (*Actualización 20/05/2026: `@WebServlet` en lugar de `@WebServer`*).

### 16. HttpServlet

**HttpServlet**: clase de utilidad. Ayuda a los programadores, ya que no todas las peticiones son iguales: usan distintos verbos HTTP. El programador **no implementa la interface Servlet**, sino que **hereda `HttpServlet`**, metiendo código en los métodos `doGet()`, `doPost()`, etc.

### 17. JSESSIONID y sesión

**JSESSIONID**: nombre de la cookie que contiene el id en Java para identificar al usuario que se conecta por HTTP. Lo asigna el app server cuando se conecta por primera vez y lo mantiene durante toda la sesión. **HTTP no tiene estado**, por eso necesita las cookies (ver [[B4 - T8 HTTP SSL TLS]]).

## Parte IV — Flujo y estructura de una aplicación

### 18. Flujo de aplicación web

Diagrama del PDF: varios usuarios envían `/URL` al **HTTP CONNECTOR** del app server (sobre la **JRE**); dentro hay varias aplicaciones (*Web App – RRHH*, *Web App – Expedientes*) con Filters → Servlets → ServletContext, JSPs, y acceso a la BBDD.

| Objeto | Cuándo se crea / alcance |
|---|---|
| `req`, `res` | Se crean continuamente **en cada petición** (junto con su Thread correspondiente) |
| `HttpSession` | Se crea **por cada usuario conectado** (cookie `JSESSIONID`) |
| Servlet / Filter | Se crea **un objeto de cada clase al inicio de la app** |
| `ServletContext` | Un objeto **global compartido por todos los servlets** |

### 19. Estructura de una aplicación (`nominas.ear`)

```
nominas.ear
├── application.xml
├── empleados.war   → html/css/jsp · WEB-INF (classes\*.class, lib\*.jar, web.xml)
├── admin.war       → html/css/jsp · WEB-INF (classes\*.class, lib\*.jar [logback.jar, iText.jar, slf4j-api.jar], web.xml)
├── calculos.jar    → META-INF\ejb-jar.xml + *.class
├── informes.jar    → META-INF\ejb-jar.xml + *.class
└── servicios.jar   → META-INF\ejb-jar.xml + *.class
```

| Fichero | Contenido |
|---|---|
| `.ear` | Empaqueta toda la aplicación empresarial |
| `.war` | Aplicación web (presentación) |
| `.jar` | **Los EJB tienen formato `.jar`** |

`application.xml` (fragmento del PDF): declara los módulos web (`<web-uri>admin.war</web-uri>`, `<context-root>administracion</context-root>`, "para que no sea 'admin' ya que es admin.war") y los EJB (`calculos.jar`).

```xml
<module>
  <web>
    <web-uri>admin.war</web-uri>
    <context-root>administracion</context-root>
  </web>
  <ejb>calculos.jar</ejb>
</module>
```

`ejb-jar.xml`: **ya no se usa este fichero de configuración**; se usa con **`@Stateless`**.

```xml
<ejb-jar>
  <session>
    <session-type>Stateless</session-type>
    <transaction-type>Container</transaction-type>
    <ejb-class>...</ejb-class>
  </session>
</ejb-jar>
```

`web.xml` (ejemplo completo del PDF: filtro, servlet, seguridad, login, página de error y sesión):

```xml
<web-app>
  <filter>
    <filter-name>SecurityFilter</filter-name>
    <filter-class>com.jee.filter.SecurityFilter</filter-class>
    <init-param>
      <param-name>encoding</param-name>
      <param-value>UTF-8</param-value>
    </init-param>
  </filter>
  <filter-mapping>
    <filter-name>SecurityFilter</filter-name>
    <url-pattern>/*</url-pattern>
  </filter-mapping>
  <servlet>
    <servlet-name>AltaEmpleadoServlet</servlet-name>
    <servlet-class>com.jee.servlet.AltaEmpleadoServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
  </servlet>
  <servlet-mapping>
    <servlet-name>AltaEmpleadoServlet</servlet-name>
    <url-pattern>/altaEmpleado</url-pattern>
  </servlet-mapping>

  <security-constraint>               <!-- Configuración de seguridad -->
    <web-resource-collection>
      <web-resource-name>admin</web-resource-name>
      <url-pattern>/admin/*</url-pattern>
    </web-resource-collection>
    <auth-constraint>
      <role-name>ADMIN</role-name>    <!-- Solo podrán acceder a /admin/ con el rol ADMIN -->
    </auth-constraint>
    <user-data-constraint>
      <transport-guarantee>NONE</transport-guarantee>
    </user-data-constraint>
  </security-constraint>

  <login-config>
    <auth-method>FORM</auth-method>
    <form-login-config>
      <form-login-page>/logon.jsp</form-login-page>   <!-- Página de login -->
    </form-login-config>
  </login-config>

  <error-page>
    <error-code>500</error-code>
    <location>/errors/servererror.jsp</location>
  </error-page>
  <session-config> <session-timeout>-1</session-timeout> </session-config>
</web-app>
```

## Parte V — Persistencia de alto nivel con JPA (ORM)

Paquete `jakarta.persistence.*`. En `persistence.xml` se define el **DataSource**:

<jta-data-source>java:jboss/datasources/RRHH-DS</jta-data-source>

### 20. Métodos principales del EntityManager (EM)

| Método | Función |
|---|---|
| `persist(obj)` | Almacenar nuevas entidades en la BBDD |
| `contains(obj)` | Comprueba si una entidad está "manejada" por el EM |
| `find(pk)` | Localizar una entidad a través de una clave primaria |
| `flush()` | Provoca que los cambios pendientes del EM se sincronicen en la BBDD |
| `merge(obj)` | Convierte una entidad "no manejada" por el EM en "manejada" |
| `remove(obj)` | Eliminar una entidad de la BBDD |

### 21. Anotaciones principales de una "entidad"

| Anotación | Función |
|---|---|
| `@Entity` | Identifica a la clase como una "entidad" |
| `@Id` | Clave primaria |
| `@Table` | Para elegir la tabla donde guardar el objeto |
| `@Column` | Para elegir la columna donde guardar un atributo |
| `@OneToMany` | Para especificar relaciones 1:N con otras clases |
| `@Transient` | Indica que ese atributo no hay que guardarlo |
| `@NamedQuery` | Para especificar consultas JPQL con nombre |
| `@Query(value="código SQL", nativeQuery=true)` | Consulta SQL nativa |
| `@PrePersist` | Para un método que se lanza antes del commit |
| `@PreUpdate` | Para un método similar a un trigger (ver [[Trigger (disparador) SQL]]) |

### 22. JPQL y carga EAGER vs LAZY

**JPQL**: SQL que usa **nombres de clases en vez de tablas**. **NativeQuery** si es SQL puro.

| | EAGER (carga temprana) | LAZY |
|---|---|---|
| Qué trae | Todo lo que esté relacionado. Si pides una factura trae todos los pagos, el cliente asociado, etc. **Peligroso**: tira del hilo | Solo lo que pides |
| Por defecto | — | `@OneToOne` y `@OneToMany` son por defecto `FetchType.LAZY` |

```java
@ManyToMany(fetch=FetchType.EAGER)
```

> [!important]
> En esta fuente, `@OneToOne` y `@OneToMany` son LAZY por defecto. EAGER hay que pedirlo explícitamente con `fetch=FetchType.EAGER`.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En la especificación JPA, el valor por defecto real de `@OneToOne` y `@ManyToOne` es EAGER, y el de `@OneToMany` y `@ManyToMany` es LAZY. El PDF indica LAZY para `@OneToOne` y `@OneToMany`; para el examen, ceñirse a lo indicado por el temario y recordar solo que EAGER es "peligroso" porque arrastra todas las relaciones.

## 🔑 Resumen ultra-rápido (para repaso)

- J2EE (Sun) → JEE (Oracle) → Jakarta EE (Eclipse Foundation). De J2EE a JEE: `javax.*` → `jakarta.*`. Proceso: JESP. Versión actual: **Jakarta EE 11** (actualización 20/05/2026).
- Perfiles: Platform (completo) > Web Profile (ligero) > Core Profile (más ligero: **no Servlet, sí REST**). Jakarta EE 11 trae **Data 1.0 (nueva)**.
- Microprofile 7.1 (última): APIs para microservicios; contiene el Core Profile y las APIs de Microprofile 7.0.
- Productos: Apache TomEE, Glassfish, WebSphere Liberty, JBoss, Payara, WebLogic, WildFly.
- Componentes (los programa el desarrollador): Presentación en Web Container (JSP, JSTL, JSF, Servlets/Filter = capa de control); Negocio (EJB Session sin/con estado y Singleton, transaccionales; EJB MDB asíncrono con colas; Web Services SOAP/REST).
- Servicios (obligan al proveedor): JTA (two-phase commit; CICS y Tuxedo), JNDI (árbol de objetos, ≈ LDAP; el servidor hace el `new`), JPA (alto nivel, ORM), JDBC (bajo nivel), JMS (colas), JSON-P, JAX-WS (SOAP), JAX-RS (REST), Jakarta MVC, Jakarta NoSQL, CDI (inyección de dependencias).
- JMS: Queue 1:1 (un solo consumidor); Topic 1:N (multidifusión). MDB implementa `MessageListener.onMessage()`.
- Objetos: JTA `UserTransaction` (commit/rollback); JNDI `InitialContext.lookup()`; JDBC Driver/DataSource, Connection, Statement/PreparedStatement (evita SQL Injection)/CallableStatement, ResultSet (cursor); JPA `EntityManager` (persist/find/delete); `@WebService`, `@Path/@GET/@POST`, `@Inject/@RequestScoped/@Named`.
- Inyección de dependencias (CDI en JEE, Spring desde siempre): `@Inject` en el atributo; el runtime coloca el objeto; abstrae de las versiones; relacionado con polimorfismo.
- Servlet = interface más importante, patrón **Front Controller**, es un Controlador. Ciclo de vida: `init()` una vez → `service()` por petición (→ `doGet`/`doPost`...) → `destroy()` al apagar.
- Se hereda `HttpServlet`, no se implementa `Servlet`. Configuración en `WEB-INF/web.xml` o con **`@WebServlet("url")`** (no `@WebServer`).
- `sendError()` → 400/500; `sendRedirect()` → 300; `addCookie()` → `Set-Cookie`; `getParameter()` → URL; `getHeader()` → cabecera.
- Filters = Chain of Responsibility: cada uno hace una cosa, pueden cortar el flujo; se ponen delante de los servlets.
- JSESSIONID = cookie de sesión asignada por el app server (HTTP sin estado). `req/res` por petición; `HttpSession` por usuario; Servlet/Filter un objeto por clase al inicio; `ServletContext` global.
- Empaquetado: `.ear` (aplicación) con `.war` (web) y `.jar` (EJB); `application.xml` (con `context-root`), `web.xml`, `ejb-jar.xml` (ya no se usa: `@Stateless`).
- JPA: paquete `jakarta.persistence.*`, DataSource en `persistence.xml` (`<jta-data-source>`). EM: persist, contains, find, flush, merge, remove. Anotaciones: `@Entity`, `@Id`, `@Table`, `@Column`, `@OneToMany`, `@Transient`, `@NamedQuery`, `@Query(nativeQuery=true)`, `@PrePersist`, `@PreUpdate`.
- JPQL usa clases en vez de tablas; NativeQuery = SQL puro. EAGER (trae todo, peligroso) vs LAZY (solo lo pedido; `@OneToOne` y `@OneToMany` LAZY por defecto según la fuente).

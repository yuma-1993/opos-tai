# Tema 7.3 · Bloque 3 — XML, JSON, XPath y YAML

> [!abstract] De qué va este tema
> XML es un estándar de la W3C derivado de SGML para estructurar, intercambiar y estandarizar información (interoperabilidad). El tema cubre su sintaxis (declaración, DOCTYPE, entidades, CDATA, espacios de nombres), la diferencia entre XML **bien formado** y **válido** (DTD / XSD), las transformaciones XSL, las tres APIs de programación (DOM, SAX, JAXB/StAX), los lenguajes de marcado ligeros (Markdown, reStructuredText), JSON (con JSON Schema y JWT), XPath y YAML. Incluye al final el ejercicio resuelto del "catálogo XML bien formado".

> [!note] Tema relacionado
> Los estándares/formatos basados en XML que ya tienes sueltos en la bóveda: [[XMI (XML Metadata Interchange)]] (intercambio de modelos UML), [[XMLDSIG]] (firma XML) y [[OOXML (Office Open XML)]] (formatos ofimáticos). SQL también incorporó XML (SQL:2006) y JSON (SQL:2016): ver [[B3 - T3 SQL]].

---

## 1. Qué es XML

Estándar de la **W3C**. Deriva de **SGML**. Sirve para estructurar la información de configuración, para intercambio de información y para estandarizar el formato de la información, permitiendo **interoperabilidad**.

XML le añade ciertas restricciones a SGML para simplificarlo:

| Restricción XML sobre SGML |
|---|
| Todas las etiquetas llevan cierre (incluso los *empty elements*) |
| Los valores de los atributos deben ir entre `" "` |
| Es *case-sensitive* |

> [!important] HTML y XML
> **HTML4** estaba completamente alineado con SGML. **HTML5 no**. **XHTML** estaba basado en las reglas de XML (MIME = `application/xhtml+xml`). Más sobre tipos MIME: [[Tipo MIME]].

## 2. Sintaxis de un documento XML

```xml
<!-- La declaración es opcional -->
<?xml version="1.0" encoding="utf-8" standalone="no"?>
<!DOCTYPE empleados SYSTEM "empleados.dtd">
<empleados>
  <empleado id="1">
    <nombre> pepe </nombre>
    <intereses> leer &amp; caminar </intereses>
    <observaciones> <![CDATA[texto que el parser no analiza]]> </observaciones>
    <role />
  </empleado>
</empleados>
```

> [!note] Nota sobre el ejemplo
> En el PDF la declaración aparece escrita como `versión` (con tilde); el nombre real del pseudo-atributo es `version`. En el PDF, junto a `SYSTEM` aparece también la palabra `PUBLIC` como alternativa para enlazar el DTD.

| Elemento del ejemplo | Qué es / qué significa |
|---|---|
| `<?xml version="1.0" encoding="utf-8" standalone="no"?>` | Declaración: empieza por `<?xml`. La **versión es obligatoria**, pero `encoding` y `standalone` **no** son obligatorios |
| `standalone="no"` | Indica que el **DTD está en un fichero externo**. `"yes"` indica que la gramática está contenida en el mismo XML y no necesita DTD. **Por defecto `standalone="no"`** |
| `<!DOCTYPE empleados SYSTEM "empleados.dtd">` | Sirve para **enlazar el DTD** (`SYSTEM` / `PUBLIC`) |
| `id="1"` | Es un **atributo** |
| `&amp;` | Es una *entity* (≈ macro de escape). El analizador XML lo sustituye por `&`. `&lt;` = `<` |
| `<![CDATA[ ... ]]>` | El analizador **no lo interpreta** y lo devuelve literalmente |
| `<role />` | *Empty element*: **no pueden tener hijos pero sí atributos** |

> [!example] Entidades predefinidas
> `&amp;` → `&` · `&lt;` → `<` (ambas aparecen en el PDF).

### 2.1 Espacios de nombres

Posibilidad de incluir **prefijos** en las etiquetas para **evitar duplicados de etiquetas con el mismo nombre**. **Los DTD no dan soporte a los espacios de nombres.**

```xml
<root xmlns:h="http://uri-a" xmlns:f="http://uri-b">
  <h:tag1> ... </h:tag1>
  <f:tag1> ... </f:tag1>
```

## 3. XML bien formado vs. XML válido

| XML **bien formado** | XML **válido** |
|---|---|
| Sintaxis XML | Según DTD/XSD |
| Solo existe un **único elemento raíz** | El documento debe estar **bien formado** y además cumplir con las reglas de la gramática especificadas en el DTD / XSD |
| Todos los elementos están **anidados y correctamente cerrados** | |
| Los valores de atributos van entre **comillas simples o dobles** | |
| Los elementos vacíos terminan con `/` (autocierre) o etiqueta de fin | |
| Las etiquetas son alfanuméricas, comenzando con una **letra, `_` o `:`** | |

> [!important] Clave de examen
> Válido ⊂ bien formado: todo XML válido es bien formado, pero no al revés. Bien formado = sintaxis; válido = además cumple la gramática (DTD/XSD). Ejercicio práctico de errores de bien formado: ver sección 9.

## 4. Gramática: DTD y XSD

**DTD / XSD** = *Document Type Definition* / *XML Schema Definition*. La definición de la estructura/gramática con **DTD fue la primera** y es **menos flexible** en definición de tipos de datos, restricciones, etc. **DTD no especifica tipos de datos.** **XSD** permite definir restricciones a los posibles valores de los tipos de datos, y se pueden establecer en diferentes aspectos, llamados **facetas**.

### 4.1 Facetas XSD

| Faceta | Faceta | Faceta |
|---|---|---|
| `xs:length` | `xs:minLength` | `xs:maxLength` |
| `xs:pattern` | `xs:enumeration` | `xs:whiteSpace` |
| `xs:maxInclusive` | `xs:maxExclusive` | `xs:minExclusive` |
| `xs:minInclusive` | `xs:totalDigits` | `xs:fractionDigits` |

### 4.2 DTD interno (gramática y datos en el mismo fichero)

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<!DOCTYPE deportistas [
  <!ELEMENT deportistas (futbol | f1 | tenis)*>
  <!ELEMENT futbol (#PCDATA)>
  <!ELEMENT f1 (#PCDATA)>
  <!ATTLIST f1 pais CDATA>
  <!ATTLIST f1 fecha_de_nacimiento CDATA #IMPLIED>
  <!ATTLIST f1 equipo CDATA #REQUIRED>
  <!ELEMENT tenis (#PCDATA)>
]>
<deportistas>
  <f1 pais="Alemania" fecha_de_nacimiento="03/07/1987" equipo="Ferrari">Sebastian Vettel</f1>
  <f1 equipo="McLaren">Fernando Alonso</f1>
  <tenis>Rafael Nadal</tenis>
</deportistas>
```

| Elemento DTD | Significado |
|---|---|
| `<!ELEMENT ...>` | etiqueta = *element* |
| `*` | 0 o N |
| `+` | 1 o muchos |
| `?` | 0 o 1 |
| `#PCDATA` | Indica que es **texto** |
| `ANY` | Contenido **mixto**: dentro de la etiqueta podemos tener etiquetas o textos |
| `EMPTY` | *Empty element* |
| `ID` / `IDREF` | Otros tipos de atributos: **clave primaria y ajena** (`GetElementByID`) |
| `#REQUIRED` | Atributo **obligatorio** |
| `#IMPLIED` | Atributo **opcional** |
| `#FIXED` | Atributo con **valor fijo** |

> [!note] Nota sobre el ejemplo
> El PDF escribe `<!ATTLIST f1 pais CDATA>` sin declaración por defecto (tal cual aparece en la fuente); en un DTD completo tras el tipo va `#REQUIRED`, `#IMPLIED` o `#FIXED`.

### 4.3 XSD: ejemplo `aeropuerto.xsd` y su documento de datos

```xml
<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
<xs:element name="aeropuerto">
  <xs:complexType>
    <xs:all>
      <xs:element name="nombre" type="xs:string"/>
      <xs:element name="vuelos">
        <xs:complexType>
          <xs:sequence>
            <xs:element name="vuelo" minOccurs="0" maxOccurs="unbounded">
              <xs:complexType>
                <xs:sequence>
                  <xs:element name="diario" minOccurs="0"/>
                  <xs:element name="origen" type="xs:string"/>
                  <xs:element name="destino" type="xs:string"/>
                  <xs:element name="hora-salida" type="xs:time"/>
                  <xs:element name="hora-llegada" type="xs:time"/>
                </xs:sequence>
                <xs:attribute name="código" type="xs:ID" use="required"/>
                <xs:attribute name="estado" default="E">
                  <xs:simpleType>
                    <xs:restriction base="xs:string">
                      <xs:pattern value="[CER]"/>
                    </xs:restriction>
                  </xs:simpleType>
                </xs:attribute>
              </xs:complexType>
            </xs:element>
          </xs:sequence>
        </xs:complexType>
      </xs:element>
      <xs:element name="fecha" type="xs:date"/>
    </xs:all>
  </xs:complexType>
</xs:element>
</xs:schema>
```

Documento de datos que cumple ese XSD (y cómo se enlaza):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<aeropuerto xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"     <!-- 1 -->
            xsi:noNamespaceSchemaLocation="aeropuerto.xsd">           <!-- 2 -->
  <nombre>JFK</nombre>
  <vuelos>
    <vuelo código="V22" estado="R">
      <diario />
      <origen>New York</origen>
      <destino>Chicago</destino>
      <hora-salida>09:30:00</hora-salida>
      <hora-llegada>11:30:00</hora-llegada>
    </vuelo>
    <vuelo código="V23" estado="C">
      <origen>New York</origen>
      <destino>Miami</destino>
      <hora-salida>10:15:00</hora-salida>
      <hora-llegada>11:15:00</hora-llegada>
    </vuelo>
  </vuelos>
  <fecha>2013-12-20</fecha>
</aeropuerto>
```

> [!important] Enlazar el fichero de datos con la gramática (XSD)
> 1º se da de alta el espacio de nombres **`xmlns:xsi`** (XML Schema Instance) y 2º se asocia el XSD con `xsi:noNamespaceSchemaLocation`.

| Concepto XSD | Qué hace |
|---|---|
| `sequence` | Obliga a un **orden**: p. ej. obliga a que `nombre` sea el 1.er elemento |
| `all` | Elementos **sin orden** |
| `choice` | **Cualquiera** de ellos |
| `minOccurs` | Si no se especifica es **1** (el PDF lo escribe como `minOcurrs="0"`) |
| `pattern value="[CER]"` | Solo vale `"C"`, `"E"` o `"R"` |
| `complexType mixed="true"` | Contiene **cosas de diferentes tipos** |
| `xs:extension base="infoPersona"` | Las **extensiones** permiten definir un tipo a partir de otro (≈ **herencia**) |
| Tipos propios | La estructura de un Schema permite usar **más tipos de datos, incluso definir los nuestros propios** |

> [!important] Atributos
> En XSD, igual que en todo XML, **los valores de los atributos siempre entre comillas**.

Ejemplo del PDF de tipo propio (`numeroMes`, entero entre 1 y 12):

```xml
<xs:element name="mes" type="numeroMes"/>

<xs:simpleType name="numeroMes">
  <xs:restriction base="xs:integer">
    <xs:minInclusive value="1"/>
    <xs:maxInclusive value="12"/>
  </xs:restriction>
</xs:simpleType>
```

> [!tip] DTD vs XSD en una línea
> DTD = primero en aparecer, sin tipos de datos, sin espacios de nombres. XSD = es XML, con tipos, facetas, tipos propios, extensiones y espacios de nombres.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Un XSD es a su vez un documento XML (de ahí el prefijo `xs:` del espacio de nombres `http://www.w3.org/2001/XMLSchema`), cosa que no ocurre con la sintaxis de un DTD. Las entidades predefinidas de XML son cinco: `&lt;`, `&gt;`, `&amp;`, `&quot;` y `&apos;`.

## 5. Transformaciones XSL

**XSL** siempre ha sido un API, una tecnología que sirve para **transformar datos**. **Ya está obsoleto.**

| Tecnología | Qué hace | Ejemplo de procesador |
|---|---|---|
| **XSLT** + Processor | Fusiona un XML con un XSLT y da como resultado **otro documento de marcas** | **Apache Xalan** |
| **XSLFO** (*Formatting Object*) | Fusionar un XML con un XSLFO da como resultado un **entregable** (PDF, imagen, etc.) | **Apache FOP** |

## 6. APIs de programación para XML

| API | Qué hace | Parser Java | Implementación |
|---|---|---|---|
| **DOM** | Árbol de objetos en memoria (nodos genéricos) | `DocumentBuilder` | Apache Xerces |
| **SAX** | Eventos, *forward-only* | `SAXParser` | Apache Xerces |
| **JAXB** | Árbol de objetos de **tus clases de negocio** | (`xjc` genera las clases desde un XSD) | — |

> [!note] Actualización 20/05/2026 (fe de erratas de Velilla, entrada del 06/08/2025 sobre B3-T7.3)
> "Corregida errata: lo correcto es **Apache Xerces** en lugar de Xerces. En el tema de Java aparece correcto." Aplicado: DOM y SAX usan **Apache Xerces**.

### 6.1 DOM

El API de DOM es un estándar de la W3C. **Ya nadie lo usa; se usa JAXB.** Implementación: **Apache Xerces**.

- El *parser* genera del XML un **árbol de objetos en memoria** que podremos modificar añadiendo nuevos nodos, eliminando o modificando.
- **Libertad absoluta** para recorrer el árbol generado, pero tiene la **desventaja de que puede llegar a ocupar mucha memoria si el XML es grande**.
- Todos los nodos son de tipo/interface `Node`, pero hay especializaciones de `Node`:

| Especialización | Representa | Ejemplo |
|---|---|---|
| `Element` | Etiqueta | `<etiqueta>` |
| `Attr` | Atributo | `<xxx atr="zzz">` |
| `Text` | Texto | `<price>10.9</price>` |
| `Document` | De tipo **instrumental**: representa a todo el documento. **No es un nodo real del árbol** | — |

- Con el API **TrAX** vuelcas el DOM de memoria a un XML. Transforma un origen en un resultado.
- **`DocumentBuilder`** es el parser DOM de Java (en el diagrama del PDF: `DocumentBuilderFactory` → `DocumentBuilder` → `Document (DOM)` a partir de los datos XML).
- Existe otro estándar para "seleccionar" nodos de un XML llamado **XPath** (≈ CSS Selectors): ver sección 8.

### 6.2 SAX

Es del mundo Java. "Modo **braSAX**" (mnemotecnia del PDF). **Más complejo de desarrollar.** Implementación: **Apache Xerces**.

- El *parser* empieza a leer el XML y envía a una clase que se ha definido previamente (la tuya) los distintos **eventos** que detecta (inicio del documento, inicio de etiqueta, etc.).
- Funciona **forward-only**. **No permite ningún tipo de recorrido, pero es el más rápido de los métodos.**
- **`SAXParser`** es el parser SAX de Java.

Diagrama del PDF (`SAXParserFactory` → `SAXParser` → `SAX Reader`, que informa a estos *handlers*):

| Handler | Métodos que se ven en el diagrama |
|---|---|
| Content Handler | `startDocument()`, `startElement()`, `characters()`, `endElement()`, `endDocument()` |
| Error Handler | `warning()`, `error()`, `fatalError()` |
| DTD Handler | `notationDecl()`, `unparsedEntityDecl()` |
| Entity Resolver | (resolución de entidades) |

### 6.3 JAXB (y StAX)

Similar al API de DOM, pero **genera objetos de tus clases de negocio**, no `Element`, `Attr`, etc.

- El *parser* genera del documento XML un árbol de objetos en memoria, pero, al contrario que el DOM, estos objetos serán de **clases de tu modelo de dominio** (ej.: `Factura`, `Empleado`).
- Con la utilidad **`xjc`** de la JDK se pueden generar esas clases **automáticamente a partir de un XSD** (diagrama del PDF: XML Schema → *Binding compiler* → clases/interfaces derivadas del esquema → aplicación con JAXB API).
- Variante **StAX**: en lugar de levantar todo el árbol de objetos, lo controla el programador y va leyendo **bajo demanda, por "trozos"**. Sirve para hacer **streaming**. Haces un árbol de negocio únicamente de lo que te interesa del XML.

| Proceso | Qué es | Equivale a |
|---|---|---|
| **UNMARSHALL** | Leer el XML y levantar el árbol de objetos de negocio en memoria | **Deserializar** |
| **MARSHALL** | Llevar el árbol de objetos de negocio a su XML correspondiente | **Serializar** |

> [!tip] Marshall / Unmarshall
> Marshall ≈ Serializar (objetos → XML). Unmarshall ≈ Deserializar (XML → objetos). En el diagrama del PDF: *Document* ⇄ *Objects*.

> [!important] DOM vs SAX vs JAXB/StAX (resumen comparativo)
> DOM = árbol completo en memoria, libertad de recorrido, mucha memoria. SAX = eventos, forward-only, el más rápido, más complejo. JAXB = árbol de tus clases de negocio (xjc desde XSD). StAX = lectura bajo demanda por trozos, streaming.

## 7. Lenguajes de marcado ligeros, JSON y YAML

### 7.1 Lenguajes de marca ligeros

Basados en una sintaxis **más simple que XML** y suelen usarse para **generar documentación**. Con pocos caracteres consigues un documento atractivo para documentar en web. Ej.: **Markdown** (`.md`) y **reStructuredText** (`.rst`).

### 7.2 JSON

**JavaScript Object Notation**. Estándar **ECMA 404**. Tipo MIME: **`application/json`** (ver [[Tipo MIME]]).

- Lenguaje ***schema-less***, nativo para JavaScript. Por defecto no queremos usar una gramática, no queremos garantizar su validez. **JSON Schema** es una iniciativa que quiere crear una gramática para validar el documento.
- Muy utilizado para intercambio de datos. Basado en **atributo-valor**. (Las bases de datos documentales como [[MongoDB]] trabajan con documentos JSON; y los servicios REST suelen intercambiar XML + JSON: ver [[B4 - T3.3 MICROSERVICIOS]].)
- Tipos de datos: **Object** (`{}` subdocumentos; un conjunto de atributos), **Array**, **Number**, **String**, `true`, `false` y `null`.
- Librerías para procesar JSON: **Jackson** y **GSON** (Google).
- APIs de programación: **JSON-B** (alto nivel) y **JSON-P** (bajo nivel).

| Regla de sintaxis JSON | Detalle |
|---|---|
| Atributos | **Siempre entre comillas** |
| Valor de tipo cadena | Entre comillas |
| Fechas | Entre comillas **porque son cadenas**. **No hay un tipo de dato fecha** |
| Número, `true`, `false`, `null` | **Sin comillas** |
| Separador decimal | `.` (16.9) |
| Separador de elementos | `,` (`[1, 2, 3]`) |
| `NaN` | *Not a Number* |
| Comentarios | **No hay comentarios en JSON** |

Ejemplo del PDF (cada comentario es la anotación del diagrama):

```json
{
  "company": "mycompany",                      // String value
  "companycontacts": {                         // Object inside object
    "phone": "123-123-1234",
    "email": "myemail@domain.com"
  },
  "employees": [                               // JSON array (array de otras cosas)
    {
      "id": 101,
      "name": "John",
      "contacts": [                            // array inside array (array de strings)
        "email1@employee1.com",
        "email2@employee1.com"
      ]
    },
    {
      "id": 102,                               // Number value
      "name": "William",
      "contacts": null                         // Null value
    }
  ]
}
```

(Las anotaciones `//` son del diagrama del PDF; el JSON real no admite comentarios.)

#### JSON Schema (ejemplo del PDF)

Esquema `painting-schema.json` (con las anotaciones del diagrama) y el documento JSON que valida:

```json
{
  "$schema": "https://json-schema.org/draft/2019-09/schema#",
  "$id": "http://my-paintings-api.com/schemas/painting-schema.json",
  "type": "object",
  "title": "Painting",
  "description": "Painting information",
  "additionalProperties": true,          // la validación NO falla si se dan propiedades no definidas
  "required": ["name", "artist", "dimension", "description", "tags"],   // propiedades obligatorias de primer nivel
  "properties": {
    "name":        { "type": "string", "description": "Painting name" },
    "artist":      { "type": "string", "maxLength": 50, "description": "Name of the artist" },   // máx. 50 caracteres
    "description": { "type": ["string", "null"], "description": "Painting description" },        // string o null permitido
    "dimension":   { "$ref": "#/$defs/dimension" },
    "tags":        { "type": "array", "items": { "$ref": "#/$defs/tag" } }
  },
  "$defs": {
    "tag": { "type": "string", "enum": ["oil", "watercolor", "digital", "famous"] },   // solo valores predefinidos
    "dimension": {
      "type": "object",
      "title": "Painting dimension",
      "description": "Describes the dimension of a painting in cm",
      "additionalProperties": true,
      "required": ["width", "height"],
      "properties": {
        "width":  { "type": "number", "description": "Width of the product",  "minimum": 1 },   // solo números positivos
        "height": { "type": "number", "description": "Height of the product", "minimum": 1 }
      }
    }
  }
}
```

```json
{
  "name": "Mona Lisa",
  "artist": "Leonardo da Vinci",
  "description": null,
  "dimension": { "height": 53.0, "width": 77.0 },
  "tags": ["oil", "famous"]
}
```

#### JWT (JSON Web Token)

Uso **muy importante en el ámbito de la seguridad, para autenticación web (JWT)**. El cliente lo envía al *backend* en cada petición usando la cabecera:

```http
Authorization: Bearer eyJhbGci...
```

Un JWT son tres partes separadas por punto (Header . Payload . Signature):

| Parte | Contenido (ejemplo del PDF) |
|---|---|
| 1 · Header | `{ "alg": "HS256", "typ": "JWT" }` |
| 2 · Payload | `{ "sub": "1234567890", "name": "John Doe", "iat": 1516239022 }` |
| 3 · Signature | `HMACSHA256( BASE64URL(header) . BASE64URL(payload), secret )` |

> [!note] Relación con otros temas
> JWT aparece también como mecanismo de autenticación entre microservicios en [[B4 - T3.3 MICROSERVICIOS]]. La cabecera `Authorization` forma parte de HTTP: ver [[B4 - T8 HTTP SSL TLS]].

### 7.3 YAML

- **YAML** es un acrónimo recursivo: ***YAML Ain't Markup Language*** (YAML no es un lenguaje de marcado).
- Formato de **serialización legible por humanos**.

| Uso de YAML | |
|---|---|
| Definición de un **API REST** en formato **Swagger/OpenAPI** | |
| Definir un **playbook de Ansible** (ver [[Playbook (Ansible)]] y [[B4 - T1.4 ADMON SSOO - ANSIBLE]]) | |
| Definir el **entorno de trabajo de un desarrollador** en **Docker Compose** (ver [[B4 - T3.2.2 VIRTUALIZACION - DOCKER]], donde también hay un YAML de pods) | |

```json
          {
            "name": "limit",
            "in": "query",
            "description": "How many items to return",
            "required": false,
            "type": "integer",
            "format": "int32"
          }
        ],
        "responses": {
          "200": { "description": "A paged array of pets" }
        }
      }
    }
  }
}
```

> [!important] YAML vs JSON
> Mismo contenido, distinta sintaxis: YAML se apoya en la **indentación y los guiones**, sin llaves ni comillas obligatorias; JSON usa `{}`, `[]` y comillas.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> JSON puede considerarse en la práctica un subconjunto de YAML 1.2, por lo que un parser YAML suele aceptar documentos JSON. A diferencia de JSON, YAML sí admite comentarios (con `#`).

## 8. XPath (XML Path Language)

Estándar para **seleccionar nodos** de un XML (≈ selectores CSS). Tabla del PDF con la equivalencia CSS 3 → XPath:

| Objetivo (*Goal*) | CSS 3 | XPath |
|---|---|---|
| Todos los elementos | `*` | `//*` |
| Todos los `p` | `p` | `//p` |
| Todos los hijos | `p>*` | `//p/*` |
| Elemento por ID | `#foo` | `//*[@id='foo']` |
| Elemento por clase | `.foo` | `//*[contains(@class,'foo')]` |
| Elemento con atributo | `*[title]` | `//*[@title]` |
| Primer hijo de todos los `p` | `p>*:first-child` | `//p/*[0]` |
| Todos los `p` con un hijo `a` | No es posible | `//p[a]` |
| Elemento siguiente | `p + *` | `//p/following-sibling::*[0]` |
| Elemento anterior | No es posible | `//p/preceding-sibling::*[0]` |

> [!note] Nota sobre la tabla
> Los índices `[0]` están transcritos tal cual aparecen en el PDF. Quédate con la **estructura** de cada expresión y con la idea de que XPath cubre casos que CSS no puede (p. ej. "todos los `p` con un hijo `a`" y "elemento anterior").

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En el estándar XPath 1.0 los índices de posición empiezan en 1 (`[1]` es el primero), por lo que en un examen conviene saber que el `[0]` del PDF es notación de la fuente.

## 9. Ejercicio resuelto: catálogo XML bien formado

El fichero `B3-T7.3.2-XML-BIEN FORMADO.pdf` es una **imagen** con un catálogo XML de 18 líneas con **errores de "bien formado"** (primera página) y la **solución** con las correcciones marcadas en rojo (segunda página).

### 9.1 Código con errores (enunciado)

```xml
 1  <?xml version="1.0" encoding="UTF-8"
 2  <catalogo>
 3    <producto>
 4      <nombre>Camisa de manga corta</nombre>
 5      <precio moneda="euros">19.99<precio>
 6      <disponible>true</disponible>
 7    <producto>
 8    <producto>
 9      <nombre>Pantalón vaquero</nombre>
10      <precio moneda="euros" moneda="dolar">29.99</precio>
11      <disponible>false</disponible>
12    </producto>
13    <producto>
14      <nombre moneda="euros">Zapatos de cuero</nombre>
15      <precio>79.99</precio>
16      <disponible>true</disponible>
17    </producto>
18  </catalogo>
```

### 9.2 Errores y corrección (según la segunda página del PDF)

| Línea | Error | Corrección (según la solución del PDF) |
|---|---|---|
| 1 | La declaración no se cierra: falta `?>` tras `"UTF-8"` | `<?xml version="1.0" encoding="UTF-8"?>` |
| 5 | La etiqueta de cierre de `precio` es `<precio>` (de apertura) | `</precio>` |
| 7 | El cierre de `producto` es `<producto>` (de apertura) | `</producto>` |
| 10 | **Atributo duplicado** (`moneda` dos veces) en el mismo elemento | Se deja un único `moneda`: la solución conserva `moneda="dolar"` |
| 14 | El atributo `moneda` está en `<nombre>` en lugar de en `<precio>` | La solución quita el atributo de `nombre` y lo coloca en la línea 15: `<precio moneda="euros">79.99</precio>` |

> [!note] Cómo se deduce
> La solución es la segunda imagen del propio PDF; los cinco cuadros rojos marcan la declaración (`?>`), `</precio>`, `</producto>`, `moneda="dolar"` y la línea del atributo movido. La elección de conservar `"dolar"` en la línea 10 y mover `moneda="euros"` a `precio` en la 15 es la que muestra la solución del PDF; lo que el ejercicio pone a prueba es que el atributo no se repita en el mismo elemento.

### 9.3 Código corregido

```xml
 1  <?xml version="1.0" encoding="UTF-8"?>
 2  <catalogo>
 3    <producto>
 4      <nombre>Camisa de manga corta</nombre>
 5      <precio moneda="euros">19.99</precio>
 6      <disponible>true</disponible>
 7    </producto>
 8    <producto>
 9      <nombre>Pantalón vaquero</nombre>
10      <precio moneda="dolar">29.99</precio>
11      <disponible>false</disponible>
12    </producto>
13    <producto>
14      <nombre>Zapatos de cuero</nombre>
15      <precio moneda="euros">79.99</precio>
16      <disponible>true</disponible>
17    </producto>
18  </catalogo>
```

> [!important] Qué reglas de "bien formado" se rompen
> Declaración mal cerrada · etiquetas no cerradas correctamente / mal anidadas · atributo repetido en el mismo elemento. Lección: *bien formado* es solo sintaxis, sin necesidad de DTD ni XSD.

## 🔑 Resumen ultra-rápido (para repaso)

- XML: estándar W3C derivado de SGML; etiquetas siempre cerradas (incluso vacías), atributos entre comillas, *case-sensitive*. HTML4 = SGML; HTML5 no; XHTML = reglas XML (`application/xhtml+xml`).
- Declaración `<?xml ...?>` opcional: `version` obligatoria; `encoding` y `standalone` no. `standalone="no"` (por defecto) = DTD externo; `"yes"` = gramática en el propio XML.
- `<!DOCTYPE ... SYSTEM/PUBLIC ...>` enlaza el DTD. `&amp;`/`&lt;` = entidades. `<![CDATA[ ]]>` = texto literal. `<role />` = empty element (sin hijos, sí atributos).
- Espacios de nombres: prefijos `xmlns:h=...` para evitar colisiones; los DTD **no** los soportan.
- Bien formado (sintaxis): raíz única, anidado y cerrado, atributos entre comillas, vacíos autocerrados, nombres que empiezan por letra, `_` o `:`. Válido = bien formado + cumple DTD/XSD.
- DTD: el primero, menos flexible, **sin tipos de datos**. `*` 0..N, `+` 1..N, `?` 0..1, `#PCDATA`, `ANY`, `EMPTY`, `ID`/`IDREF`, `#REQUIRED`/`#IMPLIED`/`#FIXED`.
- XSD: facetas (`length`, `minLength`, `maxLength`, `pattern`, `enumeration`, `whiteSpace`, `min/maxInclusive`, `min/maxExclusive`, `totalDigits`, `fractionDigits`); `sequence` (orden), `all` (sin orden), `choice`; `minOccurs` por defecto 1; `extension` = herencia; tipos propios.
- Enlazar XSD: dar de alta `xmlns:xsi` y asociar con `xsi:noNamespaceSchemaLocation`.
- XSL (obsoleto): XSLT + processor (Apache Xalan) → otro documento de marcas; XSLFO + Apache FOP → PDF/imagen.
- DOM (W3C; Apache Xerces; `DocumentBuilder`): árbol en memoria, mucha memoria; nodos `Node` → `Element`, `Attr`, `Text`, `Document` (instrumental). TrAX vuelca DOM a XML.
- SAX (Apache Xerces; `SAXParser`): eventos, forward-only, el más rápido, más complejo.
- JAXB: árbol de tus clases de negocio, `xjc` desde XSD; StAX = bajo demanda/streaming. Marshall = serializar; Unmarshall = deserializar.
- Marcado ligero: Markdown (`.md`), reStructuredText (`.rst`).
- JSON: ECMA 404, `application/json`, schema-less, tipos (Object, Array, Number, String, true, false, null), sin fechas ni comentarios, atributos siempre entre comillas, `.` decimal. Jackson y GSON; JSON-B (alto nivel) y JSON-P (bajo nivel). JSON Schema = gramática.
- JWT: header.payload.signature; cabecera `Authorization: Bearer ...`.
- YAML = *YAML Ain't Markup Language*: serialización legible; Swagger/OpenAPI, playbooks de Ansible, Docker Compose.
- XPath = selección de nodos (≈ CSS Selectors): `//p`, `//*[@id='foo']`, `//p[a]`, `following-sibling`, `preceding-sibling`.
- Ejercicio catálogo: declaración sin `?>`, cierres mal escritos (`<precio>`, `<producto>`), atributo duplicado, atributo en el elemento equivocado.

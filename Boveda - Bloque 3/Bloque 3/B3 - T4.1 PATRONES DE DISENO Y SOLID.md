# Tema 4.1 · Bloque 3 — Patrones de diseño y Principios SOLID

> [!abstract] De qué va este tema
> Los patrones son modelos tipo, ejemplos o buenas prácticas reutilizables que comparten elementos comunes de análisis, y se clasifican en patrones de análisis, de arquitectura (grandes líneas organizativas del sistema) y de diseño (catálogo GoF, aplicados con las técnicas GRASP). El tema cierra con los principios SOLID —las reglas que persiguen los patrones de diseño para lograr bajo acoplamiento y alta cohesión— y con los antipatrones, los errores de diseño opuestos.

---

## Parte I — Patrones: concepto y categorías

### 1. Qué es un patrón

**Patrón**: modelo tipo, ejemplo o buena práctica de cualquier aplicación de gestión que comparte elementos comunes de análisis. Son técnicas de alto nivel, muy semánticas.

> [!example]
> Patrón de análisis — atributo `peso` (entero) = 60 → se convierte en clase `Cantidad`: `amount = 60; unidad = Kg`.

### 2. Categorías de patrones

| Categoría | Descripción |
|---|---|
| De análisis | Ej. el patrón "Cantidad" de arriba (separar valor y unidad) |
| De arquitectura | Layer, Broker, MVC, Blackboard, Pipeline, etc. |
| De diseño | Catálogo GoF (ver Parte III) |

### 3. Contexto: diseño orientado a objetos en Métrica 3

No se trata de definir las clases y ponerse a programar directamente. En esta fase hay que "ajustar" algunos elementos del diagrama de clases de análisis, así como añadir nuevas clases y subsistemas (control, persistencia, etc.). La seguridad, la persistencia, la visualización, el almacenamiento, etc. no están definidos en el diagrama de clases inicial, y todo esto no debe ir en las clases originales, ya que el sistema debe ser fácil de mantener. Por este motivo aparecen nuevos subsistemas: de este modo cada clase tiene una sola responsabilidad, una tarea.

> Métrica v3 es la metodología de desarrollo de software de referencia de las Administraciones Públicas españolas (impulsada por el actual Ministerio para la Transformación Digital). DSI = Diseño del Sistema de Información, una de sus actividades principales, situada después del ASI (Análisis del Sistema de Información).

#### Tecnología J2EE

- **[[Patrones J2EE (DAO, Intercepting Filter, Composite View)|Intercepting filter]]**: en lugar de meter la seguridad en cada servlet, se mete en un filter. De este modo el servlet hace su labor y el filter se pone delante de los servlets.
- **[[Patrones J2EE (DAO, Intercepting Filter, Composite View)|Composite View]]**: para pantallas muy complejas, se hacen pantallas a base de otras más pequeñas, subviews.
- **[[Patrones J2EE (DAO, Intercepting Filter, Composite View)|Data Access Object (DAO)]]**: agrupa el código JPA o SQL, para no tenerlo desperdigado en las clases de negocio. DAO, Data Mapper, Active Record…

## Parte II — Patrones de arquitectura

**Patrones de arquitectura**: grandes líneas organizativas del proyecto.

- [[Layer Pattern|Layered pattern]]
- Client-server pattern
- Master-slave pattern
- [[Pipe-filter Pattern|Pipe-filter pattern]]
- [[Broker Pattern|Broker pattern]]
- Peer-to-peer pattern
- [[Event-Bus Pattern|Event-bus pattern]]
- [[MVC (Model-View-Controller)|Model-view-controller pattern]]
- [[Blackboard Pattern|Blackboard pattern]]
- Interpreter pattern

### Layer Pattern

Capas al estilo del modelo OSI: una capa N solo se comunica con la capa N+1 y la N-1.

### Pipe-filter Pattern

Filtrado de información unidireccional: `Source → Pipe 1 → Filter 1 → Pipe 2 → Filter 2 → Pipe 3 → Sink`.

### Event-Bus Pattern

Se comunican productores y consumidores de forma asíncrona (Source 1/2 → Channel 1/2 → Bus → Listener 1/2). El **[[ESB (Enterprise Service Bus)|ESB]]** (Enterprise Service Bus) es una mezcla de la cola de mensajes (bus) con el filtrado. **[[SOA (arquitectura orientada a servicios)|SOA]]**: arquitectura orientada a servicios.

### Model-View-Controller Pattern

MVC es un patrón de **arquitectura y también de diseño**. Flujo: `input events → View → view control → Controller → update model → Model → change notification → View → query model`.

> [!important]
> MVC aparece como el único patrón de la lista que la fuente clasifica explícitamente en **ambas** categorías (arquitectura y diseño) a la vez.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En el Broker pattern un componente intermediario (el broker) coordina la comunicación entre clientes y servidores desacoplados, ocultando la localización de estos últimos — es la base conceptual de tecnologías como CORBA o los buses de mensajería. El Blackboard pattern organiza la resolución de un problema mediante varios "agentes" especializados que leen y escriben en una estructura de datos compartida (la "pizarra"), útil en problemas sin una solución algorítmica determinista (ej. reconocimiento de voz).

## Parte III — Patrones de diseño (GoF)

Las técnicas de diseño, en un 99%, están para poder hacer un mejor mantenimiento.

**GoF**: Gang of Four. Patrones para resolver problemas o crear objetos. La función de los patrones de diseño es **tipificar un problema junto con su solución**.

| Tipo | Descripción |
|---|---|
| Creacionales | Crear objetos no es sencillo, ya que puede haber mucha jerarquía o tener muchas partes (ej. factura) |
| Estructurales | Solucionan algunos problemas de ciertos tipos de estructuras concretas. Cada estructura debe verse de manera individual |
| Comportamiento | Afrontan casuísticas muy variadas |

### [[GRASP (técnicas de asignación de responsabilidades)|Técnicas GRASP]]

- **Information expert**: asignar responsabilidad a la clase que tiene la información necesaria para realizar esa tarea.
- **Creator**.
- **Controller**: gestiona eventos (no de interfaz de usuario).
- **Indirection**.
- **Low coupling** y **High cohesion**: para evitar código espagueti (flujo complejo e incomprensible).
- **Polymorphism**.
- **Protected variations**.
- **Pure fabrication**.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> GRASP (General Responsibility Assignment Software Patterns) son patrones básicos de asignación de responsabilidades, más elementales que los patrones GoF. Los que el PDF no desarrolla: **Creator** (indica qué clase debe crear instancias de otra, típicamente la que las agrega/contiene/usa de cerca), **Indirection** (asigna la responsabilidad a un objeto intermedio para desacoplar dos elementos — base conceptual de patrones como Facade o Adapter), **Polymorphism** (asignar responsabilidad usando operaciones polimórficas cuando el comportamiento varía según el tipo), **Protected variations** (identificar puntos de variación previsible y poner una interfaz estable alrededor, para blindar el resto del sistema de esos cambios) y **Pure fabrication** (crear una clase que no representa un concepto del dominio, solo para lograr bajo acoplamiento/alta cohesión, ej. una clase de persistencia).

### [[Composición sobre herencia|Composición vs. herencia]]: base de varios patrones GoF

> [!example] Mal uso de la herencia en diseño
> ```java
> clase Lista {
>   object[] datos;             // atributo interno donde guardar los datos
>   objeto get(int indice) { ... }
>   void add(objeto) { ... }
> }
>
> class Pila {
>   Lista lista;                // atributo interno (reutilización por composición)
>   void push(objeto) { lista.add(...) }
>   objeto pop() { lista.get(...) }
> }
> ```
> [[Pila (Stack)|Pila]] **no hereda** de [[Lista enlazada (TAD)|Lista]] (heredar implicaría que una Pila "es una" Lista, lo cual no es cierto conceptualmente); en su lugar **reutiliza por composición**, guardando una `Lista` como atributo interno.

A partir de este tipo de ejemplos se deducen varios patrones del catálogo GoF: **Memento** (nuestro Ctrl+Z / Undo), **Observer** (mecanismo publicador/suscriptor) e **Iterator** (el cliente puede iterar sin saber la colección concreta de la que se trata) — los tres se desarrollan más abajo.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Este ejemplo ilustra el principio de diseño "prefiere la composición sobre la herencia": la herencia crea un acoplamiento muy fuerte (la clase hija depende de los detalles internos de la clase padre y se rompe si esta cambia), mientras que la composición permite intercambiar la implementación interna sin afectar al resto. Es la misma idea que subyace al patrón Strategy y al principio Liskov (ver Parte V): si dos clases no cumplen una relación "es un/a" verdadera, no deben estar unidas por herencia. Es también la misma distinción que separa un TAD de su [[TAD vs EEDD|EEDD]] (interfaz vs. implementación): `Pila` depende del "qué" que promete `Lista`, no de si por dentro hay un array o nodos enlazados.

### Patrones creacionales

**SINGLETON**. El problema que resuelve es que de una clase solo se genera un objeto para que luego sea compartido por todos (objeto global). Solución: constructor privado y método estático. Ej.: configuración, servlets, objeto DataSource, etc.

```java
public class Configuracion {
  private static Configuracion instancia;

  private Configuracion() { ... } // si el constructor es privado, no puedo hacer ningún new

  public static Configuracion getInstancia() { // no necesita un objeto para poder usarse
    if (instancia == null)
      instancia = new Configuracion(); // la primera vez que se llama se crea; el resto de veces se devuelve el mismo objeto
    return instancia;
  }
}

// Uso: Configuracion conf = Configuracion.getInstancia();
// Devuelve el mismo objeto cada vez que se hace Configuracion.getInstancia()
```

**FACTORY METHOD**. Crea objetos cuando hay varios tipos de un mismo concepto. Usa polimorfismo. La complejidad está en la jerarquía, en las herencias, en que hay muchos tipos de objetos. La fábrica fabrica lo abstracto, pero se usa lo concreto.

```java
// CreadorAbstracto define crearPolizaVida(): PolizaVida
// Creador98 y Creador2015 son implementaciones concretas del creador

public PolizaVida crearPolizaVida() {
  return new PolizaVida2015(); // Polimorfismo: creo lo concreto pero devuelvo lo abstracto
}
```

> [!important]
> Factory Method está directamente ligado a SOLID (ver Parte V): el cliente que llama a `crearPolizaVida()` depende de la abstracción `PolizaVida`, nunca de la implementación concreta que se instancia por debajo.

**BUILDER**. Busca solución al problema de crear un objeto muy complejo, compuesto por muchas partes (ej. un objeto de negocio compuesto por 15 partes; ej. DOM → `DocumentBuilder`, que va creando cada nodo). Un `Director` construye el objeto apoyándose en varios "builders" concretos (`CabeceraBuilder`, `CuerpoBuilder`, `ColaBuilder`…), cada uno responsable de construir su parte, y el director ensambla las partes finales.

**ABSTRACT FACTORY**. Interfaz para crear familias de objetos dependientes sin especificar clases concretas. Se define una serie de productos, cada producto tiene una interfaz abstracta que será usada por el cliente. A su vez se define una factoría abstracta y sus implementaciones: cada implementación de la factoría es la encargada de instanciar los productos de su familia.

> [!important] Factory Method vs. Abstract Factory
> Factory Method crea **un** tipo de objeto (con distintas variantes según la jerarquía). Abstract Factory crea **familias completas** de objetos relacionados entre sí, a través de una factoría que agrupa varios métodos de creación.

### Patrones estructurales

**PROXY**. Patrón complicado. Se utiliza para interceptar/separar responsabilidades (SOLID). El Proxy controla el acceso al objeto original; hay un Proxy para un tipo de dato y solo para uno. El Proxy siempre va por delante de la clase real: es una capa para aislar. Para el cliente es transparente (polimorfismo): la interfaz (`Factura`) es la que permite el polimorfismo, no lleva la codificación pero sí el esqueleto; internamente llama al `ProxyFactura` (que hace el "trabajo sucio", ej. `if (user is auth) { factura.abonar(...) }`) y este finalmente llama a `FacturaImpl`, la factura real.

> [!note]
> Filter es más genérico; Proxy es más específico para una clase concreta.

**COMPOSITE**. Resuelve estructuras de objetos poco flexibles. Permite un diseño de clases más flexible: si el día de mañana se crea un nuevo contenedor, se puede introducir minimizando el impacto. Un **elemento** puede ser **simple** o **compuesto**; si es compuesto, puede contener elementos simples o compuestos (relación recursiva). Un elemento compuesto tiene relación de agregación con N elementos (ej. `Sección` ◇ `División` ◇ `Estante` ◇ `Balda` ◇ `Producto`). Esto permite todas las combinatorias, es escalable, y el modelo de clases ofrece infinitos eslabones.

**FLYWEIGHT**. Sirve para eliminar redundancia. Disminuye el uso de recursos y protege ante cambios al tener las funcionalidades centralizadas en clases que no se replican, sino que se comparten, centralizando la información. No está orientado a facilitar el mantenimiento, sino a **optimizar los recursos del sistema**.

**FACADE**. La fachada proporciona un servicio intermedio de alto nivel (agregación). El patrón Proxy era para una sola clase; Facade puede tapar a varias. Sirve para desacoplar subsistemas entre sí: es una clase con métodos de alto nivel, y su objetivo es minimizar el acoplamiento entre las clases de un subsistema (clientes) que necesitan servicios de clases que se encuentran en otro subsistema. La clase Facade no solo "centraliza" las peticiones de los clientes, también les ofrece funciones/interfaz de más alto nivel. Si el proceso de negocio cambia, se cambia la implementación de la fachada.

> [!example]
> Supongamos que `Cliente1` usa `A.g() + B.h() + D.m()`. La fachada ofrece a `Cliente1` un único servicio (`servicioX(...)`) que internamente llama a los tres métodos, evitando que `Cliente1` tenga que llamarlos por separado.
> ```java
> class FacadeSubsistema2 {
>   public void servicioX(...) { /* -- f() --> ClaseA -- g() --> ClaseB -- h() --> ClaseC */ }
>   public void servicioY(...) { /* -- r() --> ClaseC -- e() --> ClaseD */ }
>   public void servicioZ(...) { /* -- m() --> ClaseD -- n() --> ClaseE */ }
> }
> // Uso:
> FacadeSubsistema2 fachada = FacadeSubsistema2.getInstancia();
> fachada.servicioX(...);
> ```

Para la creación de un objeto de la clase Facade se utiliza primero un **Singleton** y posteriormente un **Factory Method**, porque se trabaja con la idea de que la fachada tenga versiones diferentes en su implementación para los distintos clientes que la vayan usando. Es un Singleton porque esa clase solo se crea una vez para esa pieza.

**ADAPTER** (Wrapper). Intermediario que ofrece al cliente una interfaz más fácil de utilizar que la ya desarrollada. La clase cliente necesita utilizar el servicio `methodX()` pero es muy simple para sus objetivos, o incluso no sabe usarlo directamente; la clase `Adapter` le proporciona un servicio que sí sabe utilizar `Cliente`, y es la encargada de llamar o "adaptar" a `Adaptee`. Puede implementarse **por herencia** (Adapter hereda de Target y también de Adaptee) o **por asociación** (Adapter implementa Target y guarda una referencia a Adaptee).

> [!important] Proxy vs. Facade vs. Adapter
> - **Proxy**: misma interfaz que el objeto real, controla el acceso a **un único** objeto.
> - **Facade**: interfaz nueva de alto nivel que simplifica el acceso a **varias** clases/subsistemas.
> - **Adapter**: interfaz nueva para hacer compatible una interfaz **ya existente** con la que espera el cliente (traduce, no simplifica).

### Patrones de comportamiento

**CHAIN OF RESPONSIBILITY**. Cada eslabón tiene una tarea específica y le pasa el control al siguiente. Ej.: Filter de J2EE.

**COMMAND**. Se transforman los métodos en clases, así, cuando haya una modificación o extensión de comportamiento (ej. `ToPDF()` sobre un `WordDocument`), solo se añade una clase más, sin tocar las existentes.

**STRATEGY**. Similar a Command, pero orientado a un algoritmo concreto: separa/realiza implementaciones diferentes de un mismo método (ej. distintos algoritmos de ordenación — Burbuja, Merge, QuickSort — todos implementando la misma interfaz `AlgOrdenacion`). Similar al VFS con sus métodos `open`, `read`, `close`, etc.

**ITERATOR**. Iterar sobre colecciones de objetos sin conocer el tipo de colección del que se trata. `Iterator` aísla al cliente de la colección que hay por debajo: el cliente solo llama a `next()`. Para conseguirlo hace falta disponer de clases especializadas en recorrer cada tipo de colección, ofreciendo todas ellas un mismo interfaz para realizar el recorrido (ej. `IteratorTree`, `IteratorLista`).

> [!example] Por qué hace falta Iterator
> Sin él, el cliente tendría que conocer la API específica de cada colección para recorrerla:
> ```java
> // opcion a) Lista l;   l.get(...), l.add(...)
> // opcion b) Arbol a;   a.find(...), a.insert(...)
> // opcion c) Hash h;    h.put(...), h.get(...)
> ```
> Si todas las colecciones concretas ([[Lista enlazada (TAD)|Lista]], [[Árbol (conceptos básicos)|Árbol]], [[Tabla Hash|Hash]], [[Grafo (conceptos básicos)|Grafo]]) implementan el interfaz `Iterador`, el cliente puede recorrer cualquiera de ellas con el mismo código, por polimorfismo:
> ```java
> interface Iterador {
>   objeto next();
>   boolean hasNext();
> }
>
> Iterador i; // POLIMORFISMO
> while (i.hasNext()) {
>   objeto o = i.next();
> }
> ```

**STATE**. Los estados se convierten en clases. Punto de partida: una clase `Factura` con ciclo de vida (algo muy importante) suele tener un método (ej. `abonar(cantidad)`) con un "super if" (si me abonan el total, la pongo como pagada, la contabilizo, etc. — si está bloqueada, aviso a jurídico...) que es difícil de mantener. La solución saca la lógica de negocio asociada a cada estado a una clase propia:

```java
class Factura {
  Estado estado;
  Factura() {
    estado = new Emitida(); // estado inicial
  }
  void abonar() {
    if (cantidad == total) estado = new PAGADA();
    // if ...
    estado.execute(); // se elimina el super if, se delega en el estado
  }
}

interface Estado {
  void execute(); // también llamado do() en el ejemplo de ciclo de vida
}

class BLOQUEADA implements Estado {
  void execute() { /* mensaje a gabinete jurídico ... */ }
}
class PAGADA implements Estado {
  void execute() { /* ... */ }
}
class ANULADA implements Estado {
  void execute() { /* ... */ }
}
```

**MEMENTO**. Crea clases específicas para guardar la información necesaria para poder deshacer las acciones ejecutadas. UNDO. Ctrl+Z.

**OBSERVER**. Conjunto de clases que da la infraestructura necesaria para montar un sistema de notificaciones cuando una parte del sistema cambia (eventos). Es como una suscripción para consumidores y productores (≈ Topic). Cuando una parte del sistema depende de otra, se monta en medio una infraestructura que permita que unos se suscriban a los cambios de otros (Sujeto observado → notifica evento → Clientes suscritos/Observers).

**TEMPLATE METHOD**. Define un flujo de ejecución (no totalmente, parcialmente) de un cierto proceso. Un framework es un trozo de código que da resueltas ciertas cosas: a nivel Framework se definen `m()` (final, ya resuelto) y `g()`/`h()` (abstractos, sin implementar todavía, pero con el esqueleto/flujo ya definido — el "método plantilla"). A nivel Aplicación, cada negocio (`NegocioXA`, `NegocioXB`) implementa `g()` y `h()` a su manera.

> [!note]
> Las clases se van multiplicando con este enfoque, por eso es importante no sobrediseñar (*over design*) — comparable a que normalizar una base de datos implica tener más tablas.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Diferencia clave Strategy vs. State vs. Template Method (los tres "encapsulan comportamiento variable", y se confunden en examen): **Strategy** intercambia un algoritmo completo desde fuera (el cliente elige la estrategia). **State** cambia el comportamiento de un objeto según su estado interno, y es el propio objeto el que transiciona de un estado a otro. **Template Method** fija el esqueleto del algoritmo en la clase base y delega solo pasos concretos a las subclases (no se puede alterar el orden de los pasos, a diferencia de Strategy).

## Parte IV — [[Antipatrones de diseño (Anemic Domain Model, Blob, código espagueti)|Antipatrones]]

| Antipatrón | Descripción |
|---|---|
| Anemic Domain Model | Clases de dominio sin ningún comportamiento (solo datos) |
| Blob | Objeto todopoderoso |
| Código espagueti | Poca estructuración |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Los tres antipatrones son la contrapartida directa de los principios GRASP/SOLID vistos en el tema: el **Anemic Domain Model** viola *Information expert* (la lógica que debería vivir en la clase que tiene los datos se traslada a clases de servicio externas); el **Blob** (también llamado "God Object") viola *Single Responsibility* y *High cohesion*; y el **código espagueti** es justo lo que *Low coupling*/*High cohesion* y patrones como Chain of Responsibility o State buscan evitar.

## Parte V — Principios [[SOLID (principios)|SOLID]]

| Principio | Enunciado (fuente) | Explicación |
|---|---|---|
| **S** — Single Responsibility Principle | *A class should have one, and only one, reason to change* | Una clase solo debe tener una responsabilidad. No puede haber una "super clase"; debe tener una única razón para cambiar |
| **O** — Open/Closed Principle | *You should be able to extend a class's behavior, without modifying it* | Si se quiere modificar una clase, se hereda y se hacen los cambios en la subclase, pero no se toca la clase original (a menos que estuviera mal diseñada) |
| **L** — Liskov Substitution Principle | *Derived classes must be substitutable for their base classes* | Las clases hijas deben ser sustituibles por sus clases base. Al subsistema le da igual la implementación concreta; implica tener una jerarquía muy robusta y un comportamiento por defecto (el de la clase base). Se basa en el polimorfismo |
| **I** — Interface Segregation Principle | *Make fine grained interfaces that are client specific* | Los clientes no deben depender de interfaces que no utilizan |
| **D** — Dependency Inversion Principle | *Depend on abstractions, not on concretions* | Las interfaces son las abstracciones y las clases son las concreciones/implementaciones. Relacionado con la inyección de dependencias (CDI) |

### [[Interface Segregation Principle (ISP)|Interface Segregation Principle]] — en detalle

**Ideas generales previas**: buscar bajo acoplamiento entre clases de distintos subsistemas/componentes. Habrá subsistemas "cliente" y subsistemas "proveedores".

**Antes** (interfaz monolítica): para `Clase1`, el método `logica2()` es basura; para `Clase2`, el método `logica1()` es basura, porque no lo necesita.

```java
class ServicioXXX {
  public logica1() { ... }
  public logica2() { ... }
}
// Clase1 --logica1()--> ServicioXXX <--logica2()-- Clase2
```

**Después** (segregado, como hacer "vistas" de la clase — la implementación de `ServicioXXX` es la misma):

```java
interface Servicio1 { public logica1(); }
interface Servicio2 { public logica2(); }

class ServicioXXX implements Servicio1, Servicio2 {
  public logica1() { ... }
  public logica2() { ... }
}
// Clase1 usa Servicio1 s;   Clase2 usa Servicio2 s;
```

> [!example] Ejemplo de código equivalente (mapa de dependencias cliente/proveedor)
> ```java
> // subsistema de facturación
> class cliente1 {
>   FuncionesA x; // uso por composición/asociación
>   // metodo de negocio: x.f();  x.g(); --> NO SE PUEDE (no está en FuncionesA)
> }
> // subsistema de control de stock
> class cliente2 {
>   FuncionesB x;
>   // metodo de negocio: x.g();
> }
>
> class Servicio1 implements FuncionesA, FuncionesB {
>   void f() { ... }
>   void g() { ... }
>   void h(); // propia de la implementación, no forma parte de ningún interface
> }
> // en un futuro no muy lejano...
> class Servicio2 implements FuncionesA, FuncionesB {
>   void f() { ... }
>   void g() { ... }
> }
>
> interface FuncionesA { void f(); }
> interface FuncionesB { void g(); }
> ```
> `Servicio1` puede tener métodos propios (`h()`) que no pertenecen a ningún interface expuesto a los clientes, y en el futuro puede aparecer una implementación alternativa (`Servicio2`) de las mismas interfaces sin que `cliente1`/`cliente2` se enteren.

### [[Liskov Substitution Principle (LSP)|Liskov Substitution Principle]] — en detalle

Jerarquía: `Clase A` (con `f()`, `g()`), `Clase B extends A`, `Clase C extends A` (ambas redefiniendo `f()` y `g()` sin añadir métodos nuevos). Un subsistema que usa objetos de esta jerarquía (`new A`, `new B` o `new C`) debería poder usar indistintamente cualquiera de las tres, según el principio de Liskov: "compilaría" y funcionaría, aunque el resultado concreto obtenido pudiera no ser el esperado en cada caso.

### [[Dependency Inversion Principle (DIP)|Dependency Inversion Principle]] — en detalle

¿De quién depende `Clase1`, del interface o de la implementación? Del interface (`Servicio1`), que es más abstracto que la implementación (`ServicioXXX`).

```java
// Clase1 --logica1()--> ServicioXXX <--logica2()-- Clase2
@Autowired // por debajo hay una inyección "mágica": hace un new de ServicioXXX
           // y lo asocia a la variable s, sin que se entere Clase1
Servicio1 s;
```

Las interfaces no suelen cambiar, pero las implementaciones sí; por eso es mejor depender de una interfaz que de algo que cambia. **Spring** es un framework de inyección de dependencias.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> `@Autowired` es la anotación de Spring Framework que implementa la inyección de dependencias: en tiempo de arranque, el contenedor de Spring resuelve qué implementación concreta (`ServicioXXX`) debe inyectar en la variable declarada con el tipo abstracto (`Servicio1`), sin que la clase que la usa tenga que hacer `new` explícitamente. Esto es una aplicación directa del principio D de SOLID: el código cliente solo conoce la interfaz.

## 🔑 Resumen ultra-rápido (para repaso)

- Patrón = modelo tipo reutilizable. Categorías: análisis, arquitectura, diseño.
- Métrica v3, fase DSI: ajustar el diagrama de clases de análisis, añadir subsistemas (control, persistencia...) para que cada clase tenga una sola responsabilidad. DSI 4.1 a 4.7.
- J2EE: Intercepting filter (seguridad fuera del servlet), Composite View (subviews), DAO (agrupa acceso a datos).
- Patrones de arquitectura: Layer (capas tipo OSI, N solo habla con N+1/N-1), Pipe-filter (filtrado unidireccional), Event-Bus (asíncrono, ESB = bus + filtrado, base de SOA), MVC (arquitectura y diseño a la vez).
- GoF: 23 patrones — Creacionales (5), Estructurales (7), Comportamiento (11).
- GRASP: Information expert, Creator, Controller, Indirection, Low coupling, High cohesion, Polymorphism, Protected variations, Pure fabrication.
- Composición > herencia cuando no hay relación "es un/a" real (ej. Pila reutiliza Lista por composición, no por herencia).
- Creacionales: Singleton (constructor privado + método estático, un solo objeto global), Factory Method (fabrica lo abstracto, entrega lo concreto), Builder (director + builders concretos para objetos complejos), Abstract Factory (fábrica de familias de productos).
- Estructurales: Proxy (controla acceso a un objeto, 1 a 1), Composite (elementos simples/compuestos, relación recursiva), Flyweight (comparte para optimizar recursos), Facade (interfaz de alto nivel para varios subsistemas, Singleton+Factory Method), Adapter (traduce una interfaz ya existente, por herencia o asociación).
- Comportamiento: Chain of Responsibility (eslabones, ej. Filter J2EE), Command (métodos → clases), Strategy (algoritmos intercambiables), Iterator (recorrer sin conocer la colección concreta), State (estados → clases, elimina el "super if"), Memento (undo/Ctrl+Z), Observer (pub/sub), Template Method (esqueleto fijo, pasos variables en subclases).
- Antipatrones: Anemic Domain Model (clases sin comportamiento), Blob (objeto todopoderoso), código espagueti.
- SOLID: S (una responsabilidad) · O (extender sin modificar) · L (subclases sustituibles por la base) · I (interfaces específicas por cliente) · D (depender de abstracciones, no de implementaciones — @Autowired/Spring).
- No sobrediseñar (*over design*): más clases = más mantenimiento, igual que normalizar en BD implica más tablas.

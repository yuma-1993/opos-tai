# Tema 4.3 · Bloque 2 — Linux

> [!abstract] De qué va este tema
> Linux como sistema operativo de arquitectura **monolítica**: cómo se organiza en capas (user space / kernel space), cómo se instalan y gestionan paquetes (Debian vs RedHat), cómo funciona su **sistema de ficheros** (tipos, VFS, i-nodos, permisos, ACLs, enlaces), el catálogo completo de **comandos** de administración (ficheros, texto, almacenamiento, procesos, planificación), el **proceso de arranque** (BIOS/UEFI, init/systemd), la configuración de **red** e **iptables** como cortafuegos, el **shell** y el entorno gráfico, el sistema de **impresión** (CUPS) y la **seguridad** (usuarios, permisos avanzados, recursos, SELinux).

## 1. Arquitectura de Linux y familia UNIX

**Arquitectura**: Linux es principalmente **monolítica** (todos los servicios del núcleo viven en el kernel), aunque es modular (admite carga de módulos en caliente).

Capas del sistema, de arriba a abajo:

| Capa | Contenido |
|---|---|
| **User Space** | Aplicaciones de usuario → System Libraries (Lib C) |
| **System Call Interface (SCI)** | Frontera entre user space y kernel space. Ofrece las funcionalidades del SO; esta capa es **POSIX** |
| **Kernel Space** | E/S · Gestión de Memoria (memoria virtual, paginación) · Gestión de Procesos (señales, procesos, threads, scheduler) · Virtual File System (Terminales, FS: ext2, FAT, etc., Sockets) · Modules (LKM) · Drivers |
| **HW (CPU)** | El hardware |

**`int 80h`** es la rutina que hace el cambio a modo kernel (Sistema de Interrupciones): es la puerta de entrada desde user space hacia las llamadas al sistema del kernel.

### Familia UNIX

| Familia | Sistemas |
|---|---|
| Comerciales UNIX | Solaris (Sun Microsystems), SCO (Santa Cruz), HP-UX, IBM-AIX |
| BSD | FreeBSD, Mac OS X (`.dmg`) |
| Linux (por paquetería/distribución) | **Debian** (`.deb`) → Ubuntu → Mint · **RedHat** (`.rpm`) → Fedora, CentOS (ahora Rocky Linux), Mandriva → Mageia · **Suse** · **Slackware** (`.tgz`) · **Gentoo** (ebuilds) · **Puppy Linux** (PET) · **Arch Linux** (Pacman) |

### Versiones de Debian

| Versión | Nombre en clave |
|---|---|
| Debian 13 | Trixie |
| Debian 12 | Bookworm |
| Debian 11 | Bullseye |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En x86-64 moderno, el mecanismo real para pasar a modo kernel ya no es `int 80h` (eso es el mecanismo clásico de 32 bits): se usa la instrucción `syscall`, más rápida, apoyada además en el **vDSO** (una pequeña librería que el kernel mapea en el espacio de cada proceso para resolver algunas llamadas sin cambiar de modo). El PDF describe el mecanismo histórico, que sigue siendo válido conceptualmente y es el que suele preguntarse en examen.

## 2. Gestión de paquetes (paquetería)

### Familia Debian (`.deb`)

| Modo | Comando |
|---|---|
| Offline | `dpkg -i java-1.6.o.deb` |
| Frontends | `aptitude` / `dselect` / `synaptic` |

| Online — instalar | `apt-get install nombre_paquete` |

```
# dpkg -i flash_2.8.2+squeeze1_i386.deb   (instalación offline)
# dpkg -l                                (lista paquetes instalados)

# dpkg -c flash_2.8.2+squeeze1_i386.deb  (listar el contenido)
# dpkg -s nombre_paquete                 (chequea si está instalado)
# dpkg -L nombre_paquete                 (localización/directorios de la instalación)
# dpkg -P nombre_paquete                 (elimina el paquete y ficheros de configuración)
```

- **Artifactory Packages**: gestor de repositorio — foto del sistema actualizado con las instalaciones.

> `dpkg`/`rpm` trabajan **offline** contra un `.deb`/`.rpm` concreto (no resuelven dependencias por sí solos). `apt`/`apt-get` y `yum`/`dnf` trabajan **online** contra un repositorio y sí resuelven dependencias automáticamente.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Snap y Flatpak (y también AppImage, no citado en el PDF) resuelven un problema distinto al de apt/yum: empaquetan la aplicación **junto con sus dependencias**, de forma que el mismo paquete funciona igual en cualquier distribución sin depender de las versiones de librerías del sistema — a cambio de paquetes más pesados y, en el caso de Snap/Flatpak, ejecución en un sandbox con permisos limitados.

## 3. Sistema de ficheros

### 3.1 Tipos de sistemas de ficheros

| FS | Journaling | Límites / notas |
|---|---|---|
| **ext2** | No | 2 TB/archivo – 4 TB/partición |
| **ext3** | Sí | 2 TB/archivo – 32 TB/partición |
| **ext4** | Sí | 16 TB/archivo – 1 EB/partición |
| **FAT** | — | MSDOS/Windows. vFAT (FAT32): sistema enlazado |
| **iso9660** | — | CD |
| **udf** | — | DVD |
| **nfs** | — | Red |
| **zfs** | — | 16 EB/archivo – 16 EB/partición |
| **cifs** | — | SMB/CIFS. Sistema de ficheros de red: `\\servidor\carpeta_compartida` |
| **reiserFS** | Sí | Usado por Suse |
| **JFS** | Sí | — |
| **xfs** | Sí | RedHat 7 |
| **btrfs** | — | Intenta sustituir a ext4 |

**Journaling** = llevar una especie de cuaderno de bitácora (registro de las operaciones antes de aplicarlas, para poder recuperarse tras un fallo).

Todos los sistemas de ficheros se gobiernan desde un **único árbol de directorios** (ejemplo: `/` con `/home`, `/var`; `/dev/sda1` en ext4 montado en `/mnt`; `/dev/cdrom` en iso9660; `/dev/sdb1` en FAT montado como spool; `\\servidor\share` como cliente CIFS de un recurso Windows).

No es habitual, pero Linux puede actuar como servidor de ficheros compartiendo carpetas: hace falta el paquete **Samba** (`smbd` es el demonio SMB/CIFS).

```
apt install samba
apt install smbclient
```

### 3.2 Virtual File System (VFS)

Capa que ven los **procesos**; en función del sistema de ficheros montado, usa las funciones específicas de ese FS. Los procesos no ven las llamadas reales — es similar a un driver, actúa de cliente de FAT, CIFS, etc. Así se consigue usar de modo homogéneo todo el almacenamiento (algo que **no** pasa en Windows, donde las unidades son independientes). El equivalente en Windows es el **HAL** (Hardware Abstraction Layer).

Flujo: `Procesos → VFS Layer (system call: open/close/read/write) → implementación específica (ext4 / FAT / iso9660 / …)`.

### 3.3 i-nodo y `struct dirent`

Hay **un i-nodo por fichero**. El **nombre** del fichero no vive en el i-nodo, sino en la `struct dirent` (estructura interna de los directorios).

| Campo del i-nodo | Contenido |
|---|---|
| Nº i-nodo | — |
| Tamaño | — |
| Owner UID / Owner GID | — |
| a time | Acceso |
| m time | Modificación: si cambia el contenido, cambia m time. Al ser metadato, cambia también c time |
| c time | Cambio: si cambia un metadato (permiso, fecha de modificación...) |
| Tipo Fichero | — |
| Permisos | — |
| Nº Hard Links | Al borrar un hard-link se decrementa. Si llega a 0 se borra el i-nodo |
| BD directos / BD index simple / BD index doble / BD index triple | Indexación simple, doble y triple para localizar los bloques de datos |

Algunos sistemas tienen también **Creation time** (Birth).

> [!note] Ampliación (conocimiento general, no viene del PDF)
> La indexación simple/doble/triple es el mecanismo clásico de ext2/ext3/ext4: el i-nodo guarda punteros a un puñado de bloques **directos** para ficheros pequeños, y para ficheros más grandes usa bloques **indirectos** (un bloque lleno de punteros a otros bloques de datos), **doblemente indirectos** (un bloque de punteros a bloques indirectos) y **triplemente indirectos**, permitiendo que un fichero crezca mucho sin que el i-nodo tenga que guardar un puntero por cada bloque de datos. La asignación indexada basada en i-nodos frente a la asignación enlazada de FAT/FAT32 se explica en [[B2 - T4.1 SISTEMAS OPERATIVOS]].

### 3.5 Permisos

**Permisos = Permiso base AND NOT (umask)**

| | Valor |
|---|---|
| Permiso base fichero | 666 |
| Permiso base directorio | 777 |
| umask (por defecto) | 0022 |

```
# chmod 755 fichero      (activar permisos rwx r_x r_x)
# chmod --reference=fichero_origen fichero_destino   (copiar permisos de un fichero a otro)
# chmod a+x f.sh         (ejecución a todos)
```

**SetUID y SetGID**: se activan para que cualquier usuario o grupo ejecute el fichero como si fuese el owner. Se muestran en la posición del permiso `x` del user y del group: `s` si `x` está activo para user/group, `S` si no lo está. Si u/g no tiene permiso `x`, no se ejecutará.

**Sticky bit**: evita que un usuario pueda borrar ficheros o directorios de otro usuario dentro de ese directorio. `t` si `x` está activo para others, `T` si no lo está.

```
chmod 7777 file        (4 suid + 2 sgid + 1 sticky)
chmod u+s file          (también "g+s" y "o+t" para activarlos)

# chmod 1755 fichero     (activar permisos + bit sticky. Idem que "o+t")
# chmod 2755 ejecutable  (activar permisos + bit SetGID. Idem que "g+s")
# chmod 4755 ejecutable  (activar permisos + bit SetUID. Idem que "u+s")
```

> [!important] Cálculo del dígito especial de chmod
> El primer dígito de un `chmod NNNN` de 4 cifras es la suma de **SetUID (4) + SetGID (2) + Sticky (1)**. Es exactamente el mismo patrón que rwx = 4+2+1 aplicado a los tres bits especiales, no una tabla nueva que memorizar.

### 3.6 ACLs (Listas de Control de Acceso)

No se pueden especificar permisos para un usuario o grupo concreto que no sea el owner con los permisos clásicos — para eso están las **ACLs**:

```
# setfacl -m u:pepe:rw /path/fichero        (añade ACL de rw para el usuario pepe)
# setfacl -m g:developers:rwx /path/fichero (añade ACL de rwx para el grupo developers)
# setfacl -x "acl" fichero                  (elimina una ACL concreta)
# setfacl -b fichero                        (borra todas las ACLs del fichero)
getfacl file                                 (muestra las ACLs de file)
```

Si la última posición de `ls -l` tiene valor **`+`**, el fichero tiene ACLs definidas.

### 3.7 Enlaces (hard vs soft)

```
# ln -s origen nombre_enlace   (enlace simbólico, funciona con directorios y ficheros)
# ln origen nombre_enlace      (enlace duro/hard-link, no vale para directorios)
# ln -d                        (crea un enlace simbólico a un directorio)
```

| | Enlace simbólico (`ln -s`) | Enlace duro (`ln`) |
|---|---|---|
| i-nodos | Diferentes (≈ acceso directo de Windows) | Un único i-nodo, comparten todo |
| Permisos | Siempre 777, ya que son los del fichero original | Cambiar permisos del enlace cambia los de todos (es a nivel i-nodo) |
| Si se borra el original | Deja de funcionar | No afecta (solo se decrementa el contador de hard-links) |
| Entre particiones | — | **No** puede usarse (los nº de i-nodo son por partición) |
| Sobre directorios | Sí | **No**, solo contra ficheros |

| `/home/` | Directorio 'home' de usuario |
| `/lib/` | Librerías esenciales compartidas y módulos de kernel |
| `/media/` | Punto de montaje para medios removibles |
| `/mnt/` | Punto de montaje temporal para sistemas de archivos |
| `/opt/` | Agregados de paquetes de software y aplicaciones |
| `/sbin/` | Binarios de sistema |
| `/srv/` | Datos para los servicios provistos por este sistema |
| `/tmp/` | Archivos temporales |

### 4.3 Streams y redirecciones

`/stdin` = 0, `/stdout` = 1, `/stderr` = 2

| Operador | Significado |
|---|---|
| `>` | Crea el destino o lo sobrescribe |
| `>>` | Crea el destino o añade |
| `\|` | Pipe. La salida de un comando es la entrada del siguiente |
| `&>` | Redirecciona stdout y stderr |
| `2>&1` | stderr hacia donde apunte stdout |
| `1>&2` | stdout hacia donde apunte stderr |
| `: >` | Vacía un fichero |

- `tee` → redirige a un fichero y a la salida estándar a la vez.
- `xargs` → canalizaciones de ejecución. `find ./ -name "*~" | xargs -d "\n" rm`: por cada fichero localizado (separado por `\n`), hace un `rm`.

### 4.4 Expresiones regulares — metacaracteres

| Símbolo | Significado |
|---|---|
| `+` | 1 o más |
| `*` | 0 o más |
| `?` | 0 o 1 |
| `.` | Cualquier carácter, pero solo uno |
| `\` | Escapar símbolos especiales (`\.com`) |
| `^` | Inicio de línea |

| `{M,}` | M o más ocurrencias |
| `{M,N}` | M a N ocurrencias — `grep '[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}'` direcciones IP |
| `[:digit:]` | `[0-9]` |
| `[:alpha:]` | `[A-Za-z]` |
| `[:punct:]` | Caracteres de puntuación: `# $ . , ; : ( ) [ ] { } ~ ? ¿ ! ¡` etc. |

### 4.5 Compresión y empaquetado

| Comando | Función |
|---|---|
| `tar` | Empaqueta/desempaqueta (`tgz` primero, directorio después). `c` crea `x` extrae `v` verbose `t` lista `f` para ficheros `z` gzip `j` bzip2 `J` xz `r` actualiza/añade un fichero concreto |
| `gzip`/`gunzip` | Comprime/descomprime |
| `cpio` | Similar a `tar` para copias de seguridad. `-i` extrae `-o` crea. `find * \| cpio -pdm nuevo_dir` |
| `split` | Genera ficheros de trozos de X líneas o X bytes |
| `dd` | Copia entre dispositivos a bajo nivel. `if=` origen `of=` destino `bs=` bytes `count=` veces |
| `rsync` | Copia/sincronización remota de ficheros / backup inteligente usando el algoritmo delta (alternativa a [[scp y sftp (transferencia de ficheros por SSH)]] cuando se usa con `-e ssh`) |

```
# tar cvf file.tar *.c                          (crea un fichero empaquetado sin comprimir)
# tar cvfz file.tar.gz *.c                      (crea un fichero empaquetado y comprimido con gzip)
# tar cvfj Phpfiles-org.tar.bz2 /home/php       (crea un fichero empaquetado y comprimido con bzip2)
# tar xvf file.tar                              (desempaqueta un fichero con o sin compresión)
# tar xvf videos-14-09-12.tar.bz2               (desempaqueta un fichero con o sin compresión)
opciones: -r (actualiza/añade un fichero); -f (especificar el nombre del fichero resultante);
          -J (algoritmo de compresión xz); -t (lista el contenido)

# rsync -avzh /root/rpmpkgs /tmp/backups/                (en local)
# rsync -avzh rpmpkgs/ root@192.168.0.101:/home/          (en remoto contra el rsync daemon, puerto 873 por defecto)
# rsync -avzhe ssh root@192.168.0.100:/root/install.log /tmp/  (en remoto contra el servicio SSH)
opciones comunes: -v verbose · -a archive mode (recursivo, conserva links/permisos/propietarios) ·
                   -z comprime · -h human-readable · -e especifica el shell remoto (ssh) ·
                   -u si el destino está modificado no sincroniza con el origen
opciones interesantes: --delete · --max-size='200k' · --bwlimit=600 · --remove-source-files · --dry-run
```

## 5. Gestión de almacenamiento

### 5.1 Discos y particiones

| Interfaz | Dispositivo |
|---|---|
| PATA/IDE | `/dev/hda` (maestro) / `/dev/hdb` (esclavo) |
| SATA/SCSI | `/dev/sda` / `/dev/sdb` |

En **MBR**: las particiones **1-4 son siempre primarias**; las particiones **5-N son lógicas** (dentro de la extendida, que solo puede haber una).

```
# fdisk /dev/sdb   (para discos SATA o SCSI)
# fdisk /dev/hdb   (para discos PATA o IDE)

Algunos tipos de partición importantes:
8e --> Linux LVM
82 --> Linux swap (paginación)
83 --> Linux (ext4 por ej)
fd --> Linux raid
```

- `gdisk` → crea particiones GPT (también `parted`).
- `lsblk` → listado de todos los dispositivos de bloque (discos...).
- `hdparm /dev/sda1` → información física del disco: cilindros, pistas...

### 5.2 RAID (`mdadm`)

`mdadm` es la implementación software de [[RAID (Redundant Array of Independent Disks)]] en Linux — la capa que en LVM (más abajo) puede quedar por debajo de los Physical Volumes.

```
# mdadm -Cv /dev/md0 -l0 -n2 -c128 /dev/sdb1 /dev/sdc1

opciones interesantes:
-C (crear el RAID de discos)
-lX (X es el nivel de RAID deseado)
-nY (Y es el número de discos empleados)
-cZ (Z es el tamaño del chunk)
```

### 5.3 Montaje de sistemas de ficheros

```
# mount -t filesystem origen destino
# mount -t ext4 /dev/sdb1 /var/log
# mount -t cifs //server-name/nominas /var/data/nominas -o username=pepe,password=1234,domain=ruinosa
```

Opciones con `-o`:

| Opción | Efecto |
|---|---|
| `ro` | Montaje de solo lectura |
| `rw` | Montaje de lectura-escritura |
| `exec`/`noexec` | Permite ejecutar binarios sobre ese filesystem o no |
| `sync`/`async` | Sincronización de cambios contra el dispositivo o no |
| `nouser` | Solo el root podrá montar el filesystem |

Hay que ser **root** para montar. `/etc/fstab` para montajes permanentes, `/etc/mtab` para los actuales.

> [!note] Notas del PDF de comandos
> Con `cat /proc/filesystems` se ven los sistemas de ficheros soportados. Para usar `cifs` hay que cargar el módulo en el kernel: `modprobe cifs`.

### 5.4 [[LVM (Logical Volume Manager)]]

Mecanismo para hacer más flexible el almacenamiento, para no quedarnos sin espacio en las particiones (en Linux no es fácil ampliar una partición directamente). Todo lo que sean discos físicos o trozos (particiones) se convierten en **Physical Volumes (PV)**. Luego se meten en un **Volume Group (VG)** y de ahí se crean **Logical Volumes (LV)**. LVM permite ampliar en caliente, metiendo un nuevo disco duro y ampliando el VG y los LV.

*Ejemplo del diagrama del PDF*: `/dev/sda` + `/dev/sdb` → Physical Volumes → Volume Group "Data" → Logical Volumes `/web`, `/doc`, `/video`.

| Operación | Comandos |
|---|---|
| **Creación** | `pvcreate` → `vgcreate` → `lvcreate` → `mkfs` → `mount` |
| **Ampliación** | `pvcreate` → `vgextend` → `lvextend` → `resize2fs` |
| **Reducción** | `resize2fs` → `lvreduce` |

```
# pvcreate /dev/sda1 /dev/sdb1 /dev/sdc1
# vgcreate -s 32M tecmint_vg /dev/sda1 /dev/sdb1 /dev/sdc1   (VG a partir de los 3 PV, tamaño de PE=32MB)

# lvcreate -L 18G -n tecmint_documents tecmint_vg   (3 LV a partir del VG)
# lvcreate -L 18G -n tecmint_manager tecmint_vg
# lvcreate -L 18G -n tecmint_public tecmint_vg

# mkfs.ext4 /dev/tecmint_vg/tecmint_documents        (formateamos los 3 LV con ext4)
# mkfs.ext4 /dev/tecmint_vg/tecmint_public
# mkfs.ext4 /dev/tecmint_vg/tecmint_manager

# mount /dev/tecmint_vg/tecmint_documents /mnt/tecmint_documents/   (montamos cada LV)
# mount /dev/tecmint_vg/tecmint_public /mnt/tecmint_public/
# mount /dev/tecmint_vg/tecmint_manager /mnt/tecmint_manager/

Ejemplo de ampliación:
# vgextend tecmint_vg /dev/sda4                       (ampliamos el VG con un PV adicional)
# lvextend -L +2G /dev/tecmint_vg/tecmint_documents    (ampliamos un LV con 2G adicionales)
# resize2fs /dev/tecmint_vg/tecmint_documents           (necesario para que el filesystem actualice sus metadatos)

Ejemplo de reducción de un volumen lógico:
# resize2fs /dev/tecmint_vg/tecmint_documents 10G
# lvreduce -L 10G /dev/tecmint_vg/tecmint_documents

Ejemplo de reducción de un grupo de volúmenes:
# vgreduce -v vg_testing /dev/sdc1   (para esto no puede haber ningún PE en sdc1)
# pvmove /dev/sdc1                   (esto habría que hacer si sdc1 no estuviera vacío)
```

> [!note] `resize2fs` funciona sin desmontar (ampliar); para reducir hay que desmontar antes.

Comandos de gestión LVM (listado completo del PDF de arquitectura): `pvcreate`, `pvdisplay`, `vgcreate`, `vgdisplay`, `vgextend`, `vgreduce`, `lvcreate`, `lvdisplay`, `lvextend`, `lvreduce`.

**3 pasos siempre**: 1) crear la partición (`fdisk`) → 2) crear el sistema de ficheros sobre la partición (`mkfs`) → 3) montarlo para acceder (`mount`).

```
# mkfs.ext4 /dev/sdb1
# resize2fs /dev/sdb1 50g     (si no se pone tamaño, toma el máximo posible)
opción -M: reduce hasta el mínimo posible el filesystem

# umount /dev/vdb1            (requisito previo)
# e2fsck /dev/vdb1
Pass 1: Checking inodes, blocks, and sizes
Pass 2: Checking directory structure
Pass 3: Checking directory connectivity
Pass 4: Checking reference counts
Pass 5: Checking group summary information
```

### 5.5 Comandos de diagnóstico de almacenamiento

- `fsck` → chequear y reparar sistemas de ficheros.
- `df -h` → espacio disponible en un dispositivo, formato humano.
- `du -sch /var/log` → espacio ocupado por un fichero/directorio.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Además de crear/ampliar/reducir volúmenes, LVM soporta **snapshots**: una copia congelada de un LV en un instante concreto, muy usada para hacer backups consistentes de un volumen que sigue en uso (la base de datos o la VM no se detienen). No es tema del PDF, pero es la razón principal por la que LVM se usa en producción más allá de la simple flexibilidad de tamaño.

## 6. Gestión de procesos

En Linux **todo son procesos**, creados con `fork()` (system call). El proceso **`init`** tiene el **PID 1** y va creando el resto de procesos con `fork()`; cada proceso puede crear otros procesos. El kernel maneja los threads desde la versión **2.6**; antes los manejaba la propia aplicación con una librería (`pthreads` = POSIX threads).

Los comandos internos del shell **no generan procesos** (ejemplos: `cd`, `pwd`, `kill`, `umask`, `exec`, `history`, `set`, `alias`, `echo`).

### 6.1 Prioridad (`nice`/`renice`)

`nice` cambia la prioridad de un proceso: **0** por defecto, **-20** máxima, **19** mínima. Solo **root** puede dar valores negativos. `-n +-N` suma o resta prioridad.

```
nice -n valor-de-nice comando argumentos     (solo el root puede usar valores negativos; rango -20 a +19, 10 por defecto)
# nice -n 19 dd if=/dev/cdrom of=~/ubuntu-17.04-desktop-amd64.iso     (tarea pesada -> valor positivo alto)
# renice -n -12 -p 1055        (solo a ese PID)
# renice -n -2 -u apache2      (para todos los procesos del usuario apache2)
```

En `/etc/security/limits.conf` también se puede fijar un `nice` por usuario: `apache2 hard priority 10`.

En `top`, `PR` es la prioridad a nivel de kernel (`rt` = tiempo real): **PR = 20 + NI**.

### 6.2 Ejecución en background y señales al cerrar sesión

- `comando &` → lanza el comando en background. Si se hace `logout`, `exit` o `exec`, se corta el proceso, ya que se manda la señal **SIGHUP** (Hang Up = colgar) y finaliza.
- `nohup comando &` → para lanzar en background y que no finalice al salir de la sesión.

```
# nohup sh your-script.sh > /path/to/custom.out &
```

### 6.3 Consulta y control de procesos

| Comando | Función |
|---|---|
| `fg`, `bg`, `jobs` | `jobs` muestra procesos en segundo plano; `fg %1` trae el proceso 1 a primer plano; `bg %1` lo manda a background |
| `pstree` | Árbol de procesos: cómo se han ido "forkeando" y sus dependencias |
| `ps` / `top` | Muestran los procesos; `top` de forma dinámica |
| `vmstat` | Información de procesos, memoria, paginación, I/O, CPU, disco |
| `kill` | Manda señal al proceso. `kill -9 id_proc` manda SIGKILL y lo finaliza. `pkill`/`killall` actúan por nombre |
| `watch` | Monitoriza la salida de un comando en tiempo real. `-n segundos` `-d` resalta cambios |

**Campos de `top`:**

| Campo | Explicación |
|---|---|
| PID | PID del proceso |
| USER | Usuario que lanzó el proceso |
| PR | Prioridad a nivel de kernel. `rt` = tiempo real. `PR = 20 + NI` |
| NI | Valor de "nice". Bajo (hasta -20) = más prioridad; alto (hasta 19) = menos |
| VIRT | Memoria virtual total consumida por el proceso |
| RES | Memoria consumida por el proceso en RAM |
| SHR | Memoria compartida con otros procesos |
| S | Estado del proceso |
| %CPU | Porcentaje de CPU utilizado |
| %MEM | RES en porcentaje respecto del total de RAM |
| TIME+ | Tiempo de CPU usado desde que inició |

**`ps -eF`** (todos los procesos, formato largo extendido; con `--forest` o `-H` saca el árbol padres/hijos):

| Campo | Explicación |
|---|---|
| PPID | PID del proceso padre |
| C | Consumo de CPU |
| SZ | Consumo de memoria virtual |
| S / STAT | Estado del proceso (R=Running, S=interruptible sleep esperando un evento...) |
| RSS | Consumo de memoria real |
| PSR | Procesador asignado |
| STIME | Cuándo inició el proceso |

**`ps -eLf`** (info de threads; con `-H` también saca info de threads): añade `LWP` (ID del thread) y `NLWP` (número de threads del proceso).

Otras opciones de `ps`: `-p` PID concreto · `-u`/`-U` procesos del usuario efectivo/real · `-g`/`-G` procesos del grupo efectivo/real · `-eo lista_columnas`.

```
# kill -l                        (muestra todas las señales)
# kill SIGKILL 63772  o  kill -9 63772   (63772 es un PID)
```

**Señales principales:**

| Señal | Nº | Descripción |
|---|---|---|
| SIGHUP | 1 | Hang up detectado en el terminal de control o muerte del proceso de control |
| SIGINT | 2 | El usuario envía una señal de interrupción (Ctrl+C) |
| SIGQUIT | 3 | El usuario envía una señal de salida (Ctrl+D) |
| SIGFPE | 8 | Se produce un error matemático ilegal |
| SIGKILL | 9 | Si un proceso recibe esta señal debe terminar inmediatamente y no realizará ninguna operación de limpieza |
| SIGALRM | 14 | Reloj de alarma (usado para timers) |
| SIGTERM | 15 | Envío de señal de terminación software (por defecto) |
| SIGTSTP | 20 | Provoca que el proceso se suspenda |

### 6.4 Planificación de tareas

- `journalctl -xe` → muestra los mensajes de los demonios.
- `at now + 1 minute ... CTRL+D` → planifica un comando para un momento concreto. `atq` ver trabajos encolados; `atrm` eliminar un trabajo encolado.
- `anacron` → ejecuta tareas que han quedado pendientes de realizar. **Cron ejecuta anacron**.
- `cron` → demonio que va chequeando las planificaciones para ejecutarlas.

Formato del `crontab`: `minuto hora dia-mes mes dia-semana usuario comando`

| Campo | Rango |
|---|---|
| minuto (m) | 0-59 |
| hora (h) | 0-23 |
| día del mes (dom) | 1-31 |
| mes (mon) | 1-12 |
| día de la semana (dow) | 0-7 (0 y 7 son domingo) |

```
# crontab -e   (edita /etc/crontab)
# crontab -l   (lista el crontab actual)
# crontab -r   (borra el crontab actual)
```

Ejemplos: `0,30` cada 30 minutos; `*/15` cada 15 minutos.

| Cadena | Explicación |
|---|---|
| `@daily root /path/to/backup/script.sh` | Ejecución diaria del script |
| `3/3 2/4 2 2 2` | Cada 3 minutos empezando en el 3 (3,6,9…) de las horas 2,6,10… (cada 4h desde la 2) del día 2 de febrero y que sea martes |
| `45 10 * * sun root apt-get -y update` | Actualización todos los domingos a las 10:45 |
| `00 12 1,15,28 * *` | A las 12:00 los días 1, 15 y 28 de cada mes (ideal para nóminas) |
| `@reboot root /path/to/inicio/script.sh` | Ejecución única al arranque |

> [!note] Cada usuario tiene su propio crontab, guardado en `/var/spool/cron/crontabs/`, siempre que no esté en `/etc/cron.deny`. Si el día del mes y el día de la semana tienen valor ambos, se ejecuta cuando se cumpla **cualquiera** de los dos (es un OR, no un AND).

Directorios relacionados: `/etc/cron.d` (más ficheros crontab, para no meterlo todo en `/etc/crontab`), `/etc/cron.daily` y `/etc/cron.hourly` (directorios/atajo para scripts diarios/cada hora).

## 7. Arranque del sistema (boot process)

`dmesg` → lista los mensajes de consola cuando arranca el SO.

```
# dmesg --level=alert,crit,...   (filtrar por el nivel de cada mensaje)
# dmesg -k                       (mensajes del kernel)
# dmesg -T                       (fecha y hora en formato legible)
# dmesg -w                       (se queda esperando a nuevos mensajes)
# dmesg -u                       (mensajes del espacio de usuario)
```

### 7.1 Firmware y particionado de arranque

| Elemento | Descripción |
|---|---|
| **BIOS** | Basic Input/Output System. Modo texto. Prueba el HW al encender y arranca el sistema |
| **UEFI** | Unified Extensible Firmware Interface. Menú gráfico e incluso acceso remoto |
| **MBR** | Master Boot Record. 4 particiones |
| **GPT** | GUID Partition Table. Infinitas particiones, pero limitadas a 128 |
| **LILO/GRUB** | Gestores de arranque |

Flujo: `BIOS → MBR → LILO/GRUB → Boot Sector` · `UEFI → GPT → GRUB → Boot Sector`

### 7.2 Init clásico (SysVinit) vs Systemd

| | Init clásico | Systemd |
|---|---|---|
| Binario | `/sbin/init` (PID 1) | `/bin/systemd` → `/lib/systemd/systemd` |
| Scripts | `/etc/init.d` contiene los scripts de arranque de los servicios | — |
| Fichero de config del arranque | `/etc/inittab` | `/etc/systemd/system` (unidades instaladas por el administrador) |
| Unidad de modo de arranque | **Runlevel** | **Target** (ya no van por números, sino por nombres) |

**Runlevel** (modo de inicio de Linux, default 2):

| Runlevel | Significado |
|---|---|
| 0 | Apagar |
| 1 | Modo Single (root, sin red ni servicios; para reparaciones u operaciones) |
| 2-5 | Multiusuario (5 = Multiusuario con X11) |
| 6 | Reiniciar |

El runlevel indica el directorio donde están los enlaces a los scripts de los servicios/demonios: `/etc/rc0.d`, `/etc/rc6.d`, `/etc/rcS.d` (ejemplo: `S10Apache`, `S20Mysql`, `K10Jboss`; `S10Apache` → `/etc/init.d/apache2`). `S` = iniciar, `K` = parar. `S10`, `S20`... van ordenados.

**Comandos para arrancar servicios**: antes `service nombre_servicio start`; después `systemctl start nombre_servicio`.

**Tabla comparativa de comandos de servicio:**

| Acción | SysVinit | Systemd |
|---|---|---|
| Iniciar un servicio | `service dummy start` | `systemctl start dummy.service` |
| Parar un servicio | `service dummy stop` | `systemctl stop dummy.service` |
| Reiniciar un servicio | `service dummy restart` | `systemctl restart dummy.service` |
| Recargar un servicio | `service dummy reload` | `systemctl reload dummy.service` |
| Estado de un servicio | `service dummy status` | `systemctl status dummy.service` |
| Reiniciar si ya está corriendo | `service dummy condrestart` | `systemctl condrestart dummy.service` |
| Activar al arranque | `chkconfig dummy on` | `systemctl enable dummy.service` |
| Desactivar al arranque | `chkconfig dummy off` | `systemctl disable dummy.service` |
| Comprobar si está activado al arranque | `chkconfig dummy` | `systemctl is-enabled dummy.service` |
| Crear/modificar un fichero de servicio | — | `systemctl daemon-reload` |

*(Nota: versiones recientes de systemd admiten también el formato `systemctl start dummy` sin `.service`)*

**Tabla comparativa de runlevels/targets:**

| Significado | SysVinit | Systemd |
|---|---|---|
| Apagado del sistema | 0 | `runlevel0.target`, `poweroff.target` |
| Modo monousuario | 1, s, single | `runlevel1.target`, `rescue.target` |
| Multiusuario | 2 | `runlevel2.target`, `multi-user.target` |
| Multiusuario con red | 3 | `runlevel3.target`, `multi-user.target` |
| Experimental | 4 | `runlevel4.target`, `multi-user.target` |
| Multiusuario, con red, modo gráfico | 5 | `runlevel5.target`, `graphical.target` |
| Reiniciar | 6 | `runlevel6.target`, `reboot.target` |
| Shell de emergencia | `emergency` | `emergency.target` |
| Cambiar a runlevel/target multiusuario | `telinit 3` | `systemctl isolate multi-user.target` (o `systemctl isolate runlevel3.target`) |
| Fijar target multiusuario en el próximo arranque | `sed s/^id.*:initdefault:/id:3:initdefault:/` | `ln -sf /lib/systemd/system/multi-user.target /etc/systemd/system/default.target` |
| Comprobar runlevel actual | `runlevel` | `systemctl get-default` |
| Cambiar runlevel por defecto | `sed s/^id.*:initdefault:/id:3:initdefault:/` | `systemctl set-default multi-user.target` |

**Comandos de apagado/reinicio:**

```
# shutdown now      (con -P apaga la máquina)
# shutdown -H now   (para la máquina: procesos y CPU. Ej: mantenimiento/cambio de tarjeta PCI)
# shutdown -c        (cancela un shutdown pendiente)
# poweroff           (apaga la máquina)
# poweroff --reboot  (reinicia la máquina)
# halt               (para la máquina)
# halt -p            (apaga la máquina)
# halt --reboot      (reinicia la máquina)

# systemctl reboot
# systemctl poweroff
# systemctl halt
```

```
# sysctl -a                              (lista completa de parámetros del kernel)
# sysctl -w net.ipv4.ip_forward=1        (ej. capacidad de routing, cambio temporal)
# echo "net.ipv4.icmp_echo_ignore_all = 1" >> /etc/sysctl.conf    (cambio definitivo)
# sysctl -p                              (aplica los cambios)

# free -h            (formato legible)
# free -b/m/g/k       (bytes/kibi/mebi/gibibyte, base 2)
# free --si            (unidades del sistema internacional, base 10; ≈ cat /proc/meminfo)
```

## 10. iptables — cortafuegos

**Cadenas**: `PREROUTING`, `INPUT`, `FORWARD`, `POSTROUTING`, `OUTPUT`
**Tablas**: `raw`, `nat`, `filter` (por defecto), `mangle`, `connection tracking`

### 10.1 Los 3 casos de uso

| Caso | Cadenas implicadas |
|---|---|
| Filtrar el tráfico de **entrada** | `PREROUTING → INPUT` |
| Filtrar el tráfico de **salida** | `OUTPUT → POSTROUTING` |
| Máquina como **"router"** (routing/NAT) | `PREROUTING → FORWARD → POSTROUTING` |

El caso "router" supone tener varias tarjetas de red: lo que entra por una sale por otra. El **forwarding no está permitido por defecto**, hay que activarlo:

- Cambio temporal: `echo 1 > /proc/sys/net/ipv4/ip_forward`
- Cambio permanente: añadir a `/etc/sysctl.conf` la línea `net.ipv4.ip_forward=1`

### 10.2 Persistencia de las reglas

Las reglas creadas con `iptables` son **volátiles**, disponibles solo hasta que se apaga el equipo. Se pueden guardar y restaurar:

| Distro | Guardar | Restaurar |
|---|---|---|
| Debian/Ubuntu | `iptables-save > /etc/iptables/rules.v4` | `iptables-restore < /etc/iptables/rules.v4` |
| RHEL/CentOS | `iptables-save > /etc/sysconfig/iptables` | `iptables-restore < /etc/sysconfig/iptables` |

A partir de Debian 6.0 existe el paquete **`iptables-persistent`** (hay que instalarlo) encargado de la carga automática de las reglas guardadas. Se deben guardar en `/etc/iptables/rules.v4` (IPv4) y `/etc/iptables/rules.v6` (IPv6).

> [!important] Orden de las reglas
> Si en una tabla hay una regla que hace **match** (se comprueban por orden), el resto de reglas de esa tabla **no se miran**.

### 10.3 Comandos básicos

```
# apt install iptables

# iptables -t nombretabla -L -n -v   (si no se especifica -t, por defecto es "filter")
-L listar reglas
-n resultados en formato numérico
-v (verbose) salida más completa: paquetes y bytes que atraviesan una cadena

# iptables --flush   (o -F)   borra todas las reglas
# iptables -Z         pone a cero los contadores de paquetes

-P Política  · -p Protocolo · -m Módulo · -S/-L lista reglas
-i eth_input · -o eth_output · -d N (borra la regla N) · -R (reemplazar)
-D CADENA numregla   (elimina la regla según la posición, por defecto 1)
-I CADENA numregla   (inserta la regla en la posición, por defecto 1)
```

### 10.4 SNAT, MASQUERADE, DNAT y REDIRECT

```
# iptables -t nat -A POSTROUTING -s 192.168.3.0/24 -o eth0 -j SNAT --to 80.58.1.14
-A POSTROUTING: añade (--append) una regla a la cadena POSTROUTING
-s 192.168.3.0/24: se aplica a paquetes con esa IP de origen
-o eth0: se aplica a paquetes que salen (out-interface) por eth0
-j SNAT --to 80.58.1.14 (--to ≡ --to-source): cambia la dirección de origen

# iptables -t nat -A POSTROUTING -s 192.168.3.0/24 -o eth0 -j MASQUERADE
-j MASQUERADE: cambia la dirección origen por la que tenga la interfaz de salida (eth0)

# iptables -t nat -A PREROUTING -p tcp --dport 80 -i eth0 -j DNAT --to 192.168.3.2
-p tcp: protocolo de transporte
--dport 80 (≡ --destination-port 80): ligado al parámetro -p
-i eth0: interfaz de entrada (in-interface)
-j DNAT --to 192.168.3.2 (--to ≡ --to-destination): cambia la dirección IP destino

# iptables -A PREROUTING -t nat -i eth0 -p tcp --dport 8888 -j REDIRECT --to-port 80
REDIRECT --to-port 80: redirige al puerto especificado. Solo válido en la tabla nat, cadenas PREROUTING y OUTPUT

# iptables -P FORWARD DROP   (establece la política por defecto)
```

**Objetivos (`-j`) — qué hacer cuando el paquete coincide:**

| Objetivo | Efecto |
|---|---|
| `ACCEPT` | Deja pasar el paquete |
| `DROP` | Rechaza el paquete, no envía respuesta |
| `REJECT` | Rechaza el paquete y envía un mensaje de error ICMP. Solo válido en `INPUT`, `FORWARD` y `OUTPUT` |
| `REDIRECT` | Redirige al puerto especificado. Solo en tabla `nat`, cadenas `PREROUTING` y `OUTPUT` |
| `SNAT` / `MASQUERADE` | Cambian la IP de origen (la segunda, tomándola de la interfaz de salida) |
| `DNAT` | Cambia la IP de destino |

> [!important] DROP vs REJECT
> `DROP` descarta el paquete en silencio (no hay respuesta). `REJECT` descarta el paquete pero **avisa** con un mensaje ICMP de error. `REJECT` solo es válido en `INPUT`/`FORWARD`/`OUTPUT`, nunca en `PREROUTING`/`POSTROUTING`.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En la práctica, **SNAT/MASQUERADE** es lo típico en un router doméstico o de salida a Internet compartiendo una única IP pública entre varias máquinas internas (Network Address Translation clásico); **DNAT** es lo típico para publicar un servicio interno hacia fuera (port-forwarding: "quien llegue al puerto 80 del router, que se le redirija al servidor interno 192.168.3.2"). La diferencia entre `SNAT` y `MASQUERADE` es que `SNAT` exige indicar la IP fija de salida, mientras que `MASQUERADE` la toma dinámicamente de la interfaz — útil cuando la IP pública es asignada por DHCP y puede cambiar.

## 11. Shell, scripting y entorno gráfico

### 11.1 Shell

**Shell**: intérprete de comandos, permite programar (*shell scripting*). Se pueden tener varios niveles de shell: si se hace `su root` se entra en un nivel de shell diferente; `exit` vuelve al nivel anterior. Se usa para aislar, proteger y dar visibilidad.

Tipos: **BASH · BSH · TCSH · CSH · KSH · ZSH**

Ficheros de configuración:

| Ámbito | Fichero |
|---|---|
| Global al sistema | `/etc/profile` (llama a `bash.bashrc`), `/etc/bash.bashrc` |
| Plantilla para nuevos usuarios | `/etc/skel` (ficheros que tendrá cada usuario nuevo en su HOME tras crearse) |
| Del usuario | `~/.profile`, `~/.bashrc` (`~` es el HOME_DIR) |
| Histórico | `~/.bash_history` |

### 11.2 Scripting

Los scripts son ficheros `.sh`. Comienzo típico: `#! /bin/sh`, que fuerza a que el script se lance con el shell indicado.

- `$(comando)` ≈ `` `comando` `` → resultado de ejecutar el comando.
- `if [-s /tmp/f1.txt]` ≈ `if test -s /tmp/f1.txt` → `[ ]` y `test` hacen lo mismo, evalúan una condición. `-s` comprueba que el tamaño es > 0.

**Línea de comandos dentro de un script:**

| Variable | Significado |
|---|---|
| `$0` | Nombre del comando |
| `$1`, `$2`... | Parámetros |
| `$$` | PID asignado por el SO para ejecutar ese script |
| `$*` (≡ `$@`) | Todos los parámetros juntos |
| `$#` | Número de parámetros |

`echo '$0: ' + $0` debe ir entre comillas para que no se resuelva.

**Variables de entorno:**

| Acción | Sintaxis |
|---|---|
| Asignación | `TEST=valor` |
| Listado | `echo $TEST` |
| Referencia/Valor | `$TEST` |
| Exportación | `export TEST` |

Variables predefinidas: `env` muestra las variables de entorno — `PWD` (path), `HOME` (raíz del usuario), `USER` (usuario conectado), `OLDPWD` (directorio anterior, `cd -`), `SHELL` (shell utilizado).

`awk` es un lenguaje de programación diseñado para procesar datos basados en texto, ficheros o flujos de datos.

### 11.3 X-Window

**Protocolo X-Window** (o Sistema X-Window): los escritorios tienen gestores de ventanas por debajo. El **Servidor X** es la máquina del usuario final, quien manda los eventos. El **Cliente X** es donde está la aplicación, quien pinta las ventanas. La evolución es **Wayland**, que promete ser más simple y eficiente que X-Window.

**Gestores de ventanas:**

| Gestor | Componente |
|---|---|
| KDE | Qt |
| GNOME | GTK+ |
| xfce | GTK+ |
| LXDE | GTK |
| UNITY | GTK3 |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> El código de salida de un script/comando (`$?`) no aparece en el PDF, pero es imprescindible para el scripting real: cada comando termina con un código numérico (0 = éxito, distinto de 0 = error) accesible en la variable `$?` inmediatamente después de ejecutarlo, y es la base de las condiciones en scripts (`if comando; then ...`).

## 13. Seguridad

### 13.1 Gestión de usuarios y grupos

`/etc/passwd` — formato: `nombre : password : uid : gid : home : shell`

- Si la password es `x`, está cifrada y el hash se guarda en `/etc/shadow`.
- Si delante del hash aparece `!`, la cuenta está bloqueada.
- Si aparece `*`, o si el shell es `/usr/sbin/nologin` o `/bin/false`, es una cuenta de servicio (no nominal), no puede hacer login desde terminal.
- El usuario **root** tiene el **ID 0**. Los usuarios normales se crean a partir del **ID 1000**.

```
Fichero /etc/passwd (username - password - uid - gid - comentario - home - shell)
sally:x:1029:503:Sally Jones:/home/sally:/bin/bash
TIP: la "x" indica que la password está en /etc/shadow

Fichero /etc/shadow (username - hash de la password - último cambio de password ...)
sally:$6$EmoFkLZPkHkpczVN2XRcMdyj8/ZeeT5UnTQ:15505:0:-1:7:-1:-1:
TIP: un "!" delante de la password indica cuenta bloqueada
TIP: un "*" en la password indica que no se puede hacer login

Fichero /etc/group (groupname - password - GID - lista de usuarios)
project1:x:504:sally,sam,ellen,george
```

| Comando | Función |
|---|---|
| `useradd` | Crea un usuario. `-g` grupo principal `-G` grupos secundarios |
| `adduser` | Script que usa `useradd` (usa `/etc/adduser.conf`, proceso de alta más sencillo e interactivo) |
| `usermod` | Modifica una cuenta de usuario |
| `userdel` | Elimina un usuario y sus ficheros |
| `groupadd` | Crea un grupo (`/etc/group`) |
| `addgroup` | Script que usa `groupadd` |
| `groupmod` | Modifica un grupo |
| `groupdel` | Elimina un grupo del sistema |
| `chage` | Info de expiración de una cuenta. `-L usuario` \| `-E fecha`. Gestiona la expiración de la cuenta y la política de expiración de la password |
| `passwd` | Cambia la contraseña. `-aS` estado de todos los usuarios `-l` bloquea `-u` desbloquea `-e` expira `-d` borra la contraseña |
| `gpasswd` | Administra un grupo. `-a`/`-d` añade/borra usuario `-r` borra contraseña `-A` establece lista de administradores `-M` establece lista de usuarios (machaca) |


**Eliminar usuario de un grupo**: `usermod -rG n_gr n_usu` / `gpasswd -d n_usu n_gr` / `deluser n_usu n_gr`


### 13.2 `sudo` y `su`

- `sudo` → ejecuta un comando como otro usuario (`/etc/sudoers`). `sudo -u carlos comando`.
- `su` → *switch user*, cambiar de usuario para ejecutar comandos. `su -` hace el cambio de usuario **y** carga las variables del environment.

```
Fichero /etc/sudoers (se edita con visudo)
Defaults  badpass_message="Password is wrong, please try again"
Defaults  passwd_tries=5
...
QUIEN DONDE=(COMO QUIEN) COMANDOS
o
USER MACHINE=(EFECTIVE_USER) COMANDOS   (restricciones)
```

### 13.3 Gestión de recursos

- `ulimit` → limita el uso de recursos (nº ficheros abiertos, memoria consumida...). `-S` soft `-H` hard `-n` open files `-T` threads `-a` lista todos los límites.
- `cgroups` → crea "jaulas" para aplicar políticas de control de recursos a un proceso. Más avanzado que `ulimit`. Usado por **Docker**.

```
# cat /proc/sys/fs/file-max    (máximo número de ficheros abiertos para todo el sistema)
# su - oracle
$ ulimit -Hn   (ver el hard limit)
$ ulimit -Sn   (ver el soft limit)

/etc/security/limits.conf:
httpd soft nofile 4096
httpd hard nofile 10240
```

> [!note] Un usuario puede cambiar su límite **soft** pero nunca por encima del **hard** (ej. `$ ulimit -S -s 8192` cambia el stack size a 8192).

### 13.4 SELinux

Módulo diseñado por la **NSA** para implantar políticas de seguridad super restrictivas para una máquina. Sirve para **bastionar y securizar**.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> El contraste habitual con SELinux es **AppArmor** (usado por defecto en Debian/Ubuntu, frente a SELinux en RedHat/CentOS/Fedora): SELinux etiqueta cada proceso y fichero con un contexto de seguridad y aplica políticas muy granulares basadas en esas etiquetas (más potente pero más complejo de administrar); AppArmor aplica perfiles de seguridad basados en **rutas de fichero**, más simple de leer y mantener aunque algo menos granular.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> `cgroups` (control groups) es una de las dos piezas del kernel de Linux sobre las que se construyen los contenedores (Docker, LXC): `cgroups` limita y contabiliza los **recursos** (CPU, memoria, I/O) que puede usar un grupo de procesos, mientras que los **namespaces** (no mencionados en el PDF) aíslan la **vista** que ese grupo de procesos tiene del sistema (su propio árbol de procesos, red, sistema de ficheros...). Un contenedor es, en esencia, un proceso normal de Linux acotado por cgroups y aislado con namespaces — no hay "máquina virtual" real por debajo.

## 🔑 Resumen ultra-rápido

- Arquitectura Linux: monolítica y modular. User space (apps, libc) → SCI (POSIX) → Kernel space (E/S, memoria, procesos, VFS, drivers) → HW. `int 80h` = cambio a modo kernel.
- Familia UNIX: Solaris, SCO, HP-UX, IBM-AIX, BSD (FreeBSD, macOS). Linux por paquetería: Debian(.deb)→Ubuntu→Mint; RedHat(.rpm)→Fedora/CentOS(Rocky)/Mandriva(Mageia); Suse; Slackware(.tgz); Gentoo; Arch(Pacman).
- Paquetería: `dpkg`/`rpm` offline (no dependencias); `apt`/`apt-get` y `yum`/`dnf` online (con dependencias). Catálogos: `/etc/apt/sources.list` (Debian), `/etc/yum.repos.d` (RedHat).
- FS: ext2 (no journal), ext3/ext4 (journal), FAT/vFAT, iso9660(CD), udf(DVD), nfs, zfs, cifs, reiserFS, JFS, xfs, btrfs. VFS unifica el acceso (≈HAL en Windows).
- i-nodo: uno por fichero, sin nombre (el nombre va en `struct dirent`). atime/mtime/ctime. Indexación directa/simple/doble/triple.
- Permisos = base AND NOT umask (fichero 666, dir 777, umask 0022). SetUID/SetGID/Sticky = dígito extra (4+2+1). ACLs con `setfacl`/`getfacl` (marca `+` en `ls -l`).
- Enlaces: simbólico (`ln -s`, i-nodo distinto, se rompe si borras el original, funciona con dirs) vs duro (`ln`, mismo i-nodo, no cruza particiones, no vale para dirs).
- LVM: PV → VG → LV. Crear: pvcreate→vgcreate→lvcreate→mkfs→mount. Ampliar: pvcreate→vgextend→lvextend→resize2fs. Reducir: resize2fs→lvreduce.
- Particiones MBR: 1-4 primarias, 5+ lógicas (tipos: 8e LVM, 82 swap, 83 Linux, fd RAID). GPT hasta 128 particiones.
- Procesos: `fork()`, init = PID 1. nice -20(max, root)..19(min). Señales: SIGHUP(1) cierre sesión, SIGKILL(9), SIGTERM(15). `nohup` evita SIGHUP.
- Boot: BIOS→MBR→LILO/GRUB / UEFI→GPT→GRUB. Init clásico (runlevels 0-6, `/etc/init.d`) vs Systemd (targets, `systemctl`).
- Red: `ip`(nuevo ifconfig), `ss`(nuevo netstat), `nmap` contra otras máquinas, `netstat`/`ss` contra la propia.
- iptables: cadenas PREROUTING/INPUT/FORWARD/POSTROUTING/OUTPUT; tablas raw/nat/filter/mangle. Entrada=PREROUTING+INPUT; Salida=OUTPUT+POSTROUTING; Router=PREROUTING+FORWARD+POSTROUTING (requiere `ip_forward=1`). SNAT/MASQUERADE cambian origen; DNAT cambia destino; DROP silencioso vs REJECT con ICMP.
- Seguridad: `/etc/passwd`(info)+`/etc/shadow`(hash, `!`=bloqueada)+`/etc/group`. root=UID 0, usuarios desde 1000. `sudo` ejecuta como otro usuario; `su -` carga entorno. `ulimit`(soft≤hard) y `cgroups`(usado por Docker) limitan recursos. SELinux (NSA) securiza.
- CUPS: IPP sobre HTTP:631, LPD TCP:515 (desuso).
- Shell: BASH/CSH/KSH/ZSH... Scripting `.sh`, `#!/bin/sh`, `$0 $1 $$ $* $#`. X-Window: servidor X = máquina usuario, cliente X = donde vive la app; evoluciona a Wayland.

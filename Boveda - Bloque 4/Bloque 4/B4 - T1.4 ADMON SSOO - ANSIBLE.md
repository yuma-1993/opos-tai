# Tema 1.4 · Bloque 4 — Administración de Sistemas Operativos: Ansible

> [!abstract] De qué va este tema
> Laboratorio práctico de Ansible: los ficheros de configuración concretos (`ansible.cfg`, inventario de hosts, `group_vars`), ejemplos de comandos ad-hoc (modo imperativo) y un playbook completo de ejemplo (modo declarativo) que instala Apache. Es la cuarta práctica de la serie de administración de sistemas, y complementa la introducción teórica de Ansible ya vista en [[B4 - T1.1 ADMON SSOO]] (agentless, solo SSH, inventario en `/etc/ansible/hosts`, Playbooks en YAML) con ficheros y comandos concretos y ejecutables.

---

## 1. Ficheros de configuración

### 1.1 `ansible.cfg` — configuración global

```ini
[defaults]
inventory = /etc/ansible/hosts
```

> [!note] Ampliación (conocimiento general, no viene del PDF)
> `ansible.cfg` es el fichero de configuración global de Ansible. Aquí solo se ve una directiva (`inventory`), que le dice a Ansible dónde está el fichero de inventario por defecto — precisamente la ruta `/etc/ansible/hosts` que ya se menciona en [[B4 - T1.1 ADMON SSOO]]. Si no se especifica, Ansible ya asume esa ruta por defecto; declararla aquí explícitamente sirve para dejarlo documentado o para apuntar a una ruta distinta.

### 1.2 Inventario de hosts (`/etc/ansible/hosts`)

```bash
[group_name]
alias ansible_ssh_host=your_server_ip
```

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Esta es una plantilla: `[group_name]` se sustituye por el nombre real del grupo (por ejemplo `labservers`, el que se usa más abajo en el playbook), `alias` por un nombre cualquiera que le quieras dar a ese host dentro del inventario, y `ansible_ssh_host` es la variable que le dice a Ansible a qué IP/hostname conectarse realmente cuando se invoque ese alias. Es el mecanismo que permite usar nombres cortos y legibles en los playbooks aunque el host real tenga otra IP.

### 1.3 `group_vars` — variables por grupo

Fichero: `/etc/ansible/group_vars/labservers`

```yaml
---
ansible_ssh_user: root
```

> [!note] Ampliación (conocimiento general, no viene del PDF)
> El nombre del fichero dentro de `group_vars/` tiene que coincidir con el nombre del grupo del inventario (`labservers`) — así Ansible sabe que esas variables aplican a todos los hosts de ese grupo. Aquí la variable `ansible_ssh_user: root` le dice a Ansible que se conecte como usuario `root` por SSH a todos los hosts del grupo `labservers`, sin tener que repetirlo host a host ni pasarlo en cada comando. Esto solo funciona sin pedir contraseña si ya hay acceso SSH sin contraseña configurado como root (`ssh-copy-id`), como se documenta en [[B4 - T1.2 ADMON SSOO - SSH]].

> [!important] Idea clave
> Los tres ficheros trabajan juntos: `ansible.cfg` apunta al inventario, el inventario (`/etc/ansible/hosts`) define los grupos y hosts, y `group_vars/<grupo>` define variables (como el usuario SSH) que se aplican automáticamente a todo ese grupo.

## 2. Comandos ad-hoc (modo imperativo)

| Comando | Qué hace |
|---|---|
| `ansible all -m ping` | `-m` para usar un módulo determinado (aquí, `ping`) |
| `ansible all -m shell -a 'df -h'` | `-a` para pasar argumentos al módulo. Hace un `df -h` en todos los nodos → **imperativo** |
| `ansible all -a "uname -a"` | Usa el módulo por defecto, `command` |
| `ansible all -m apt -a "name=vim"` | Instala `vim` en todos los servidores (mismo gestor de paquetes [[B4 - T1.1 ADMON SSOO\|apt]] documentado en T1.1) |
| `ansible all -m file -a "dest=/var/www/prueba mode=644 state=directory"` | Crea un directorio |
| `ansible-playbook apache.yml` | Ejecuta un playbook sobre server1 |

> [!important] Idea clave para el examen
> `-m` selecciona el módulo a usar (`ping`, `shell`, `apt`, `file`...); `-a` pasa argumentos a ese módulo. Si no se indica módulo con `-m`, Ansible usa por defecto el módulo `command`.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Estos comandos `ansible ...` (sin playbook) son el modo **ad-hoc**: una única tarea suelta, lanzada directamente desde la línea de comandos, sin guardarla en ningún fichero. Es el equivalente a escribir una sola tarea de un playbook pero de forma imperativa e inmediata — típico para comprobaciones rápidas (`ping`, `uname -a`) o cambios puntuales, no para configuraciones repetibles que se quieran versionar.

> [!note] Aclaración sobre la fuente
> El propio PDF anota `ansible-playbook apache.yml (ejecuta un playbook sobre server1)`, mientras que el playbook de la sección siguiente declara `hosts: labservers`. Son dos nombres distintos (`server1` vs `labservers`) en la misma fuente — lo dejo tal cual, sin resolver la discrepancia, para no perder información del original.

## 3. Playbooks (modo declarativo)

### 3.1 Ejemplo: instalar Apache

```yaml
---
- name: Playbook to install Apache
  hosts: labservers
  become: true
  user: root
  tasks:
    - name: Ansible apt install Apache
      apt:
        name: apache2
        state: present
```

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Frente a los comandos ad-hoc de la sección 2 (imperativos: "haz esto ahora"), un playbook es **declarativo**: describe el estado final que quieres (`apache2` presente) y es Ansible quien decide si hace falta hacer algo o no. Si `apache2` ya está instalado, ejecutar este playbook de nuevo no vuelve a instalarlo ni da error — simplemente no cambia nada (idempotencia). `become: true` + `user: root` indican que las tareas se ejecutan con privilegios de root en el nodo remoto. Este playbook instala el paquete que luego se configura en detalle en [[B4 - T1.3 ADMON SSOO - APACHE]] (activación de sites/módulos, VirtualHost, SSL). Es la misma distinción abstracta "qué quieres" (declarativo) vs "cómo obtenerlo" (procedimental/imperativo) que aparece en [[Álgebra relacional vs Cálculo relacional]], aplicada aquí a la gestión de configuración en vez de a consultas de bases de datos.

### 3.2 Estados del módulo `apt`

Con `state:` se manejan estados:

| Grupo de estados | Efecto |
|---|---|
| `present` / `installed` / `latest` | Instalar un paquete |
| `absent` / `remove` | Eliminar un paquete |

> [!important] Idea clave
> `present` e `installed` dejan el paquete instalado en cualquier versión disponible ya presente; `latest` fuerza además a que sea la versión más reciente del repositorio. `absent` y `remove` lo desinstalan. Son grupos de alias entre sí, no cuatro comportamientos distintos.

## 🔑 Resumen ultra-rápido

- `ansible.cfg` → `[defaults] inventory = /etc/ansible/hosts` (apunta al inventario).
- Inventario (`/etc/ansible/hosts`): `[group_name]` + `alias ansible_ssh_host=ip`.
- `group_vars/<grupo>`: variables aplicadas a todo un grupo (ej. `ansible_ssh_user: root`).
- Ad-hoc (imperativo): `ansible all -m <módulo> -a "<args>"`. Sin `-m`, módulo por defecto = `command`.
- Ejemplos ad-hoc: `ping` (conectividad), `shell`/`command` (ejecutar comandos), `apt` (instalar paquetes), `file` (crear directorios/ficheros).
- Playbook (declarativo): `ansible-playbook fichero.yml`. Estructura: `name`, `hosts`, `become`, `user`, `tasks` (lista de `name` + módulo).
- Módulo `apt` + `state`: `present`/`installed`/`latest` = instalar; `absent`/`remove` = eliminar.

# Tema 1.2 · Bloque 4 — Administración de Sistemas Operativos: SSH

> [!abstract] De qué va este tema
> Laboratorio práctico de SSH: instalación del paquete, ficheros de configuración (servidor, cliente, claves de host y de usuario), y el conjunto de comandos principales del ecosistema SSH — generación y gestión de claves (`ssh-keygen`, `ssh-copy-id`, `ssh-agent`/`ssh-add`), conexión remota (`ssh`, incluidos túneles) y transferencia de ficheros (`scp`, `sftp`). Es la continuación práctica de la fila "Red" de comandos de administración de Linux vista en [[B4 - T1.1 ADMON SSOO]].

## 1. Instalación

| Comando | Qué instala |
|---|---|
| `apt install openssh-server` | Solo el servidor |
| `apt install ssh` | Cliente y servidor |

Ver [[Gestores de paquetes (apt, yum, dpkg, rpm)]] para el resto de gestores de paquetes de Linux (apt/yum, dpkg/rpm).

## 2. Ficheros de configuración

### 2.1 Servidor: `/etc/ssh/sshd_config`

| Directiva (ejemplo del PDF) | Valor |
|---|---|
| `Port` | 22 |
| `ListenAddress` | 192.168.0.22 |
| `PermitRootLogin` | no |
| `PasswordAuthentication` | no |
| `AllowUsers` | user1,user2 |
| `AllowGroups` | sshmembers |
| `ClientAliveInterval` | 300 (timeout en segundos) |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> El PDF no explica el significado de cada directiva salvo `ClientAliveInterval` (que trae su propia aclaración "timeout en segundos"). Añado el significado habitual de las demás porque ayuda a fijarlas: `Port` es el puerto de escucha (cambiarlo del 22 por defecto es una medida de "seguridad por oscuridad", no una protección real); `ListenAddress` restringe a qué IP local se pega el demonio; `PermitRootLogin no` impide iniciar sesión directamente como root (hay que entrar como usuario normal y escalar con `su`/`sudo`); `PasswordAuthentication no` obliga a autenticarse por clave pública, desactivando el login por contraseña; `AllowUsers`/`AllowGroups` son listas blancas de quién puede conectarse, incluso si tiene credenciales válidas — son los mismos usuarios y grupos que se gestionan con `useradd`/`groupadd` (ver [[B4 - T1.1 ADMON SSOO]]).

### 2.2 Cliente: `/etc/ssh/ssh_config`

- Fichero de configuración del lado cliente (sin directivas de ejemplo en el PDF).

### 2.3 Ficheros de claves y de hosts conocidos

- **`~/.ssh/authorized_keys`**: fichero con las claves públicas de los clientes autorizados a conectarse. Está en el servidor a administrar.
- **`~/.ssh/known_hosts`**: fichero con los fingerprints de las claves públicas de los servidores a los que nos hemos conectado. Servidor central.

Ver [[authorized_keys vs known_hosts]] para la comparación completa entre ambos ficheros.
- **`/etc/ssh/ssh_host_rsa_key`** (autenticación del host).
- **`/etc/ssh/ssh_host_dsa_key`** (ídem).
- **`/etc/ssh/ssh_host_ecdsa_key`** (ídem).

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Estas claves de host (`ssh_host_*_key`) no son las mismas que la clave de usuario (`id_rsa`/`id_rsa.pub`, ver más abajo). Las claves de host identifican al **servidor** ante los clientes — son las que generan el fingerprint que ves la primera vez que te conectas a una máquina ("The authenticity of host X can't be established...") y que se guarda en `known_hosts`. Las claves de usuario (`id_rsa`/`id_rsa.pub`) identifican a la **persona** que se conecta, y son las que se copian a `authorized_keys` del servidor destino con `ssh-copy-id`. Son dos mecanismos de autenticación distintos: uno autentica el servidor frente a ti, el otro te autentica a ti frente al servidor. Comparación completa en [[Claves de host vs claves de usuario (SSH)]].

## 3. Comandos principales

### 3.1 Generación y gestión de claves

Ver [[Comandos de gestión de claves SSH (ssh-keygen, ssh-copy-id, ssh-agent, ssh-add, ssh-keyscan)]] para el detalle de cada comando.

| Comando | Qué hace |
|---|---|
| `ssh-keygen -t rsa/dsa/ecdsa -b numero_bits_clave` | Genera un par de claves |
| `ssh-keygen -l -f ssh_host_ecdsa_key.pub` | Muestra el fingerprint de esa clave |
| `ssh-copy-id username@remote_host` | Copia la clave pública al servidor donde queremos conectarnos |
| `ssh-agent` | Agente de autenticación |
| `ssh-add` | Añade claves privadas al agente de autenticación |
| `ssh-keyscan` | Recopila claves públicas de ciertos hosts |

- **`ssh-copy-id`**: para poblar el fichero `authorized_keys` copias tu clave pública a los servidores a los que te quieres conectar con esa clave. Te llevas el fichero `id_rsa.pub` del origen a los destinos. A partir de ahí, cuando hagas `ssh root@ip_host` no pedirá credenciales — este acceso sin contraseña es precisamente el prerrequisito que usa una herramienta *agentless* como Ansible (ver [[B4 - T1.1 ADMON SSOO]]; ejemplo concreto con `ansible_ssh_user: root` en [[B4 - T1.4 ADMON SSOO - ANSIBLE]]).
- **`ssh-agent`**: sirve para evitar tener que teclear la passphrase cada vez.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> La passphrase que menciona el PDF para `ssh-agent` no es la contraseña del usuario remoto: es la contraseña opcional con la que se puede cifrar la propia clave privada (`id_rsa`) en el disco local. Sin `ssh-agent`, si la clave privada tiene passphrase, se pediría en cada conexión SSH aunque la autenticación por clave ya esté configurada; `ssh-agent` la mantiene descifrada en memoria durante la sesión tras pedirla una única vez, y `ssh-add` es el comando que se la "entrega" al agente.

### 3.2 Conexión remota: `ssh`

| Comando | Qué hace |
|---|---|
| `ssh username@remote_host` | Conecta al host e inicia sesión interactiva remotamente. Pedirá la contraseña si no se ha registrado la clave pública |
| `ssh -l username remote_host` | Conectar al host e iniciar una sesión interactiva remotamente (sintaxis alternativa) |
| `ssh username@remote_host comando` | Ejecuta un comando remotamente |
| `ssh -p puerto username@remote_host comando` | Conecta a un puerto diferente al 22 |
| `ssh -A` | Estando conectado a un servidor, si quieres conectarte a otro, esta opción transmite las credenciales |

### 3.3 Túneles SSH

Ver [[Túneles SSH (-L y -R)]] para el detalle de ambos tipos de túnel.

- **`ssh -L your_port:site_or_IP_to_access:site_port username@host`** (túnel local): crea el SSH en tu máquina conectándote a servicios al puerto `your_port` y se redirige al puerto `site_port`. Hacemos túneles para ocultar servicios; se crea un canal seguro para acceder a otros servicios.
- **`ssh -R remote_port:site_or_IP_to_access:site_port username@host`** (túnel remoto): el puerto `remote_port` es de otra máquina y nos redirige al puerto `site_port`.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> La diferencia práctica entre `-L` y `-R` es hacia dónde apunta el reenvío: con `-L` (local) el puerto que abres está **en tu máquina** y el tráfico sale hacia el servidor remoto (útil para acceder tú a un servicio que solo es visible desde el servidor). Con `-R` (remoto) el puerto que se abre está **en el servidor remoto** y el tráfico entra hacia tu máquina (útil para exponer un servicio tuyo, local, a través de un servidor que sí es accesible desde fuera — por ejemplo, para saltarte un NAT).

### 3.4 Transferencia de ficheros: `scp` y `sftp`

Ver [[scp y sftp (transferencia de ficheros por SSH)]] para el detalle de ambos comandos.

```
scp [other options] [source username@IP]:/[directory and file name] [destination username@IP]:/[destination directory]
scp your_username@remotehost.edu:foobar.txt /some/local/directory
scp foobar.txt your_username@remotehost.edu:/some/remote/directory
```

| Opción | Qué hace |
|---|---|
| `-r` | Copia recursiva |
| `-p` | Conserva los tiempos de modificación iniciales y los atributos del archivo |
| `-l` | Limita el ancho de banda usado (Kbit/s) |

- **`sftp`**: copia remota similar a `scp`.

## 4. Seguridad del canal: claves RSA

> [!important] Base de la seguridad de SSH
> La capacidad de securización del canal de SSH se basa en que se han generado claves públicas y privadas, claves RSA. Cuando instalas SSH te crea 2 ficheros: `~/.ssh/id_rsa` (clave privada) y `~/.ssh/id_rsa.pub` (clave pública). Ver [[Criptografía asimétrica (clave pública y privada)]] para el mecanismo completo.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Esto es criptografía asimétrica: cada usuario tiene un par de claves matemáticamente relacionadas, pero solo la privada puede quedarse en tu máquina (nunca se comparte) y la pública es la que se distribuye y se copia a `authorized_keys` en cada servidor al que quieres acceder sin contraseña. El servidor, al recibir tu petición de conexión, te reta a demostrar que tienes la clave privada correspondiente a una de las públicas que tiene registradas — sin que la privada viaje nunca por la red. El PDF menciona RSA como algoritmo por defecto, pero el propio comando `ssh-keygen` también admite DSA y ECDSA (ver la sección de ficheros de configuración, donde aparecen las tres variantes para las claves de host).

> [!note] Ver también
> Apache usa un esquema de clave pública/privada distinto y para otro propósito: certificados TLS (`SSLCertificateFile`/`SSLCertificateKeyFile`) para cifrar el tráfico HTTP de un sitio web público, frente a las claves RSA de SSH que autentican una sesión de administración remota. Comparación completa en [[B4 - T1.3 ADMON SSOO - APACHE]].
>
> SaltStack resuelve un problema de confianza equivalente (establecer confianza antes de poder ejecutar nada remotamente) con su propio mecanismo de claves entre master y minion (`salt-key -L`/`-A`), en vez de con claves RSA de SSH. Detalle en [[B4 - T1.5 ADMON SSOO - SALTSTACK]].

## 🔑 Resumen ultra-rápido

- Instalación: `openssh-server` (solo servidor) vs `ssh` (cliente + servidor).
- `sshd_config` (servidor): `Port`, `ListenAddress`, `PermitRootLogin no`, `PasswordAuthentication no`, `AllowUsers`/`AllowGroups`, `ClientAliveInterval` (timeout).
- `authorized_keys` (servidor, claves públicas de clientes admitidos) vs `known_hosts` (cliente, fingerprints de servidores ya visitados).
- Claves de host (`ssh_host_rsa/dsa/ecdsa_key`, identifican al servidor) ≠ claves de usuario (`id_rsa`/`id_rsa.pub`, identifican a la persona).
- `ssh-keygen` genera el par de claves; `ssh-copy-id` lo despliega en `authorized_keys` remoto; `ssh-agent` + `ssh-add` evitan repetir la passphrase; `ssh-keyscan` recopila claves públicas de hosts.
- `ssh -p` cambia de puerto; `ssh -A` reenvía credenciales al saltar a un segundo servidor.
- Túnel `-L` (local): puerto abierto en tu máquina, tráfico hacia el remoto. Túnel `-R` (remoto): puerto abierto en el servidor remoto, tráfico hacia tu máquina.
- `scp` (copia punto a punto, `-r`/`-p`/`-l`) y `sftp` (similar a `scp`) para transferencia de ficheros.
- La seguridad del canal se basa en claves RSA asimétricas (pública/privada); la privada nunca sale de tu máquina.

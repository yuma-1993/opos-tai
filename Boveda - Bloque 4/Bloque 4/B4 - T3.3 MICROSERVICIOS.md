# Tema 3.3 · Bloque 4 — Microservicios

> [!abstract] De qué va este tema
> Los microservicios (μs) son servicios independientes, muy débilmente acoplados y modelados alrededor de un dominio de negocio, ideales para desplegar en contenedores. El tema recorre sus ventajas y retos (DDD, Bounded Context), cómo se comunican (síncrono, asíncrono, RPC, REST...), las dos generaciones de infraestructura de apoyo (API Gateway v1.0 y Service Mesh v2.0), cómo se resuelven los datos sin ACID (CQRS, 2PC, SAGA) y, por último, orquestación, despliegue, tests, observabilidad, seguridad, resiliencia y escalado.

---

## 1. Concepto y características

Los **contenedores son ideales para las arquitecturas de μs** (ver [[B4 - T3.2.1 VIRTUALIZACION]]). Son servicios que pueden ser **desplegados de manera independiente** y que se modelan **alrededor de un dominio de negocio**.

| Característica | Explicación |
|---|---|
| Tamaño | "μ" **no** significa muy pequeño: el tamaño lo dictará el **servicio que preste** |
| Cajas negras | Tienen una funcionalidad definida y producen un resultado |
| Tipo de arquitectura | Son un **tipo de SOA** — ver [[SOA (arquitectura orientada a servicios)]] |
| Acoplamiento | **Muy débilmente acoplados** |
| Granularidad | **Muy fina** (poca responsabilidad) |
| Comunicación | Mediante **protocolos ligeros** (http) |
| Equipos | **Equipos de desarrollo independientes** |
| Tecnología | Pueden definirse en **diferentes lenguajes** y con **distintas BD**. Cada μs puede tener su BD (100 % independiente) |
| Resiliencia | Si falla un μs **no se viene abajo toda la app** |

> [!important] Idea clave
> No todo funciona mejor con μs. Son un tipo de SOA, con granularidad muy fina y cada μs con su propia BD (100 % independiente).

### 1.1 Nuevos retos y nuevos problemas

| Retos (positivos y de diseño) | Nuevos problemas |
|---|---|
| Independientemente **desplegables** | **Latencia** |
| **Distribución de responsabilidad** | **Fallos de red** |
| Independientemente **escalables** | **Consistencia de datos** |
| **Acoplamiento y cohesión** | **Sobrecarga de operaciones** |
| **Mezcla de tecnologías** | **Resolución de problemas** |
| **Gobernanza**: gestionar los μs es complejo, por eso hay orquestadores, patrones de diseño específicos, transaccionalidad, dependencias, etc. | **Muchas opciones a elegir** |

### 1.2 DDD y Bounded Context

- **DDD (Domain Driven Design)**: intenta descubrir los conceptos del negocio desde varios puntos de vista, permitiéndonos definir **servicios, entidades y repositorios**.
- **Bounded Context**: patrón de diseño que **divide el modelo en submodelos, especializados en áreas**. Cada μs tendrá un Bounded Context asociado: se encargará de una funcionalidad del negocio, de un contexto, de un área de negocio. **Es mejor segregar.**
- Ejemplo del PDF: la clase **compra** del contexto A tendrá unos atributos diferentes de la del contexto B. Se relaciona con **SOLID (segregación de interfaces)** — ver [[SOLID (principios)]] e [[Interface Segregation Principle (ISP)]].

> [!note] Esquema del PDF (diagramas de ejemplo)
> Tres diagramas sucesivos con las mismas entidades (Persona, Compra, Pago, Factura, Producto, Categoría, Dirección, Tipo Pago, Cliente, Visitante):
> 1. **Diagrama de flujo**: Persona → Compra → Pago → Factura; Compra → Producto → Categoría.
> 2. **Diagrama de clases**: añade Dirección, Tipo Pago y la especialización de Persona en **Cliente** y **Visitante**.
> 3. **Bounded Context**: el modelo se parte en **Bounded Context A** (Dirección, Persona, Compra, Cliente, Visitante) y **Bounded Context B** (Compra, Tipo Pago, Pago, Factura, Producto, Categoría), separados por un **límite de contexto**. La entidad Compra aparece en ambos con atributos distintos.

## 2. Arquitectura

### 2.1 Comunicación entre μs

| Tipo | Detalle |
|---|---|
| **Síncrona** | **Mala**, porque dependes del **eslabón más débil** |
| **Asíncrona — Petición-Respuesta** | **Basado en colas. Es transaccional.** Usa **brokers de mensajes**: intermediarios entre μs para una comunicación asíncrona (**colas de mensajes / Topics**). **Entrega garantizada. Confianza. Transaccionalidad.** Productos: **Apache Kafka**, **RabbitMQ**, **Apache ActiveMQ**, **Google Cloud Pub/Sub** — ver [[Apache Kafka]] |
| **Asíncrona — Dirigida por eventos** | Genero un **evento** con info y mis **suscriptores (Topic)** usan el evento y la info como **inicio de su trabajo** — ver [[Event-Bus Pattern]] |
| **Asíncrona — Datos compartidos** | **No es la más típica.** Subes un fichero a la nube, notificas a los interesados y podrán consumirlo cuando lo necesiten. Pueden usarse **volúmenes de un contenedor, NAS/S3 o BBDD** en modelos con segregación de responsabilidad (**CQRS**) |
| **RPC / gRPC** | **A día de hoy de lo más usado.** **HTTP2. Protocol Buffer.** Generación de código nativa |
| **SOAP** | **Muy usado en la AGE por el ENI** — ver [[B1 - T8 ACCESO ELECTRONICO, ENS Y ENI]] |
| **RMI** | Muy dependiente de la tecnología (**Java**), pero permite aprovechar el conocimiento previo del equipo |
| **GraphQL** | **Agregador de consultas** con capacidades de filtrado. **Resolver, Queries y Mutations** |
| **REST** | **A día de hoy de lo más usado.** **HTTP 1.1. XML + JSON.** Generación de código con **OpenAPI / Swagger** |

> [!important] gRPC vs REST
> Ambos son "de lo más usado a día de hoy". **gRPC**: HTTP/2 + Protocol Buffer + generación de código nativa. **REST**: HTTP 1.1 + XML/JSON + generación de código con OpenAPI/Swagger. **SOAP** = AGE/ENI. **RMI** = Java. **GraphQL** = agregador de consultas (Resolver, Queries, Mutations).

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Un *broker* como Kafka o RabbitMQ es la implementación práctica del patrón de bus de eventos que ya aparece en [[Event-Bus Pattern]] y, en el estilo SOA clásico, en el [[ESB (Enterprise Service Bus)]]. En el ecosistema Big Data, Kafka también sincroniza Hadoop y NoSQL (ver [[Persistencia políglota]]).

### 2.2 API Gateway (v1.0)

- **Puerta de entrada a los μs, aislándolos del exterior.** Productos liberados por **Netflix**.
- **Zuul** es el primer producto que hace de **proxy inverso**, canalizando peticiones y ocultando la complejidad de los μs. Zuul se **replica muchas veces** para que no caiga todo en caso de fallo.
- **API Gateway es un patrón de diseño** que **centraliza la lógica de acceso** a los μs que están detrás. Esta versión tiene **mucha complejidad** para gestionar los μs.

> [!note] Esquema del PDF (diagramas del API Gateway y de Zuul)
> **API Gateway**: clientes (Web UI en Angular, app iOS, app Android) → **API Gateway** → servicios (Inventory Service con MySQL, Shipping Service con MongoDB, Account Service con MySQL), cada uno con su propia base de datos.
> **Zuul**: `Zuul` (con `Ribbon` y `Hystrix`) → `Microservicio A` y `Microservicio B` (cada uno con `Ribbon` y `Hystrix`, y varias instancias replicadas) ↔ `Eureka Server` y `Cloud-Config`.

| Componente (Netflix) | Función |
|---|---|
| **Zuul** | API Gateway / Edge Service (proxy inverso) |
| **Ribbon** | Librería para **balancear** peticiones de clientes |
| **Hystrix** | Librería de **errores en cascada** usando el patrón **Circuit Breaker** |
| **Eureka** | Servidor para **registrar μs y sus metadatos** |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Un API Gateway funciona como un proxy inverso delante de los servicios; el patrón estructural genérico de "intermediario que oculta el objeto real" está en [[Proxy (patrón GoF)]].

**Patrón Circuit Breaker**: cuando un μs llama a otro y éste a otro, si alguno falla, hace que **no se caiga todo**. Permite definir **política de reintentos y timeout**. **Corta el acceso al μs erróneo** de cara a futuras llamadas por otros μs e implementa una **política de restauración** para ese μs. (Se amplía en la sección 6, Resiliencia.)

### 2.3 Service Mesh (v2.0)

- Tecnología diseñada para abordar las **complejidades de las arquitecturas de μs**.
- Solo tienes que instalar el producto **Istio** (podría ir en un contenedor) y **Envoy** (que es el **proxy**, la implementación del **patrón sidecar**). **Istio habla con los Envoy.** Centraliza las peticiones de los proxys.
- **Service Mesh = Istio + Envoy.** Es como un **framework**: hace el "trabajo sucio" a los μs para que solo te preocupes de la **lógica de negocio**, no de la arquitectura. Hay un **plano de control** donde se solucionan problemas de chequeo de políticas de seguridad, métricas, etc. Los proxys se comunican entre ellos.
- **Patrón sidecar**: te ayuda dialogando con otra parte de la arquitectura llamada Service Mesh.

> [!note] Esquema del PDF (diagrama)
> Dos servicios (`svc A`, `svc B`) en la **capa de aplicación (lógica de negocio)**, cada uno acompañado de su **sidecar-proxy Envoy** (intercepción de llamadas de red); por debajo, el **plano de control de Istio** (Mixer, Pilot, Istio-Auth) con servicios proporcionados por **Kubernetes**.

| Función | Qué aporta | Productos |
|---|---|---|
| **Abstracción** | Abstrae a los desarrolladores de los problemas de arquitectura: **discovery; balanceo de carga; recuperación** | **Envoy** |
| **Centralización** | Se crea un **punto centralizado** para controlar las funciones de los μs en una aplicación | **Istio**, **Linkerd** |
| **Trazabilidad** | Centralizamos y mostramos trazas asociadas con una sola solicitud entre múltiples servicios: **distributed tracing; monitorizar transacciones distribuidas; análisis de Root Cause**. **Id único** para cada traza | **Jaeger**, **Spring Cloud Sleuth** (distributed tracing) |
| **Observabilidad** | Observaciones y telemetría sobre los μs: **salud; topología; métricas; dashboards; configuración** | **elasticsearch** (logs), **Grafana** (dashboard), **kiali**, **Prometheus** (métricas) |
| **Seguridad** | **Cifrado; autenticación; autorizaciones** | **keycloak**: gestión de identidades con **SSO** (Java) |

> [!important] API Gateway (v1.0) vs Service Mesh (v2.0)
> API Gateway = puerta de entrada que aísla del exterior (Zuul, proxy inverso), centraliza el acceso, **mucha complejidad** de gestión. Service Mesh = **Istio + Envoy** (sidecar), plano de control que resuelve discovery, balanceo, recuperación, trazabilidad, observabilidad y seguridad. **Es bastante habitual combinar API Gateway y Service Mesh.**

> [!note] Esquema del PDF (combinación)
> Diagrama con un **API Gateway** a la entrada y varios nodos **Mesh** interconectados detrás.

## 3. Bases de datos

No podemos asegurar **ACID** por ser un sistema **altamente distribuido** (ver [[ACID (transacciones)]]). Por eso hay **3 patrones**:

| Patrón | Descripción |
|---|---|
| **CQRS** (*Command and Query Responsibility Segregation*) | **CRUD**: la mayor parte de las operaciones son de lectura (R); el resto son de creación (C), actualización (U) y borrado (D). Por eso **dividimos el μs en 2: R y CUD** |
| **2PC** (*Two-Phase Commits*) — transacciones distribuidas | **Fase de Voting y fase de Commit.** **No suele usarse por ser muy costoso** — ver [[Transacciones distribuidas (Two-Phase Commit, Monitor Transaccional)]] |
| **SAGA** | Algoritmo que coordina múltiples cambios en estados, **evitando bloquear recursos por largos periodos de tiempo**. Separamos una **LLT** (*Long Lived Transaction*) en una **secuencia de transacciones independientes**. Si hay fallos podemos **reintentar o hacer rollback**. Se gobierna con **Orquestador o Coreógrafo**. Como es difícil hacer rollback, se guarda una **tx compensatoria**: en lugar de hacer rollback en todos los μs, **mandamos a todos los μs la tx compensatoria** |

> [!note] Esquema del PDF (diagrama CQRS Pattern)
> A la izquierda: la `UI` se comunica con un **Query Service** (Query Model, que **lee**) y un **Command Service** (Command Model, que **escribe**), ambos sobre el mismo `Storage`. A la derecha: un balanceador de carga (*Load balancer*) reparte entre instancias de pedidos (*Order instance*); las **lecturas** van a **réplicas de lectura** (*Read replica*) y las **escrituras** al **nodo primario** de la BD (*Primary DB node*), con replicación en segundo plano (*Background replication*).

> [!important] 3 patrones sin ACID
> **CQRS** (separar lectura R de escritura CUD) · **2PC** (voting + commit, costoso, poco usado) · **SAGA** (LLT dividida en transacciones independientes + **transacción compensatoria** en lugar de rollback; orquestador o coreógrafo).

## 5. Orquestación, despliegue y operación

### 5.1 Orquestación

| Concepto | Definición |
|---|---|
| **Nodo** | Elemento del clúster que puede albergar **pods** en su interior |
| **Clúster** | Agrupación de nodos a orquestar. **Al menos 1 master y 1 worker** |
| **Pod** | Conjunto de **uno o más contenedores** |
| **Servicio** | Conjunto de pods a los que enviamos tráfico (**ingress**) |
| **Volumen** | Directorio con datos accesibles a los contenedores del pod |
| **Namespace** | **Clúster virtual** o partición de nuestro clúster |

Productos: **Docker Swarm** y **Kubernetes** (ver [[B4 - T3.2.1 VIRTUALIZACION]] y el laboratorio [[B4 - T3.2.2 VIRTUALIZACION - DOCKER]]).

### 5.2 Despliegue

| Principio | Explicación |
|---|---|
| **Ejecución aislada** | Ejecuta los μs de forma aislada, con sus recursos computacionales, y que su ejecución **no impacte a otros μs cercanos** |
| **Automatización** | Según crezca el número de μs, la automatización cobra mayor importancia (**CI/CD, DevOps**) — ver [[DevOps]] |
| **IaC** | Representa la configuración de tu infraestructura para facilitar los despliegues. Se usa **control de versiones** — ver [[IaC (Infrastructure as Code)]] |
| **Despliegues Zero-Downtime** | Intenta desplegar μs **sin tener downtime** para los usuarios o para tu servicio |
| **Estados deseados** | **Declarativo.** Usa una plataforma que mantenga los μs en un estado definido, lanzando nuevas instancias si fuese necesario |

### 5.3 Modos de despliegue

| Modo | Descripción | Ejemplos |
|---|---|---|
| **Máquina física** | La instancia del μs se ejecuta en una máquina física directamente, **sin virtualización** | — |
| **Máquina virtual** | Se ejecuta en una máquina virtual | — |
| **Contenedor** | Se ejecuta en un contenedor separado, en un host físico o virtual. Puede gestionarse por un orquestador como **k8s** (Kubernetes) | — |
| **Contenedor de aplicaciones** | El μs se ejecuta dentro de un contenedor de aplicaciones que administra otras aplicaciones | **Tomcat**, **WebLogic** |
| **PaaS** | **Instancias administradas**, abstrayéndonos de la gestión inferior y que corren nuestros μs | **Heroku**, **Google AppEngine**, **AWS Beanstalk** |
| **FaaS** | La instancia del μs se despliega como una **función (serverless)** | **AWS Lambda**, **Google Cloud Functions**, **Azure Functions** |
| **KaaS** | **Servicio de orquestación de contenedores en la nube.** Creas contenedores desde repositorios de imágenes y la infraestructura es administrada por el CSP | **Amazon EKS**, **Google GKE**, **Azure AKS** |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> El PDF desarrolla las siglas de **CSP** como "Proveedor de Servicios de Comunicaciones"; en el contexto de KaaS lo habitual es que CSP sea *Cloud Service Provider* (proveedor de servicios en la nube). Se deja la redacción del PDF y se avisa de la posible inexactitud.

### 5.4 Tests

| Tipo de test | Descripción |
|---|---|
| **Unitarios (TDD)** | **Muy importantes en entornos CI/CD** |
| **Servicio** | Se prueba el μs **como un todo**. **Stubs y Mocks** |
| **End-to-End** | **Sistema completo** |

### 5.5 Observabilidad

| Elemento | Descripción |
|---|---|
| **Agregación de logs** | Cada μs tiene sus registros, pero conviene tenerlo todo **recopilado** |
| **Agregación de métricas** | Se capturan constantes de los μs (**cpu, ram, peticiones**), pero también solicitudes, compras o **indicadores del negocio** |
| **Trazas distribuidas** | Hay que saber qué ha ocurrido y **no perder el rastro de una solicitud o una saga** |
| **Alertas** | Con esta información podemos lanzar alertas que incluso emitan eventos para **modificar la infraestructura**. **Evitar la fatiga de alertas** |
| **Pruebas en producción** | **Transacciones sintéticas, Canary, Tests A/B, ejecuciones paralelas, Chaos Engineering** |

### 5.6 Seguridad

Debe formar parte **desde el inicio** del desarrollo. **Service Mesh ofrece muchas de estas funcionalidades** pero hay que tenerlas siempre presentes.

- **Mínimo privilegio posible y alcances limitados**: esta cuenta de servicio solo puede acceder aquí; este servicio se identifica con esta cuenta.
- **Credenciales fuera del código**, en el entorno o en **Secrets Managers**.
- Autenticaciones **S2S**, **OAUTH2**, **TLS**, **JSON Web Token** (sobre TLS ver [[Certificado TLS-SSL (X.509)]]).

## 6. Resiliencia

| Mecanismo | Descripción |
|---|---|
| **Timeouts** | Tiempo permitido a una ejecución hasta que falle, o tiempo que hay que esperar antes de decidir que ha ido mal |
| **Reintentos** | Si algo falla, **no se reintenta inmediatamente**: se aplica **back-off exponencial** y un **número máximo de intentos** |
| **Circuit Breaker** | Si hay un fallo con otro μs: **se detecta, se dejan de enviar peticiones, se recupera y se vuelve a enviar** |
| **Bulkheads** | **No está en el μs que llama, sino en medio, entre los μs.** Se pone delante para no tumbar el μs en caso de muchas llamadas. Son **barreras o protecciones** entre componentes que protegen sus recursos de manera que el fallo de un componente no afecte a otro: **cuotas a nivel de CPU/RAM/persistencia; cuotas de uso de APIs; rate limit de peticiones (DoS)** |
| **Idempotencia** | Propiedad de realizar una acción varias veces y conseguir el **mismo resultado** que si se realizase una sola vez. Relacionado con el patrón **Event Sourcing**. Al haber tantos μs es posible que se **dupliquen eventos**: el productor genera un evento y lo mete en una cola para notificar a los consumidores; si el evento se duplica, **los consumidores no lo procesan 2 veces**. **Apache Kafka** (gestor de colas) |

**Estados del Circuit Breaker** (según el PDF): **básico: abierto y cerrado**. **Cerrado**: cierra el acceso a un μs si después de aplicar la política de reintentos se ve que está caído; de este modo los siguientes μs ni lo intentan. También hay una **política de recuperación** para volver a dejar el acceso en estado **abierto**.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Aviso de terminología: el PDF usa "cerrado" para "acceso cortado" y "abierto" para "acceso restablecido". En la convención más habitual del patrón Circuit Breaker (analogía con un circuito eléctrico) es al revés: **cerrado** = las llamadas pasan con normalidad; **abierto** = el circuito está "disparado" y se cortan las llamadas. Se respeta la redacción de la fuente, pero hay que tenerlo en cuenta por si una pregunta de examen usa la otra convención.

> [!important] Idempotencia en μs
> Misma idea que en la gestión de configuración ([[Idempotencia]]): repetir la operación no cambia el resultado. Aquí evita procesar dos veces un evento duplicado en una cola (Event Sourcing / Kafka).

> [!tip] Truco: resiliencia
> Timeouts (cuánto espero) → Reintentos (back-off exponencial + máximo) → Circuit Breaker (corto el acceso y recupero) → Bulkheads (barreras/cuotas entre μs) → Idempotencia (no duplicar efectos).

## 7. Escalado

| Tipo | Descripción |
|---|---|
| **Vertical** | **Mejorar los recursos**: más memoria, más CPU, más almacenamiento, más ancho de banda |
| **Horizontal** | **Crecemos en instancias**: podemos lanzar nuevos pods o servicios a demanda y bajarlos cuando la demanda ha bajado; también podemos crecer en workers, lo que me permite crecer en instancias |
| **Particionar por datos** | Distribuimos la carga de trabajo haciendo **particiones sobre los datos**: usando una dimensión Apellido, Geografía, etc. (concepto afín a [[Sharding]]) |
| **Descomposición funcional** | Extraemos una funcionalidad **muy demandante** a otro μs, para luego poder escalarlo |

## 🔑 Resumen ultra-rápido

- μs = servicios **independientes**, **muy débilmente acoplados**, granularidad **muy fina**, protocolos **ligeros** (http), equipos y tecnologías/BD independientes, **resiliencia**. Tipo de **SOA**. "μ" no significa pequeño. No todo funciona mejor con μs.
- Retos: despliegue/escalado independiente, acoplamiento y cohesión, gobernanza. Problemas: latencia, fallos de red, consistencia de datos, sobrecarga, diagnóstico.
- **DDD** + **Bounded Context** (un μs = un contexto de negocio; mejor segregar; SOLID/ISP).
- Comunicación: **síncrona** (mala, eslabón más débil); **asíncrona**: petición-respuesta (colas/brokers: Kafka, RabbitMQ, ActiveMQ, Pub/Sub), dirigida por eventos, datos compartidos. **gRPC** (HTTP2, Protocol Buffer) y **REST** (HTTP 1.1, XML+JSON, OpenAPI/Swagger) los más usados; **SOAP** (AGE/ENI); **RMI** (Java); **GraphQL** (Resolver/Queries/Mutations).
- **API Gateway v1.0**: puerta de entrada, proxy inverso. **Netflix**: **Zuul** (gateway), **Ribbon** (balanceo), **Hystrix** (circuit breaker), **Eureka** (registro de μs).
- **Service Mesh v2.0 = Istio + Envoy** (patrón sidecar, plano de control): abstracción (Envoy), centralización (Istio, Linkerd), trazabilidad (Jaeger, Spring Cloud Sleuth), observabilidad (elasticsearch, Grafana, kiali, Prometheus), seguridad (keycloak, SSO). Habitual combinarlo con API Gateway.
- Sin ACID: **CQRS** (R vs CUD), **2PC** (voting + commit, costoso), **SAGA** (LLT → tx independientes; orquestador o coreógrafo; **tx compensatoria**).
- Frameworks: Java (Spring Cloud/Boot, Micronaut, Quarkus, Helidon, Microprofile), Flask, NodeJS, .NET.
- Orquestación: nodo, clúster (≥ 1 master + 1 worker), pod, servicio (ingress), volumen, namespace; Docker Swarm / Kubernetes.
- Despliegue: ejecución aislada, automatización (CI/CD), IaC, zero-downtime, estados deseados (declarativo). Modos: física, virtual, contenedor, contenedor de aplicaciones (Tomcat, WebLogic), PaaS (Heroku, AppEngine, Beanstalk), FaaS (Lambda, Cloud Functions, Azure Functions), KaaS (EKS, GKE, AKS).
- Tests: unitarios (TDD), servicio (stubs y mocks), end-to-end. Observabilidad: logs, métricas, trazas, alertas (evitar fatiga), pruebas en producción (sintéticas, Canary, A/B, paralelas, Chaos Engineering).
- Seguridad: mínimo privilegio, credenciales fuera del código (Secrets Managers), S2S, OAuth2, TLS, JWT.
- Resiliencia: timeouts, reintentos (back-off exponencial + máximo), Circuit Breaker, Bulkheads (entre μs; cuotas, rate limit), idempotencia (Event Sourcing, Kafka).
- Escalado: vertical (más recursos), horizontal (más instancias), particionar por datos, descomposición funcional.

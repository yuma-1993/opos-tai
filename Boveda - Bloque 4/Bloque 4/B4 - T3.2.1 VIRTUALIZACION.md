# Tema 3.2.1 · Bloque 4 — Virtualización

> [!abstract] De qué va este tema
> La virtualización crea, mediante una capa de abstracción software, la posibilidad de multiplexar recursos hardware entre varios clientes; evoluciona de lo físico a lo virtual y a Cloud. Tiene dos grandes familias: la virtualización clásica con **hipervisor** (máquinas virtuales completas, ideal para servicios) y la **virtualización ligera** con **contenedores** (virtualizan el kernel, ideal para aplicaciones; Docker, Kubernetes y el estándar OCI). Termina con las plataformas de servicio (IaaS, PaaS, SaaS, CaaS/KaaS). El laboratorio práctico de comandos está en [[B4 - T3.2.2 VIRTUALIZACION - DOCKER]] y la arquitectura de microservicios que se apoya en contenedores en [[B4 - T3.3 MICROSERVICIOS]].

---

## 1. Concepto de virtualización

- Camino: **FÍSICO → VIRTUAL → CLOUD**.
- Una virtualización es una **abstracción**: algo que no existe pero simula serlo.
- Se crea mediante una **capa de abstracción (SW)**, para una serie de recursos HW (CPU, memoria, red, etc.), incluso del SO, la posibilidad de **multiplexarlos** entre varios clientes. Permite crear **máquinas virtuales** y repartir/multiplexar los recursos HW para que parezca que tenemos varias máquinas (lógicas).
- Ese SW es el llamado **Hipervisor** o **VMM** (*Virtual Machine Monitor*).

| Ventaja de la virtualización | Explicación |
|---|---|
| Optimización del uso del HW | Se aprovecha mejor el hardware |
| **Aislamiento** entre máquinas | Si cae una no afecta a las otras |
| Mejor aprovisionamiento y administración del entorno | Amplías y reduces los recursos **bajo demanda** |

> [!important] Virtualización vs Cloud
> La principal característica de **Cloud** es la **gestión de la demanda y tarificación por consumo**, con sistemas de **autoescalado** por si aumenta la demanda. En la virtualización te podías quedar sin recursos; en Cloud es casi imposible.

## 2. Tipos de virtualización

### 2.1 Virtualización de máquinas

El HW debe tener ciertas características para permitir virtualización:

| Tecnología | Fabricante / función |
|---|---|
| **VT-x** | Intel |
| **VT-d** | Intel — virtualización de **entrada/salida** |
| **VT-c** | Intel — virtualización de **red** |
| **AMD-V** | AMD |

#### Hipervisor tipo 1 vs tipo 2

> [!note] Esquema del PDF (diagrama)
> **Tipo 1**: `MV | MV` (cada una con `APP` y `SO`) → `HIPERVISOR` → `HARDWARE`. Ejemplos: **KVM / Hyper-V / XEN**, **VMware ESX**, **XCP-ng**.
> **Tipo 2**: `MV | MV` (cada una con `APP` y `SO`) → `HIPERVISOR` → `SIST. OPER.` → `HARDWARE`. Ejemplos: **VMware Player**, **VirtualBox**, **Parallels (Mac)**.

| | Tipo 1 | Tipo 2 |
|---|---|---|
| Se sitúa sobre | El **hardware** directamente | Un **sistema operativo** (que a su vez está sobre el HW) |
| Ámbito | Mezcla y optimización del HW y SO del tipo 2, **diseño orientado a la virtualización** | **Doméstico** (menos optimizado) |
| Productos | KVM / Hyper-V / XEN, VMware ESX, XCP-ng | VMware Player, VirtualBox, Parallels (Mac) |

> [!important] Trampa: Hyper-V
> **Hyper-V se instala sobre Windows y parecería que es de Tipo 2, pero se sitúa encima del HW, por debajo del SO** → es de **Tipo 1**.

### 2.2 Virtualización del almacenamiento

| Nivel | Tipo | Técnica |
|---|---|---|
| **Bloque** | De servidor | **LVM** — ver [[LVM (Logical Volume Manager)]] |
| **Bloque** | De dispositivo | **RAID**: la controladora me abstrae — ver [[RAID (Redundant Array of Independent Disks)]] |
| **Bloque** | De red | **SAN, vSAN**: se usan las **LUNs** para abstraerse — ver [[SAN (Storage Area Network)]] y [[LUN y LUN Masking]] |
| **Fichero** | — | **NAS** (NFS / CIFS / AFP) — ver [[NAS (Network Attached Storage)]] |

### 2.3 Virtualización del backup

Emula la interfaz de la **librería de cintas** con **discos** al otro lado (**VTL**, *Virtual Tape Library*). Sobre cintas ver [[LTO (Linear Tape-Open)]] y [[Estrategias de backup (Completa, Incremental, Diferencial)]].

### 2.4 Virtualización del puesto de usuario (escritorio y aplicaciones)

| Tipo | Descripción | Producto |
|---|---|---|
| **Infraestructura VDI** | Herramientas que te crean un **escritorio** | VMware Horizon / Xen Desktop |
| **Virtualización de aplicaciones** | Lo que muestras al usuario es un **acceso**, una interfaz para acceder a la aplicación | Citrix XenApp |

## 3. Formatos y extensiones

| Formato | Significado |
|---|---|
| **VMDK** | Formato de código abierto para almacenamiento de datos de las MV (**VMware**) |
| **OVF** | *Open Virtualization Format*. Para **distribuir** MV (*Virtual Appliance*) |
| **OVA** | *Open Virtualization Appliance*. Es un **OVF empaquetado en TAR** |
| **VMEM** | **Volcado de la memoria principal** de la MV cuando se pausa |
| **VDI** | Imágenes de **VirtualBox** de Oracle |
| **VHD** | Almacenamiento de **Hyper-V** |

> [!tip] Truco
> OVF = descriptor para distribuir; OVA = OVF + TAR (un único fichero). VMDK → VMware; VDI → VirtualBox; VHD → Hyper-V; VMEM → memoria al pausar.

## 4. Virtualización ligera (contenedores)

- Ideal para **aplicaciones**. La virtualización **clásica** es para **servicios**, como Oracle, Correo, DNS, etc.
- **No existe hipervisor**: se sustituye por una capa de acceso al **kernel / gestor de contenedores**.
- Se virtualiza el **SO (kernel)** y se crean **contenedores** o **EV (Entorno Virtual)**. Dentro del contenedor hay **parte del SO, las utilities (paquetería básica), pero no el kernel**.
- Los contenedores ejecutan cosas **pequeñas, ligeras**, por eso son **fáciles de distribuir**. Hay contenedores Linux, Windows y Mac. El contenedor es una virtualización del kernel, sobre el que se le instalan las apps.
- Productos: **Docker** (fue el primero), **Podman**, **RKT**, **Mesos**, **LXC**, **OpenVZ**.
- Los contenedores **no están pensados para consumirse por humanos**, sino para alojar un **servicio que sea distribuido en muchos hosts**.

> [!note] Esquema del PDF (diagrama comparativo)
> **Contenedores**: `App A … App F` → `Docker` → `Host Operating System` → `Infrastructure`.
> **Máquinas virtuales**: `App A / App B / App C`, cada una con su `Guest Operating System` → `Hypervisor` → `Infrastructure`.

| | Máquina virtual (hipervisor) | Contenedor |
|---|---|---|
| Qué se virtualiza | HW (cada MV con su SO invitado completo) | **El kernel** (SO compartido del host) |
| Capa intermedia | Hipervisor | Capa de acceso al kernel / gestor de contenedores (Docker) |
| Uso ideal | **Servicios** (Oracle, correo, DNS) | **Aplicaciones**, servicios pequeños, distribuibles |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En Linux, los contenedores se apoyan en funciones del kernel como los `cgroups` (limitación de recursos), que ya aparecen en [[B2 - T4.3 LINUX]] como el mecanismo "usado por Docker" (junto con los directorios `/var/lib/docker` y `/var/lib/docker/volumes`). Los `namespaces` (aislamiento de procesos, red y ficheros) son la otra pieza clave y no vienen en el PDF.

### 4.1 Funcionamiento con Docker

Una **imagen** es **estática**; el **contenedor** es la representación de la imagen **en memoria, en ejecución**.

> [!note] Esquema del PDF (diagrama)
> `Dockerfile` —**build**→ `Docker Image` —**run**→ `Docker Container`.

**Paso 1.** Crear el fichero **Dockerfile** con la configuración de nuestra imagen (generalmente a partir de otra). Ejemplo del PDF:

```
FROM microsoft/mssql-server-linux      # FROM scratch: instalación desde cero
RUN mkdir -p /usr/src/app
...
RUN chmod +x ...
RUN apt-get ...
...
VOLUME /var/opt/mssql
EXPOSE 1433
```

| Elemento | Qué es |
|---|---|
| `FROM scratch` | Instalación **desde cero** |
| **Capas** | Cada comando crea una capa. Todas las capas son de **lectura (R)**, menos la **última (R/W)**. **Las capas se reutilizan** |
| **Alpine** y **BusyBox** | Imágenes de Linux **muy ligeras (< 5 MB)** |
| `docker scout` | Comprueba **CVEs** de cada capa de la imagen |
| `VOLUME /var/opt/mssql` | Almacenamiento **persistente** aunque se elimine el contenedor |
| Almacenamiento por defecto | **Efímero**: filosofía de **usar y tirar** |
| `EXPOSE 1433` | Puerto |

**Paso 2.** A partir de este fichero, creamos la imagen en disco: `docker build -t etiqueta`

**Paso 3.** Levantar un contenedor en memoria a partir de la imagen construida: `docker run -name mssql01 -d etiqueta -p 1433:1433`

> [!important] Imagen vs contenedor
> Imagen = estática, en disco, capas de solo lectura (la última R/W). Contenedor = esa imagen **en ejecución** en memoria. Flujo: `Dockerfile` → `docker build` → imagen → `docker run` → contenedor.

### 4.2 Orquestación: Kubernetes / Docker Swarm

Cuando hay **muchos contenedores y muchos nodos** donde distribuirlos (**orquestación**): **Kubernetes / Docker Swarm**. Permiten:

- **Escalar**.
- Meter **seguridad**: si se cae un nodo, **replica** ese contenedor en otro nodo.
- **Balancear** las ejecuciones de contenedores entre varios nodos; puede coger un contenedor de una máquina y llevárselo a otra menos saturada.
- Un contenedor concreto está en una máquina y Kubernetes puede **replicarlo** en varias.
- Usado en **Producción**. Es **multiplataforma**.
- Se instala en el **servidor central** y el agente **Kubelet** en los **nodos**.

**Pod**: agrupación de contenedores para administrarlos de forma agrupada. Se agrupan en una misma **IP** contenedores y volúmenes. **IP flotante**: una misma IP para varias máquinas o para varios contenedores.

> [!note] Esquema del PDF (diagrama de pods)
> Cuatro pods (`Pod 1` a `Pod 4`), cada uno con su dirección IP (10.10.10.x), con distinto número de contenedores y volúmenes dentro; la leyenda distingue **IP address**, **volume** y **containerized app**.

### 4.3 Open Container Initiative (OCI)

Proyecto de la **Linux Foundation** para definir especificaciones relativas a los contenedores para **estandarizar ejecución, imagen y distribución**:

| Especificación | Qué estandariza |
|---|---|
| **OCI Runtime Specification** | Entorno de ejecución de contenedores: **Container Runtime Interface (CRI)** |
| **OCI Image Format** | Formato de imagen, para poder usar una misma imagen con Docker u otros |
| **OCI Distribution Specification** | Distribución de imágenes; afecta a los **repositorios de imágenes**: DockerHub, Artifactory, Nexus, Archiva |

- Al principio Kubernetes solo funcionaba con Docker. Para poder ser **multicontainer** se crea la capa **CRI**, que es un **API**.
- **`runc`** es un componente que implementa OCI y es el **corazón de cualquier contenedor**. Cualquier contenedor usa runc; por runc pasa casi todo lo que se hace con los contenedores.

> [!note] Esquema del PDF (diagrama de capas)
> `docker` y `Kubernetes` → `Container Runtime Interface` → `containerd` / `CRI-O` → `Open Container Initiative (OCI) spec` → `runc` → `container` (dos).

### 4.4 Docker Compose

Permite gestionar **varios contenedores a la vez**. El fichero **`docker-compose.yml`** define los contenedores deseados y así se levanta todo de golpe, por ejemplo para tener un entorno de trabajo para desarrolladores.

> [!important] Compose vs Kubernetes
> **Docker Compose** gestiona varios contenedores **en una máquina**; **Kubernetes** los **distribuye** (entre nodos).

## 🔑 Resumen ultra-rápido

- Virtualización = abstracción SW (hipervisor / VMM) que multiplexa HW; ventajas: aprovechamiento del HW, **aislamiento**, aprovisionamiento bajo demanda. Cloud = demanda + tarificación por consumo + autoescalado.
- HW: **VT-x** (Intel), **VT-d** (E/S), **VT-c** (red), **AMD-V**.
- **Tipo 1** (sobre HW: KVM/Hyper-V/XEN, ESX, XCP-ng) vs **Tipo 2** (sobre SO, doméstico: VMware Player, VirtualBox, Parallels). **Hyper-V = Tipo 1** aunque se instale sobre Windows.
- Almacenamiento: bloque (LVM servidor, RAID dispositivo, SAN/vSAN con LUNs) vs fichero (NAS: NFS/CIFS/AFP). Backup: **VTL**. Puesto de usuario: **VDI** (Horizon / Xen Desktop) vs aplicaciones (Citrix XenApp).
- Formatos: **VMDK** (VMware), **OVF** (distribuir), **OVA** (OVF en TAR), **VMEM** (memoria al pausar), **VDI** (VirtualBox), **VHD** (Hyper-V).
- Contenedores: sin hipervisor, virtualizan el **kernel**; Docker, Podman, RKT, Mesos, LXC, OpenVZ. Para **aplicaciones** (la virtualización clásica para servicios).
- Docker: `Dockerfile` → `docker build -t` → imagen → `docker run` → contenedor. Capas de solo lectura (última R/W), se reutilizan; `VOLUME` = persistente; Alpine/BusyBox < 5 MB; `docker scout` = CVEs.
- **Kubernetes / Docker Swarm**: orquestación (escalar, replicar, balancear); servidor central + **Kubelet** en nodos. **Pod** = contenedores + volúmenes en una IP.
- **OCI** (Linux Foundation): Runtime (CRI), Image Format, Distribution. **runc** = corazón de cualquier contenedor.
- **Docker Compose** (`docker-compose.yml`, varios contenedores en una máquina) vs Kubernetes (los distribuye).
- IaaS (AWS: S3/EC2/EBS; OpenStack: Nova/Swift/Cinder/Neutron/Horizon; Azure, Google Cloud, Nube SARA), PaaS (OpenShift, Heroku, Cloud Foundry), SaaS, CaaS/KaaS.

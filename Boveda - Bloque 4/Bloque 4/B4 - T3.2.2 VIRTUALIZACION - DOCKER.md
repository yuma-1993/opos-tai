# Tema 3.2.2 · Bloque 4 — Laboratorio de virtualización: Docker y Kubernetes

> [!abstract] De qué va este tema
> Laboratorio práctico de la virtualización ligera vista en [[B4 - T3.2.1 VIRTUALIZACION]]: los comandos de Docker para gestionar imágenes y contenedores, un Dockerfile completo de ejemplo (PostgreSQL) con la tabla de instrucciones (`FROM`, `ENV`, `ARG`, `COPY`, `RUN`, `EXPOSE`, `VOLUME`, `WORKDIR`, `USER`, `CMD`, `ENTRYPOINT`), y el manejo de un clúster Kubernetes con `kubectl`, un fichero YAML de definición de pod y el glosario de objetos de Kubernetes.

> [!note] Esquema del PDF (diagrama "Thick vs. thin provisioning")
> La primera página incluye este diagrama de almacenamiento. **Thick provisioning**: cada volumen (A y B) tiene reservado espacio fijo (*Allocated, fixed and unused storage*) además de sus datos (*Data*); el espacio reservado no usado queda bloqueado. **Thin provisioning**: el almacenamiento disponible no reservado (*Available, unreserved storage*) es común y los volúmenes (A y B) solo ocupan el espacio de sus datos (*Data*).

## 1. Comandos de Docker

### 1.1 Información y estado

| Comando | Qué hace |
|---|---|
| `docker info` | Información sobre el uso de docker en el equipo |
| `docker version` | Versión del runtime docker |
| `docker ps` | Listado de los contenedores **activos** del sistema |
| `docker ps -a` | Todos los contenedores, **activos e inactivos** |
| `docker images` | Muestra todas las imágenes que tengo y algo de su información |
| `docker image ls` | ≈ `docker images` |

Salida de ejemplo de `docker info` (PDF):

```
Containers: 7
 Running: 0
 Paused: 0
 Stopped: 7
Images: 5
....
Registry: https://index.docker.io/v1/     → registry por defecto
Docker Root Dir: /var/lib/docker
```

Salida de ejemplo de `docker images`:

| REPOSITORY | TAG | IMAGE ID | CREATED | SIZE |
|---|---|---|---|---|
| centos | latest | 589dc4d40385 | 41 hours ago | 237MB |
| postgres | latest | ee227fd504c8 | 3 months ago | 348MB |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> `/var/lib/docker` (Docker Root Dir) y `/var/lib/docker/volumes` también aparecen como directorios clave de Docker en [[B2 - T4.3 LINUX]].

### 1.2 Ciclo de vida de contenedores e imágenes

| Comando | Qué hace |
|---|---|
| `docker pull imagen` | Descarga una imagen del hub (**DockerHub**). Ej.: `docker pull jenkins` |
| `docker run imagen` | **Arranca un nuevo contenedor** en base a una imagen y devuelve su identificador (≈ hash) |
| `docker create NombreImagen` | **Crea** un contenedor pero **no lo arranca** |
| `docker start/stop id_del_contenedor` | Arrancar y parar un contenedor |
| `docker kill id_contenedor` | Hace el stop de forma **inmediata** |
| `docker build -t NombreImagen:TagImagen` | Crea una imagen a partir del fichero **Dockerfile** situado en el directorio actual |
| `docker attach id_del_contenedor` | Enlaza la salida, la entrada y el error al contenedor. Permite **conectarnos / unirnos** a un contenedor en ejecución. Ej.: `docker attach 07b0b6f434fe` |
| `docker exec` | **Ejecutar un comando contra un contenedor en ejecución**. Ej.: `docker exec -it centos bash` (entramos en el bash del contenedor) |
| `docker export` | Guarda un contenedor en un **tar**, hace un **backup** |
| `docker commit` | Crea una **imagen a partir de un contenedor** ya en ejecución |
| `docker rm id_del_contenedor` | **Borrar contenedor**. Ej.: `docker rm 9f215ed0b0d3` |
| `docker rmi id_de_la_imagen` | **Borrar imágenes**. Ej.: `docker rmi 7a86f8ffcb25` |

> [!important] Pares confundibles
> `docker rm` borra **contenedores**; `docker rmi` borra **imágenes**. `docker create` crea pero **no arranca**; `docker run` crea **y arranca**. `docker stop` vs `docker kill` (inmediato). `docker attach` (se engancha a la entrada/salida del contenedor) vs `docker exec` (ejecuta un comando nuevo dentro). `docker commit` = imagen desde contenedor; `docker export` = contenedor a tar (backup).

### 1.3 `docker run` — mapeo de puertos y opciones

```
docker run -p 8080:8080 -p 50000:50000 jenkins
docker run centos -it /bin/bash
```

- El primer ejemplo arranca el contenedor con esos **mapeos de puertos `HOST:CONTAINER`**: el primer puerto es el **real** (el del host) y el siguiente es el de **Docker** (el del contenedor). Esto es **PAT** (*Port Address Translation*).
- El segundo levanta un contenedor con **CentOS en modo interactivo** y al finalizar nos saldrá el shell.

| Opción | Qué hace |
|---|---|
| `-p HOST:CONTAINER` | Mapeo de puertos (PAT) |
| `-v /usr/local/bin:/target` | Asocia un **volumen** con un almacenamiento externo. Formato `PATH_HOST:PATH_CONTAINER` |
| `-d` | Arranque en **segundo plano** |
| `-i` | **Interactivo** |
| `-t` | **tty** |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En la sintaxis real de Docker las opciones (`-it`, `-p`, `-d`...) van **antes** del nombre de la imagen y lo que va después es el comando a ejecutar dentro del contenedor (lo normal sería `docker run -it centos /bin/bash`). El PDF lo escribe como `docker run centos -it /bin/bash`; se respeta tal cual aparece en la fuente, pero conviene saber la forma habitual.

## 2. Dockerfile

### 2.1 Ejemplo del PDF: servicio PostgreSQL

Ejemplo de Dockerfile de la documentación de Docker (`docs.docker.com/engine/examples/postgresql_service/`), con sus comentarios originales en inglés:

```dockerfile
FROM ubuntu:16.04

# Add the PostgreSQL PGP key to verify their Debian packages.
# It should be the same key as https://www.postgresql.org/media/keys/ACCC4CF8.asc
RUN apt-key adv --keyserver hkp://p80.pool.sks-keyservers.net:80 --recv-keys B97B0AFCAA1A47F044F244A07FCC7D46ACCC4CF8

# Add PostgreSQL's repository. It contains the most recent stable release of PostgreSQL, ``9.3``.
RUN echo "deb http://apt.postgresql.org/pub/repos/apt/ precise-pgdg main" > /etc/apt/sources.list.d/pgdg.list

# Install ``python-software-properties``, ``software-properties-common`` and PostgreSQL 9.3.
# There are some warnings (in red) that show up during the build. You can hide them by
# prefixing each apt-get statement with DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y python-software-properties software-properties-common postgresql-9.3 postgresql-client-9.3 postgresql-contrib-9.3

# Note: The official Debian and Ubuntu images automatically ``apt-get clean`` after each ``apt-get``

# Run the rest of the commands as the ``postgres`` user created by the ``postgres-9.3`` package
# when it was ``apt-get installed``
USER postgres

# Create a PostgreSQL role named ``docker`` with ``docker`` as the password and then create
# a database `docker` owned by the ``docker`` role.
# Note: here we use ``&&\`` to run commands one after the other - the ``\`` allows the RUN command to span multiple lines.
RUN /etc/init.d/postgresql start &&\
    psql --command "CREATE USER docker WITH SUPERUSER PASSWORD 'docker';" &&\
    createdb -O docker docker

# Adjust PostgreSQL configuration so that remote connections to the database are possible.
RUN echo "host all all 0.0.0.0/0 md5" >> /etc/postgresql/9.3/main/pg_hba.conf

# And add ``listen_addresses`` to ``/etc/postgresql/9.3/main/postgresql.conf``
RUN echo "listen_addresses='*'" >> /etc/postgresql/9.3/main/postgresql.conf

# Expose the PostgreSQL port
EXPOSE 5432/tcp

# Add VOLUMEs to allow backup of config, logs and databases
VOLUME ["/etc/postgresql", "/var/log/postgresql", "/var/lib/postgresql"]

# Set the default command to run when starting the container
CMD ["/usr/lib/postgresql/9.3/bin/postgres", "-D", "/var/lib/postgresql/9.3/main", "-c", "config_file=/etc/postgresql/9.3/main/postgresql.conf"]
```

> [!note] Del PDF (anotación al final del ejemplo)
> Sobre el `CMD`, el PDF anota "**Arrancas el servicio de postgres**" y rotula los cuatro elementos de la lista como **1º param, 2º param, 3º param, 4º param** (ejecutable, `-D` con el directorio de datos, `-c`, y el fichero de configuración).

### 2.2 Instrucciones del Dockerfile

| Instrucción | Qué hace |
|---|---|
| `FROM` | Imagen:tag **base** (ubuntu, alpine, ...) a partir de la cual crear la nuestra |
| `ENV` | Define **variables de entorno**. Existe durante la construcción de la imagen **y** en el contenedor durante su ejecución |
| `ARG` | Crea variables que **solo se usan durante la creación**, no durante la ejecución |
| `COPY` | Copiar desde el HOST/url **hacia dentro de la imagen**. Copias en la imagen **cuando se crea**, no cuando se ejecuta |
| `RUN` | Ejecución de comandos: apt, mkdir, etc. |
| `EXPOSE` | Exponer puertos **en el CONTAINER**. **Solo con esto no podremos acceder desde el HOST** |
| `VOLUME` | Define un directorio cuya información será **persistente** |
| `WORKDIR` | Establece el **directorio de trabajo** |
| `USER` | Usuario con el que se ejecutarán las acciones; **por defecto será root** |
| `CMD` | Comando + argumentos **por defecto** que se ejecutará cuando se inicie un CONTAINER con esta imagen. **Solo puede haber un `CMD`** en el Dockerfile. Se puede **sobrescribir** con `docker run` |
| `ENTRYPOINT` | **No se puede sobrescribir** (CMD sí). El resto es igual que CMD |

> [!example] CMD sobrescrito
> Con `CMD ["echo", "Hola Mundo"]` en el Dockerfile y una imagen llamada `prueba`:
> - `docker run prueba` → muestra "Hola Mundo".
> - `docker run prueba df` → **no** muestra "Hola Mundo", sino que hace un `df` (el argumento sobrescribe el `CMD`).

> [!important] Diferencias que caen
> `ENV` (existe en construcción **y** ejecución) vs `ARG` (**solo** construcción). `EXPOSE` solo expone en el contenedor: para acceder desde el host hace falta el mapeo `-p`. `CMD` se puede sobrescribir; `ENTRYPOINT` no (según el PDF). `USER` por defecto = root.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Matiz sobre `ENTRYPOINT`: en Docker real se puede cambiar en el arranque con la opción `--entrypoint` de `docker run`; lo que no sucede es que los argumentos pasados tras el nombre de la imagen lo sustituyan (a diferencia de `CMD`). Para el examen, la regla de la fuente es: CMD sí se sobrescribe, ENTRYPOINT no. Para el resto de elementos del Dockerfile (capas, `VOLUME`, `FROM scratch`...) ver [[B4 - T3.2.1 VIRTUALIZACION]]. `RUN apt-get` se apoya en los gestores de paquetes de [[Gestores de paquetes (apt, yum, dpkg, rpm)]].

## 3. Kubernetes: `kubectl`

`kubectl` sirve para **manejar un clúster de contenedores sobre una infraestructura de nodos distribuida**.

### 3.1 Fichero `definicion_pods.yaml`

```yaml
# Número de versión del api que se quiere utilizar
apiVersion: v1
# Tipo de fichero que se va a crear.
kind: Pod
# Aquí van los datos propios del pod como el nombre y los labels que tiene asociados para seleccionarlo
metadata:
   name: my-nginx
   # Especificamos que el pod tenga un label con clave "app" y valor "nginx"
   labels:
      app: nginx
# Contiene la especificación del pod
spec:
# Aquí se nombran los contenedores que forman parte de este pod. Todos estos contenedores serían visibles por localhost
   containers:
      - name: nginx
        image: nginx
        ports:
         - containerPort: 80
# Aquí se define la política de restauración en caso de que el pod se detenga o deje de ejecutarse debido a un fallo interno.
   restartPolicy: Always
```

| Campo | Significado |
|---|---|
| `apiVersion` | Versión del API que se quiere utilizar |
| `kind` | Tipo de objeto que se va a crear (aquí `Pod`) |
| `metadata` | Datos propios del pod: nombre y **labels** para seleccionarlo (aquí `app: nginx`) |
| `spec` | Especificación del pod |
| `containers` | Contenedores del pod. **Todos serían visibles por `localhost`** |
| `restartPolicy: Always` | Política de restauración si el pod se detiene o falla internamente |

### 3.2 Comandos `kubectl`

| Comando | Qué hace |
|---|---|
| `kubectl apply -f definicion_pods.yaml` | Crea el pod en **modo declarativo** |
| `kubectl create -f definicion_pods.yaml` | Crea el pod en **modo imperativo** |
| `kubectl run my-nginx --image=nginx --port=80` | Creación de un pod **sin YAML** |
| `kubectl get pods` | Pods que están ejecutándose |
| `kubectl describe pod nombreDelPod` | Info más detallada del pod |
| `kubectl get nodes` | Nodos en el clúster |
| `kubectl logs my-nginx` | Logs del pod |

> [!important] apply vs create
> `kubectl apply` = **declarativo** (describes el estado deseado); `kubectl create` = **imperativo**. Misma distinción declarativo/imperativo que en la gestión de configuración (ver [[Idempotencia]] y [[IaC (Infrastructure as Code)]]).

### 3.3 Glosario de Kubernetes

| Concepto | Definición (según el PDF) |
|---|---|
| **Cluster** | Conjunto de máquinas **físicas o virtuales** y otros recursos utilizados por Kubernetes |
| **Nodo** | Una máquina física o virtual ejecutándose en Kubernetes donde los **pods pueden ser programados** |
| **Pod** | La **unidad más pequeña desplegable** que puede ser creada, programada y manejada por Kubernetes. Es un grupo de **uno o más contenedores**, con **almacenamiento compartido** entre ellos |
| **Replication Controller** | Se asegura de que el **número especificado de réplicas** del pod estén ejecutándose. Permite **escalar** fácilmente los sistemas y maneja la **re-creación de un pod** cuando ocurre un fallo |
| **Service** | **Abstracción** que define un conjunto de pods y la lógica para acceder a los mismos |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> La orquestación con Kubernetes y los conceptos nodo/clúster/pod/servicio/volumen/namespace también se resumen desde el punto de vista de los microservicios en [[B4 - T3.3 MICROSERVICIOS]].

## 🔑 Resumen ultra-rápido

- `docker info` (estado; registry por defecto `https://index.docker.io/v1/`; root dir `/var/lib/docker`), `docker version`, `docker ps` (activos) / `ps -a` (todos), `docker images` ≈ `docker image ls`.
- `docker pull` (DockerHub) / `docker run` (crea + arranca; devuelve hash) / `docker create` (no arranca) / `docker start`/`stop` / `docker kill` (stop inmediato).
- `docker run -p HOST:CONTAINER` (PAT; primero puerto real/host), `-v PATH_HOST:PATH_CONTAINER` (volumen), `-d` (segundo plano), `-i` (interactivo), `-t` (tty).
- `docker build -t Nombre:Tag` (desde Dockerfile del directorio actual), `docker attach` (enlaza entrada/salida/error), `docker exec -it centos bash` (comando en contenedor en ejecución), `docker export` (contenedor → tar, backup), `docker commit` (contenedor → imagen), `docker rm` (contenedor), `docker rmi` (imagen).
- Dockerfile: `FROM` (base), `ENV` (construcción + ejecución), `ARG` (solo construcción), `COPY` (host→imagen al crear), `RUN`, `EXPOSE` (solo en container; no basta para acceder desde el host), `VOLUME` (persistente), `WORKDIR`, `USER` (por defecto root), `CMD` (uno solo, sobrescribible con `docker run`), `ENTRYPOINT` (no sobrescribible).
- `kubectl apply -f` (declarativo) vs `create -f` (imperativo); `run my-nginx --image=nginx --port=80` (sin YAML); `get pods`, `describe pod`, `get nodes`, `logs`.
- Pod YAML: `apiVersion`, `kind: Pod`, `metadata` (`name`, `labels`), `spec.containers` (visibles por `localhost`), `restartPolicy: Always`.
- Kubernetes: **Cluster** (máquinas), **Nodo** (donde se programan pods), **Pod** (unidad mínima desplegable, 1+ contenedores, almacenamiento compartido), **Replication Controller** (nº de réplicas, recrea), **Service** (abstracción de conjunto de pods + acceso).
- Thick provisioning (reserva fija por volumen) vs thin provisioning (espacio compartido no reservado, el volumen ocupa solo lo que usa).

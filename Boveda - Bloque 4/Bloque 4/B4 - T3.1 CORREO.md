# Tema 3.1 · Bloque 4 — Correo electrónico

> [!abstract] De qué va este tema
> El correo electrónico se reparte entre cinco agentes (MUA, MSA, MTA, MDA, MAA) que usan SMTP para enviar y POP3/IMAP para leer; el mensaje tiene un formato (RFC 822 + extensión MIME) y se protege con SPF, DKIM, DMARC, ARC y DANE, todos ellos apoyados en registros del DNS (MX, TXT, TLSA...). Por eso el tema termina con la arquitectura DNS y la lista de tipos de registro, que es la pieza que une todo lo demás.

---

## 1. Agentes del correo

> [!note] Esquema del PDF (diagrama)
> **Origen**: `MUA` → (LAN/Internet) → `MTA / MSA` (por **SMTP**, formato RFC 822 + MIME); el MTA/MSA consulta al `DNS` el *MX Record* del dominio destino.
> **Destino**: `MTA` (Recepción) → `MDA` → `Mail Spool` → `MAA` (Acceso, por **IMAP/POP3**) → `MUA` del destinatario.

| Siglas | Nombre | Papel |
|---|---|---|
| **MUA** | Mail User Agent | Cliente de correo del usuario |
| **MTA** | Mail Transfer Agent | Servidor que transfiere el correo entre dominios |
| **MSA** | Mail Submission Agent | Recibe el envío de los MUA dentro de una organización |
| **MDA** | Mail Delivery Agent | Entrega el mensaje al buzón (spool) |
| **MAA** | Mail Access Agent | Da acceso al buzón al usuario (IMAP/POP3) |

- Una **MTA por cada dominio**. Las **MSA** se usan para gobernar en una organización el envío de mails, para distribuir y dividir de forma controlada el envío y no tumbar las MTAs.
- Mi MUA alcanza mi MTA porque antes se configura el **servidor saliente y entrante**.
- Si en el MAA hubiese un **webmail**, como OWA, no iría por IMAP/POP3 sino por **HTTP**.
- El **spool** está orientado a la **recepción**, no al envío. Son los **buzones de correo**. Almacenamiento físico: `/var/spool/mail` (ver [[B2 - T4.3 LINUX]], donde aparece entre los directorios clave de Linux; el concepto genérico de spool como cola de espera está en [[Spooling]]).

## 2. Formato del correo electrónico

### 2.1 RFC 822

- **Solo texto** (ASCII: 7+1 bits). **No permite mandar ficheros adjuntos.**
- Cabeceras: `From:` `Date:` `To:` `Subject:` `Message-ID:` `In-Reply-To:` `Received:` `Return-Path:` `CC:` `Reply-To:` + `<CRLF>` + `Body:`.

| Cabecera | Para qué sirve (según el PDF) |
|---|---|
| `Message-ID` | La usa la MTA y se usa para **agrupar por hilos de conversación** |
| `Received` y `Return-Path` | **Trazabilidad** de la MTA, ya que el mensaje puede pasar por varias MTAs hasta alcanzar el destino |

### 2.2 Extensión MIME

- Cabecera `MIME-Version:`
- `Content-Type:` `text/plain`; `multipart/mixed`; `multipart/alternative`; `application/pdf`; `image/gif`; `video/mpeg`... + `boundary = ………`: identificador que encontramos en el **body** para indicar **cambio de contenido**.
- `Content-Transfer-Encoding:` `7 bit` / `8 bit` / `binary` / `quoted-printable` / `base64`.

> [!note] Esquema del PDF (ejemplo de mensaje MIME)
> El PDF incluye una imagen (pequeña, texto poco legible) de un mensaje con la cabecera general (`Date`, `From`, `To`, `Subject`, `MIME-Version: 1.0`, `Content-Type: multipart/mixed` con su `boundary`) y dos partes del cuerpo (*Body part 1* y *Body part 2*) separadas por el `boundary`: cada una con su propia cabecera (`Content-Type: text/xml`, `Content-Transfer-Encoding: quoted-printable`) y su *payload* (un XML).

> [!important] RFC 822 vs MIME
> RFC 822 solo admite texto ASCII y **no permite adjuntos**; es la extensión **MIME** la que lo hace posible (`multipart/*`, `boundary`, codificaciones `base64`/`quoted-printable`).

> [!note] Ampliación (conocimiento general, no viene del PDF)
> `base64` y `quoted-printable` son codificaciones que convierten datos binarios o con caracteres no ASCII en texto de 7 bits para que atraviesen sin daño sistemas que solo manejan ASCII. Es el mecanismo por el que un adjunto binario (PDF, imagen) puede viajar dentro de un correo que, por debajo, sigue siendo texto.

## 3. Protocolos

### 3.1 Comparativa de puertos

| Protocolo | Función | Puerto | Puerto seguro |
|---|---|---|---|
| **POP3** (Post Office Protocol) | Recepción. Orientado a **descarga**. Muy simple | **110** | **995** |
| **IMAP** (Internet Message Access Protocol) | Recepción. **Carpetas en el servidor**, uso **online** | **143** | **993** |
| **SMTP** (Simple Mail Transfer Protocol) | Envío / transferencia | **25** y también **2525** | **587** (el **465** ha quedado **obsoleto**) |

### 3.2 POP3 — comandos

| Comando | Qué hace |
|---|---|
| `USER texto` / `PASS texto` | Usuario y contraseña |
| `LIST` | Lista nº de mensajes y tamaño |
| `RETR nº mensaje` | Descarga el mensaje |
| `DELE nº mensaje` | **Marca** el mensaje para borrado |
| `STAT` | Muestra el total de mensajes y el tamaño |
| `QUIT` | Sale. **Si hago `DELE` y luego `QUIT`, borra** |

### 3.3 IMAP — comandos

| Comando | Qué hace |
|---|---|
| `LOGIN username@dominio password` | Autenticación |
| `LIST <mailbox path> <search argument>` | Carpetas (*folders*) |
| `STATUS <mailbox name> <status data>` | Mensajes (`MESSAGES`, `RECENT`, `UNSEEN`, ...) |
| `SELECT <mailbox path>` | Selecciona un buzón |
| `EXAMINE` | Como `SELECT` pero **solo lectura** |
| `FETCH` | Leer contenido, headers, etc. (`BODY[TEXT]`, `BODY[HEADER]`, `FLAGS`, `UID`) |
| `SEARCH <criteria>` | `FROM`/`TO`, `DATE`/`SINCE`/`BEFORE`, `BODY`... `DELETED` |
| `STORE Flags` | Modifica *flags*. Los mensajes tienen una especie de estado; con `STORE` cambiamos esos flags. Uno de ellos es `\Deleted` ≈ `DELE` |
| `EXPUNGE` | Borra los mensajes con el flag `\Deleted` activado. ≈ `QUIT` |

> [!important] Equivalencias POP3 ↔ IMAP en el borrado
> `DELE` (POP3) ≈ `STORE ... \Deleted` (IMAP): solo **marcan**. `QUIT` (POP3) ≈ `EXPUNGE` (IMAP): es lo que **borra de verdad**.

> [!important] POP3 vs IMAP
> POP3 = orientado a descarga, muy simple. IMAP = carpetas y mensajes **en el servidor**, uso online. Puertos: 110/995 y 143/993.

### 3.4 SMTP — comandos

```
HELO client.example.com
MAIL FROM: <carlos@ibm.com>
RCPT TO: <dani@indra.com>
DATA ……… <CRLF>.<CRLF>
QUIT
```

- `DATA`: cuando haya una línea con **únicamente un punto "."**, finalizará el comando `DATA`.

### 3.5 ESMTP (Enhanced SMTP)

Versión mejorada de SMTP.

| Comando | Qué hace |
|---|---|
| `EHLO client.example.com` | Las letras **E y H intercambiadas** (respecto a `HELO`) indican que se quiere ESMTP |
| `STARTTLS` | Característica para pasar de modo **no seguro (puerto 25)** a modo **seguro (puerto 587)**. No solo sirve para correo. Hace *handshake* como el de HTTP |
| `AUTH PLAIN Base64 (credenciales)` | Se manda usuario y contraseña **sin cifrar** |
| `AUTH LOGIN` | Se manda usuario y contraseña **en 2 pasos**, no en 1 como PLAIN. Las credenciales van en **texto claro**, por eso es importante **cifrar el canal** |

> [!tip] Truco
> `HELO` → SMTP clásico; `EHLO` (E y H intercambiadas) → ESMTP. `AUTH PLAIN` = 1 paso, `AUTH LOGIN` = 2 pasos; ambos en claro, así que se usan tras `STARTTLS`.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Por eso el orden habitual en una sesión ESMTP segura es: `EHLO` → `STARTTLS` (el canal pasa a cifrado) → `AUTH` (ya cifradas, las credenciales viajan protegidas). El handshake TLS es el mismo mecanismo que se ve en HTTPS (ver [[Certificado TLS-SSL (X.509)]]).

## 5. Securización del correo

| Mecanismo | Nombre completo | Qué hace |
|---|---|---|
| **SPF** | Sender Policy Framework | Especifica **qué servidores están autorizados a enviar** correos en nombre del dominio. Se comprueban las **IPs autorizadas** en el **registro TXT** |
| **DKIM** | Domain Keys Identified Mail | Agrega una **firma digital** a cada correo que se envía desde su dominio. La **clave pública** está registrada en un **registro TXT** |
| **DMARC** | Domain-based Message Authentication, Reporting & Conformance | **Complementa a SPF y DKIM**. Indica **qué hacer** si los correos no pasan SPF o DKIM |
| **ARC** | Authenticated Received Chain | Verifica la autenticación de correo de los mensajes **reenviados** y los servidores de reenvío. **Añade cabeceras** |
| **DANE** | DNS-Based Authentication of Named Entities | Infraestructura **DNSSEC**. Usa los registros **TLSA**. Establece **canal seguro remitente-destinatario** |

> [!important] Qué registro DNS usa cada uno
> SPF → registro **TXT** (IPs autorizadas). DKIM → registro **TXT** (clave pública). DMARC → complementa a ambos (qué hacer si fallan). DANE → registro **TLSA** + DNSSEC.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> La firma DKIM usa [[Criptografía asimétrica (clave pública y privada)]]: el servidor emisor firma con la clave privada y el receptor verifica con la clave pública que publica el dominio en el TXT. En DMARC, el dominio indica su política (`none`, `quarantine` o `reject`) para los mensajes que no pasan las comprobaciones.

> [!note] Cotejo con "Actualizaciones 20_05_2026"
> El documento de actualizaciones del autor solo registra para este tema: las expansiones de siglas de POP3, IMAP, SMTP y ESMTP (22/01/2026), el método ARC (14/10/2024) y el método DANE con el registro TLSA (25/04/2025), junto con una explicación más sencilla de los métodos de securización. Todo ello ya figura en el PDF y en esta nota; no hay erratas que corregir.

## 6. Arquitectura DNS

El DNS interviene en cada servicio que usa un nombre de host. El **resolver** es mi servidor DNS (`/etc/resolv.conf`, ver [[B2 - T4.3 LINUX]]; comandos `nslookup`/`dig` en la fila "Red" de [[B4 - T1.1 ADMON SSOO]]).

### 6.1 Resolución paso a paso

> [!note] Esquema del PDF (diagrama)
> PC ↔ DNS Resolver (petición **recursiva**, flechas 1 y 8) y el Resolver ↔ Servidor Root (2-3), Servidor TLD (4-5) y Servidor Autoritativo (6-7) con peticiones **iterativas**.

1. Preguntamos al **resolver** por ese dominio. Si lo tiene **cacheado** nos da la IP; si no, pregunta al **Root Server**.
2. El **Root Server** nos dice el servidor **Top-Level Domain** que lleva el dominio por el que pregunto.
3. El **Top-Level Domain** nos dice qué servidor **Autoritativo** lleva ese dominio.
4. Preguntamos al **DNS Autoritativo** por la entrada/registro "A".
5. Con la IP del registro "A" tenemos que `www.domain.com` es `173.204.151.53`.

Un **registro DNS** es un componente de las bases de datos de los servidores autoritativos.

### 6.2 Tipos de registro

| Registro | Función | Ejemplo del PDF |
|---|---|---|
| **A** | Direcciones IP correspondientes a tus dominios y subdominios | `www.example.com. 12879 IN A 93.184.216.34` |
| **PTR** | Búsqueda **inversa** (IP → nombre) | `34.216.184.93.in-addr.arpa. IN PTR ruinosa.com.` |
| **MX** | Especifica a un **MTA emisor** en qué MTA(s) deberían ser entregados los emails | `example.com. IN MX 10 mail1.example.com.` / `IN MX 20 mail2...` / `IN MX 30 mail3...` |
| **CNAME** | Redirecciones desde subdominios a otros dominios/subdominios. Una especie de **alias** | `www.example.net. CNAME www.example.com` |
| **TXT** | Almacenar info relacionada con tu dominio. Muy común: **SPF**, para prevenir ataques de *spoofing* | `gmx.es. IN TXT 14400 v=spf1 ip4:213.165.64.0/23 ip4:74.208.5.64/26 … ip4:82.165.159.0/24 -all` |
| **AAAA** | Mapea un nombre de dominio a la dirección **IPv6** del ordenador que aloja el dominio | `www.example.com. IN AAAA 2606:2800:220:1:248:1893:25c8:1946` |
| **SRV** | Indica qué **servicios** queremos ofrecer bajo nuestro dominio. Ejemplo: VoIP. No solo se usa CNAME para algunos servicios | Formato general: `_service._proto.name. TTL class SRV priority weight port target`. SIP: `_sip._tcp.example.com. 86400 IN SRV 0 5 5060 sipserver.example.com.`. Correo (MSA): `_submission._tcp.example.com. SRV 0 1 587 mail.example.com.` |
| **CAA** | **Restringir qué entidades pueden expedir certificados** para un dominio | `acme.com. CAA 0 issue "comodo.com"` / `acme.com. CAA 0 issue "letsencrypt.org"` |
| **SOA** | "Inicio De Autoridad": info importante sobre un dominio o zona: **email del administrador**, cuándo se actualizó por última vez, **tiempos de refresco, reintento, caducidad y TTL mínimo** | — |
| **TLSA** | TLS Authentication. Almacena las **huellas digitales de un certificado TLS/SSL** | — |

> [!important] Registros clave para el correo
> **MX** (a qué MTA entregar; el número menor = mayor prioridad, ver ampliación), **TXT** (SPF y clave pública de DKIM), **TLSA** (DANE), **SRV** (servicio `_submission._tcp` del MSA en el puerto 587), **PTR** (resolución inversa).

> [!note] Ampliación (conocimiento general, no viene del PDF)
> En un registro MX el número (10, 20, 30) es la **preferencia**: el MTA emisor prueba primero el de valor más bajo y pasa al siguiente solo si ese no responde. Los registros TXT con SPF terminan en `-all` (rechazar lo no autorizado) o `~all` (marcar como sospechoso, *softfail*); el PDF muestra el ejemplo con `-all`.

## 🔑 Resumen ultra-rápido

- Agentes: **MUA** (cliente), **MSA** (envío controlado en la organización), **MTA** (una por dominio), **MDA** (entrega al buzón), **MAA** (acceso al buzón: IMAP/POP3; un webmail como OWA va por **HTTP**).
- Spool = buzones de **recepción**, `/var/spool/mail`.
- **RFC 822**: solo ASCII (7+1 bits), sin adjuntos. Cabeceras `From/Date/To/Subject/Message-ID/In-Reply-To/Received/Return-Path/CC/Reply-To`. `Message-ID` = hilos; `Received` + `Return-Path` = trazabilidad.
- **MIME**: `MIME-Version`, `Content-Type` (`multipart/mixed`, `multipart/alternative`, `application/pdf`, `image/gif`, `video/mpeg`; `boundary` = cambio de contenido), `Content-Transfer-Encoding` (7bit/8bit/binary/quoted-printable/base64).
- **POP3** 110/995 (descarga, simple; `USER PASS LIST RETR DELE STAT QUIT`, DELE+QUIT borra). **IMAP** 143/993 (carpetas en servidor; `SELECT`/`EXAMINE`/`FETCH`/`SEARCH`/`STORE`/`EXPUNGE`). **SMTP** 25 y 2525 / 587 seguro (465 obsoleto).
- SMTP: `HELO`, `MAIL FROM`, `RCPT TO`, `DATA` (termina con línea con solo `.`), `QUIT`. ESMTP: `EHLO`, `STARTTLS` (25 → 587), `AUTH PLAIN` (1 paso) / `AUTH LOGIN` (2 pasos), ambos en claro.
- Seguridad: **SPF** (IPs autorizadas, TXT), **DKIM** (firma digital, clave pública en TXT), **DMARC** (qué hacer si fallan SPF/DKIM), **ARC** (mensajes reenviados, añade cabeceras), **DANE** (DNSSEC + TLSA, canal seguro).
- DNS: resolver → Root → TLD → Autoritativo → registro A. Registros: A, PTR (inverso), MX, CNAME (alias), TXT (SPF), AAAA (IPv6), SRV, CAA (quién emite certificados), SOA (inicio de autoridad), TLSA (huella de certificado).

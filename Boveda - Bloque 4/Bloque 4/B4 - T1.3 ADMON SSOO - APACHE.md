# Tema 1.3 · Bloque 4 — Administración de Sistemas Operativos: Apache HTTP Server 2.x

> [!abstract] De qué va este tema
> Laboratorio práctico de Apache HTTP Server 2.x: activación de sites y módulos mediante enlaces simbólicos (`a2ensite`, `a2enmod`), gestión del servicio (`apache2ctl`/`apachectl`), ubicación de los ficheros de configuración según distribución (Debian vs Red Hat), y un ejemplo completo de configuración con `VirtualHost` y SSL. Es la tercera práctica de administración de sistemas, tras la gestión general del sistema ([[B4 - T1.1 ADMON SSOO]]) y SSH ([[B4 - T1.2 ADMON SSOO - SSH]]).

> [!note] Ver también
> El playbook de ejemplo de [[B4 - T1.4 ADMON SSOO - ANSIBLE]] instala precisamente el paquete `apache2` que se configura en detalle en este tema.

## 1. Activación de sites y módulos

Ver [[a2ensite y a2enmod (activación de sites y módulos en Apache)]].

### 1.1 `a2ensite` — activar configuración de un site

- `a2ensite 100-ruinosa.conf` activa la configuración de ese site.
- En realidad se hacen unos enlaces simbólicos entre ficheros del directorio `sites_available` y `sites_enabled`, dentro de `/etc/apache2`.

### 1.2 `a2enmod` — activar módulos

- `a2enmod ssl` activa el módulo de SSL.
- En realidad se hacen unos enlaces simbólicos entre ficheros del directorio `mods_available` y `mods_enabled`, dentro de `/etc/apache2`.

> [!note] Aclaración (conocimiento general, no viene del PDF)
> El texto extraído del PDF escribe estos directorios con guion bajo (`sites_available`, `sites_enabled`, `mods_available`, `mods_enabled`). La convención real de Apache en Debian/Ubuntu usa guion medio: `sites-available`, `sites-enabled`, `mods-available`, `mods-enabled`. Dejo el nombre tal cual aparece en el PDF en el cuerpo principal (regla de no perder información de la fuente), pero aviso aquí de la diferencia por si el guion bajo es un artefacto de la extracción del texto del PDF y no lo que aparece realmente en la imagen original.

> [!note] Ampliación (conocimiento general, no viene del PDF)
> El mecanismo es idéntico en ambos casos: `sites-available`/`mods-available` contienen **todas** las configuraciones/módulos instalados, estén activos o no; `sites-enabled`/`mods-enabled` contienen solo enlaces simbólicos a los que están realmente activos. Por eso "activar" no es instalar ni escribir configuración nueva, es simplemente crear ese enlace — y "desactivar" (con los comandos complementarios `a2dissite`/`a2dismod`, que no aparecen en el PDF pero son el par natural de `a2ensite`/`a2enmod`) es borrarlo, sin tocar el fichero original. Esto permite tener una configuración guardada pero apagada, lista para reactivar sin volver a escribirla.

## 2. Gestión del servicio: `apache2ctl` / `apachectl`

Ver [[apache2ctl y apachectl (gestión del servicio Apache)]].

| Comando | Qué hace |
|---|---|
| `apache2ctl status` / `apache2ctl fullstatus` | Estado del servicio |
| `apache2ctl start` / `stop` / `restart` | Arrancar/parar/reiniciar el servicio |
| `apache2ctl -M` | Ver los módulos activos |
| `apache2ctl -t` | Test del fichero de configuración |

> [!note] Ampliación (conocimiento general, no viene del PDF)
> `apache2ctl` y `apachectl` son el mismo binario (el nombre cambia según la distribución/paquete). `apache2ctl -t` es el comando que conviene ejecutar siempre antes de un `restart` en producción: si el fichero de configuración tiene un error de sintaxis, un `restart` directo puede dejar el servicio caído sin arrancar; `-t` valida la sintaxis sin llegar a recargar nada.

## 3. Ficheros de configuración según distribución

| Distribución | Fichero principal |
|---|---|
| Debian | `/etc/apache2/apache2.conf` |
| Red Hat | `/etc/httpd/conf/httpd.conf` |

> [!important] Idea clave para el examen
> El patrón Debian vs Red Hat se repite: mismo servicio, ficheros/directorios distintos (`apache2` vs `httpd`). Es el mismo tipo de diferencia ya vista en la gestión de paquetes en [[B4 - T1.1 ADMON SSOO]] (`apt` + `/etc/apt/sources.list` en Debian frente a `yum` + `/etc/yum.repos.d` en Red Hat): cada familia de distribuciones tiene su propia convención de nombres y rutas para el mismo concepto.

## 4. Ejemplo de configuración: `VirtualHost` con SSL

```apache
<VirtualHost *:443>
    ServerName www.example.com
    ServerAlias example.com
    DocumentRoot /var/www/example.com/public_html
    ErrorLog /var/www/example.com/error.log
    CustomLog /var/www/example.com/requests.log combined
    SSLEngine on
    SSLCertificateFile /etc/apache2/ssl/example/apache.crt
    SSLCertificateKeyFile /etc/apache2/ssl/example/apache.key
</VirtualHost>

<VirtualHost *:443>
    ServerName www.example2.com
    DocumentRoot /var/www/example2.com/public_html
    ServerAlias example2.com
    ErrorLog /var/www/example2.com/error.log
    CustomLog /var/www/example2.com/requests.log combined
    SSLEngine on
    SSLCertificateFile /etc/apache2/ssl/example2/apache.crt
    SSLCertificateKeyFile /etc/apache2/ssl/example2/apache.key
</VirtualHost>
```

> [!note] Ampliación (conocimiento general, no viene del PDF)
> Un [[VirtualHost (Apache)|VirtualHost]] permite que un único servidor Apache sirva varios sitios web distintos, cada uno con su propio `ServerName`, `DocumentRoot` y logs — es la base del hosting compartido. Cada bloque define: a qué dominio responde (`ServerName`/`ServerAlias`), de dónde sirve los ficheros (`DocumentRoot`), y dónde registra accesos y errores (`CustomLog`/`ErrorLog`).
>
> El ejemplo del PDF tiene un matiz técnico interesante: los dos `VirtualHost` escuchan en el mismo puerto (`*:443`) pero con `ServerName` distinto. Con HTTPS "clásico" esto es problemático, porque el certificado SSL se negocia **antes** de que el servidor sepa a qué `ServerName` va dirigida la petición (el nombre de dominio va dentro de la petición HTTP, que todavía está cifrada en ese momento) — así que Apache no sabría qué certificado (`example.crt` o `example2.crt`) presentar. La extensión que resuelve esto es [[SNI (Server Name Indication)|SNI (Server Name Indication)]], que envía el nombre de dominio sin cifrar durante el propio saludo TLS, permitiendo elegir el certificado correcto antes de completar el cifrado. Prácticamente todos los navegadores y versiones modernas de Apache lo soportan, pero es la pieza que hace que un ejemplo como este funcione en la práctica.

> [!important] No confundir con las claves de [[B4 - T1.2 ADMON SSOO - SSH|SSH]]
> `SSLCertificateFile`/`SSLCertificateKeyFile` son un [[Certificado TLS-SSL (X.509)|certificado y una clave privada X.509/TLS]], emitidos (normalmente) por una autoridad de certificación y usados para cifrar el tráfico HTTP del sitio web. No tienen relación con el par de [[Criptografía asimétrica (clave pública y privada)|claves RSA]] de usuario (`id_rsa`/`id_rsa.pub`) ni con las claves de host (`ssh_host_rsa_key`, etc.) de SSH — son dos sistemas de PKI distintos que resuelven problemas distintos (cifrar una web pública para cualquier visitante vs autenticar una sesión de administración remota).

## 🔑 Resumen ultra-rápido

- `a2ensite`/`a2enmod`: activan site/módulo creando un enlace simbólico entre `*_available` y `*_enabled` dentro de `/etc/apache2` (no instalan nada nuevo).
- `apache2ctl`/`apachectl`: `status`/`fullstatus`, `start`/`stop`/`restart`, `-M` (módulos activos), `-t` (test de sintaxis antes de recargar).
- Fichero de configuración principal: Debian → `/etc/apache2/apache2.conf`; Red Hat → `/etc/httpd/conf/httpd.conf` (mismo patrón Debian/RedHat que en [[B4 - T1.1 ADMON SSOO]]).
- `VirtualHost`: un servidor, varios sitios (`ServerName`, `DocumentRoot`, `ErrorLog`/`CustomLog` por sitio).
- SSL en Apache: `SSLEngine on` + `SSLCertificateFile` + `SSLCertificateKeyFile`. Certificado TLS del sitio web, no confundir con las claves RSA de SSH ([[B4 - T1.2 ADMON SSOO - SSH]]).
